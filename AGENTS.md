# Agent Instructions: Multitenant Budget RAG (Nels)

This repository contains Nels, a personal budgeting co-pilot with a Rust backend, a Svelte 5 frontend app, and a SvelteKit marketing site.

## Repo Boundaries & Tech Stack
- **/backend**: Rust web API using `axum`, `sqlx` (PostgreSQL + `pgvector`), and `totp-rs`.
- **/frontend**: Svelte 5 (Vite PWA) using `pnpm`, `@tailwindcss/vite` (Tailwind v4), and `daisyui` v5. The authenticated product app.
- **/marketing**: SvelteKit 2 (Svelte 5 runes) marketing website, fully prerendered to static HTML, `@tailwindcss/vite` (Tailwind v4) + `daisyui` v5, `@sveltejs/adapter-cloudflare`. Public, SEO-focused; deployed to Cloudflare Pages at `nels.money`. Its CTA links to the app signup.
- **/admin**: A NEW Svelte 5 (Vite PWA) admin console using `pnpm`, `@tailwindcss/vite` (Tailwind v4), and `daisyui` v5. A standalone, installable PWA. TOTP login gated on `users.is_admin`; consumes `GET /api/admin/users`. Deployed to Cloudflare Pages project `nels-admin`.

## Critical Quirks & Caveats

### 1. Authentication (TOTP)
- **No Password Authentication**: The app uses TOTP (RFC 6238) authenticator codes — no passwords. Both flows are two-step: `start` (by email) returns a `flow_id`; `finish` submits `{flow_id, code}`.
  - **Register**: `POST /api/auth/register/start {email}` → `{flow_id, secret, url}` (the `url` is an `otpauth://` URI for the QR code; `secret` is the base32 key for manual entry). `POST /api/auth/register/finish {flow_id, code}` → `{token, user}`.
  - **Login**: `POST /api/auth/login/start {email}` → `{flow_id}`. `POST /api/auth/login/finish {flow_id, code}` → `{token, user}`.
- **DB-Backed Challenges & Sessions**: Pending register/login flows (`auth_flows` table, 10-min TTL) and sessions (`sessions` table, random UUID tokens, 30-day TTL) are persisted in PostgreSQL — a backend restart no longer logs users out or kills in-progress auth flows. Expired rows are purged hourly by a background task.

### 2. AI & RAG Embeddings (768 Dimensions)
- **768 Vector Size**: `chat_messages.embedding` is `vector(768)`. It is specifically built for Gemini's `text-embedding-004`.
- **Database Index**: Uses `hnsw` with cosine distance (`chat_embeddings_cosine_idx USING hnsw (embedding vector_cosine_ops)`).
- **Offline / Fallback Mode**: If `GEMINI_API_KEY` is not set, the backend falls back to an offline pattern-matching router. Do not assume embedding generation will fail if the API key is missing.
- **Testability seam (#269, extended #283)**: `GEMINI_API_BASE` overrides the Gemini API base URL (defaults to `https://generativelanguage.googleapis.com` when unset/blank), mirroring `GITHUB_API_BASE`/`STRIPE_API_BASE`. All 5 hardcoded Gemini call sites resolve their URL through `rag.rs`'s `gemini_api_base()` (now `pub(crate)`): 4 in `rag.rs` (`get_gemini_embedding`, the main chat call, `generate_conversation_title`, `generate_suggested_question`) plus `reports.rs`'s `gemini_narrative` (#283, which also gained its own explicit 20s `reqwest` timeout — the last of the `#249` hang-class sites). Tests can point any of them at a local mock server; `rag.rs`'s test-only `GEMINI_ENV_LOCK` (also `pub(crate)`, #283) is shared across both files' test modules to serialize env-var-mutating tests. **Superseded by nels-oss#3 (see §27)**: every production Gemini call now goes through `llm.rs`, which owns the base-URL rule. `rag::gemini_api_base()` is now `#[cfg(test)]` and simply delegates to `llm::Provider::Gemini.api_base()`, kept only for the existing base-URL tests. `GEMINI_ENV_LOCK` now also guards every test that mutates `OPENAI_API_BASE`, `ANTHROPIC_API_BASE`, `LLM_MODEL_GEMINI` / `LLM_MODEL_OPENAI` / `LLM_MODEL_ANTHROPIC` or `ENABLED_BYO_PROVIDERS`, since they are all process-global. Must remain unset in production.

### 3. Database & Migrations
- **Auto-Migrations**: SQLx migrations inside `backend/migrations` are executed automatically on server start (`sqlx::migrate!`). No need to run `sqlx migrate run` manually.
- **pgvector Service**: The database container must be `pgvector/pgvector:pg16` to support the `vector` type.

### 4. Per-Budget Rollover (#47)
- **Toggle**: `budgets.rollover_enabled BOOLEAN NOT NULL DEFAULT FALSE`. Default FALSE keeps existing budgets behaving exactly as before.
- **Computed on read, no scheduler**: there is no period-boundary job. For the current period the carried amount is computed on demand as `carried = rollover_enabled ? max(0, base − prev_period_spent) : 0`, `effective = base + carried`, where `base` is the budget's computed total (sum of expense category amounts, per #46) and the previous-period window is derived from `time_frame` (`budget::previous_period_window`). Pure helpers `budget::carried_amount` and `budget::previous_period_window` are unit-tested.
- **Negative-remainder rule**: an overspend (`prev_spent > base`) does **NOT** carry as a negative — it clamps to 0.
- **Surfacing**: exposed via the budget REST response (`base_amount`, `carried_amount`, `effective_amount`, `rollover_enabled`) and the RAG "ACTIVE BUDGET DETAILS" context; the toggle is settable via REST (`BudgetPayload.rollover_enabled`) and via chat (CREATE_BUDGET / UPDATE_BUDGET).

### 5. Project-Based Budgets (#48)
- **Type discriminator**: `budgets.budget_type TEXT NOT NULL DEFAULT 'time_based'` — values `'time_based'` (existing, period-resetting behavior) or `'project'` (a one-off pool for a finite effort, e.g. a kitchen remodel). The DEFAULT keeps every existing budget time-based (backward compatible).
- **Excluded from rollover/reset**: a project budget never carries. The pure helper `budget::effective_carried(budget_type, rollover_enabled, base, prev_spent)` returns 0 for `'project'` (so `carried == 0`, `effective == base`) even when `rollover_enabled` is true; otherwise it delegates to `budget::carried_amount`. Used at every read site (REST list/get/update handlers and the RAG context) so REST and chat agree.
- **Full project span**: spend is tracked across the budget's lifetime, `created_at → closed_at` (or now if open), via `budget::project_span` + `budget::period_expense_spent`. The lifetime spend figure is surfaced in the RAG "ACTIVE BUDGET DETAILS" context (`Project spend to date`), not as a new numeric REST field.
- **Close lifecycle (read-only)**: `budgets.closed_at TIMESTAMPTZ` (NULL = open). Only project budgets can be closed (closing a time-based budget → 400). A **closed** budget is read-only: `budget::ensure_not_closed` (409 Conflict) guards new transactions, category create/delete, and budget field edits on BOTH the REST handlers and the chat mutation arms; reads (get/list/report/chat-context) remain allowed. Closing is idempotent and non-destructive (no reopen in scope; delete still works).
- **Surfacing**: REST — `BudgetPayload.budget_type` (settable on create/update), `BudgetListItem.budget_type`/`closed_at`, and `POST /api/budgets/:id/close` (owner-only). Chat — CREATE_BUDGET accepts `budget_type`, and a new non-destructive `CLOSE_BUDGET` action (resolves `target_budget_name` or the active budget). Frontend shows a `Project` / `Closed` badge on the active-budget display; create/close are driven through chat per the chat-first precedent of #46/#47.

### 6. Archive Budgets (#50)
- **Visibility flag**: `budgets.archived_at TIMESTAMPTZ` (NULL = active/unarchived). DEFAULT NULL keeps every existing budget unarchived — backward compatible, no backfill.
- **Archive vs Close (reconciliation, IMPORTANT)**: archiving is a **separate** concept from #48's close. **Close** = stop tracking a *project* budget; it makes the budget read-only (project-only, guarded by `ensure_not_closed`). **Archive** = hide ANY budget from the main list while preserving all data/history. They are independent columns/endpoints/badges — a budget can be both closed AND archived. Crucially, archive is **NOT** read-only: archived budgets remain fully readable AND editable (there is intentionally no `ensure_not_archived` guard); archiving only affects default list visibility, and unarchive restores the budget to the main list.
- **Excluded from main list, dedicated archived view**: `GET /api/budgets` excludes archived budgets by default (`archived_at IS NULL`); `GET /api/budgets?archived=true` returns only archived budgets. The filter is applied to both owned and shared budgets.
- **Rollover interaction (#47/#49, documented choice)**: archived budgets are excluded from active listings, so they do not participate in active rollover surfacing. This falls out of being excluded from the active list/context (rollover is computed-on-read per budget, no scheduler). Archiving does **NOT** delete `rollover_enabled` / per-category rollover flags / historical spend — all data is preserved; unarchiving restores prior behavior intact.
- **Idempotent + owner-only**: archive/unarchive require budget Owner permission; both are idempotent (archiving an already-archived budget, or unarchiving an active one, is a no-op returning the current state).
- **Surfacing**: REST — `BudgetListItem.archived_at`, `POST /api/budgets/:id/archive` and `POST /api/budgets/:id/unarchive` (owner-only), and the `?archived=` list filter. Chat — `ARCHIVE_BUDGET` / `UNARCHIVE_BUDGET` actions (resolve `target_budget_name` or the active budget; audit `AI_ARCHIVE_BUDGET` / `AI_UNARCHIVE_BUDGET`), with an offline-router fallback ("archive budget" / "unarchive budget"). The RAG "ACTIVE BUDGET DETAILS" Status line shows "(archived YYYY-MM-DD)". Frontend shows an `Archived` badge on the active-budget display (mirroring the #48 `Project` / `Closed` badges).

### 7. Recurring / Auto-Renewing Budgets (#51)
- **Opt-in toggle**: `budgets.auto_renew BOOLEAN NOT NULL DEFAULT FALSE`. The recurrence schedule REUSES the existing `time_frame` (monthly/quarterly/yearly) rather than adding a separate interval column. DEFAULT FALSE keeps every existing budget non-recurring — backward compatible, no backfill.
- **Persisted idempotency marker**: `budgets.next_renewal_at TIMESTAMPTZ` (NULL when auto-renew is off). It holds the next period boundary at which the budget will renew. A CHECK constraint (`budgets_auto_renew_only_time_based_check`: `NOT auto_renew OR budget_type = 'time_based'`) makes auto-renew on a non-time_based budget unrepresentable at the data layer.
- **In-place renewal (NOT row cloning)**: rollover and period logic are computed-on-read from `time_frame` (one budget row per logical budget; there are no per-period rows). Renewal therefore advances the SAME row's `next_renewal_at` marker rather than cloning a new budget. Categories and amounts are unchanged; crossing the boundary makes the just-completed period the "previous period", so rollover (#47/#49) carries the remainder into the new period automatically on the next read (overspend still clamps to 0).
- **Scheduled job on the hourly ticker**: `budget::renew_due_budgets` runs in the existing hourly background task in `main.rs` (alongside the purge jobs, same `Result<u64, sqlx::Error>` + `tracing` shape). It selects budgets where `auto_renew AND next_renewal_at <= now() AND budget_type='time_based' AND closed_at IS NULL AND archived_at IS NULL`, advances each marker to `budget::next_period_boundary(time_frame, now())`, and writes an `AUTO_RENEW_BUDGET` audit row per renewal.
- **Idempotent + safe hourly**: the new marker is always computed from `now()`, so it lands strictly in the future. Re-running the tick within the same period renews NOTHING (the marker no longer satisfies `<= now()`). The UPDATE is guarded by the same due predicate so concurrent ticks cannot double-renew. After downtime spanning several boundaries, a single advance jumps straight to the next FUTURE boundary (no catch-up loop). Pure helpers `budget::next_period_boundary` and `budget::renewal_marker` are unit-tested; idempotency and the project/closed/archived exclusions have DB-backed (`--ignored`) tests.
- **Excludes project / closed / archived (#48/#50)**: project budgets do not recur; closed budgets are read-only; archived budgets are inactive. All three are excluded by the job's WHERE filter (and the CHECK already forbids auto_renew on a project). Enabling auto-renew on a project is rejected (400 REST / chat error); converting a budget to `project` clears `auto_renew` + `next_renewal_at`.
- **Surfacing**: REST — `BudgetPayload.auto_renew` (settable on create/update; enabling computes `next_renewal_at`, disabling clears it, a `time_frame` change recomputes it), `BudgetListItem.auto_renew`/`next_renewal_at`. Chat — `CREATE_BUDGET` / `UPDATE_BUDGET` accept `auto_renew` (audit `AI_UPDATE_BUDGET`); the RAG "ACTIVE BUDGET DETAILS" shows an "Auto-renew: on (next renews YYYY-MM-DD)" / "off" line. Frontend shows an `Auto-renew` badge on the active-budget display (mirroring the #47 `Rollover` / #48 `Project` / #50 `Archived` badges), with the next-renewal date in its tooltip.

### 8. Budget Rollup / Aggregation — Linked Category Model (#52)
- **Supersedes the prior budget-level aggregation (IMPORTANT)**: an earlier implementation modelled rollup as parent/child *budget-level* summing (a children loop inside `aggregated_budget_amounts`). That was reopened as **not matching the issue's intent** and is **superseded** by the *linked-category* model documented here. Rolling a CHILD up into a PARENT now creates a single LIVE **mirror expense category** inside the parent; there is no children-summing loop. The implemented model remains *non-destructive and computed-on-read* (consistent with #46–#51): no categories or transactions are ever moved, copied, or deleted — the child keeps its own identity and is represented in the parent as ONE linked category.
- **Mechanism — the mirror category**: `categories.linked_budget_id UUID REFERENCES budgets(id) ON DELETE CASCADE` (NULL on every ordinary category, the default). A category with `linked_budget_id` set is a MIRROR: `category_type = 'expense'`, `category_limit = NULL` (it never contributes its own limit), and it points at the SOURCE (child) budget. `ON DELETE CASCADE` removes the mirror automatically if the source budget is deleted. A unique partial index `categories_one_mirror_per_source_idx (budget_id, linked_budget_id) WHERE linked_budget_id IS NOT NULL` makes "at most one mirror per (parent, source)" a data-layer invariant, so linking is idempotent.
- **Live amount, snapshot name (computed on read, missing amounts = 0 per #46)**: a mirror contributes the SOURCE budget's OWN expense total, resolved ONE level deep in SQL by `budget::computed_budget_total` (and its batched twin `budget::computed_budget_totals`): a non-linked category contributes `COALESCE(category_limit, 0)`; a mirror contributes a correlated `SUM(COALESCE(lc.category_limit,0))` over the source's `expense` categories. Because the parent's OWN total already folds in the mirror, `aggregated_budget_amounts` now returns the parent's own (base, effective, spent) with NO children loop — so the aggregated and per-budget views cannot diverge and cannot double-count. The mirror's AMOUNT is fully LIVE: any later change to the source (a new/edited expense category or limit) is reflected in the parent on the very next read, no job/refresh. The mirror's NAME is a link-time SNAPSHOT (`budget::rollup_category_name` resolves a collision-free name from the parent's existing names, suffixing on a case-insensitive clash, 409 if both the source name and its suffixed form are taken); it intentionally does NOT track later renames of the source — only the amount is live.
- **`rollup_parent_id` backlink (retained)**: `budgets.rollup_parent_id UUID REFERENCES budgets(id) ON DELETE SET NULL` is kept as the child→parent backlink (NULL = standalone, the default; `ON DELETE SET NULL` keeps a child standalone if its parent is deleted). It is the source of truth for the SINGLE-LEVEL guard and the child-side UI: the pure, unit-tested `budget::validate_rollup_link(parent_id, child_id, parent_is_child, child_is_parent, parent_type, child_type, parent_strategy, child_strategy)` rejects a self-link (400), a parent that is itself a child (409), a child that is already a parent (409), and — since #300 — a `budget_type` or `budget_strategy` mismatch between parent and child (409 each; see §13); combined with the DB `budgets_rollup_not_self_check` CHECK, cycles are structurally impossible. A child already linked to a DIFFERENT parent must be unlinked first (409); re-linking to the SAME parent is idempotent (the guarded `UPDATE … WHERE rollup_parent_id IS NULL OR = $parent` also closes a concurrent-reparent TOCTOU race). Link and unlink manage the backlink AND the mirror atomically in one transaction. `rollup_child_ids` (non-archived children, ordered by name) and the child's `Rolled up` badge are driven off this backlink.
- **Interactions**: ARCHIVED sources (#50) are EXCLUDED from a rollup parent on BOTH sides — one rule, *archived children don't count*: `budget::linked_budgets_spent` drops the archived source's spend (its sources are filtered `archived_at IS NULL`) AND `computed_budget_total` / `computed_budget_totals` drop its budgeted envelope (the mirror subquery joins `budgets … archived_at IS NULL`, so an archived source resolves to 0). So the combined budget and combined spend always cover the SAME set of sources, the per-category mirror line in the RAG context renders an archived source as `$0.00 (… source archived, not counted)`, and the rollup_line / system-prompt directive 2i ("archived children are excluded from the parent's combined totals") are accurate. CLOSED / project sources (#48) ARE included (a closed/project pool still contributes its budgeted total + spend, via the source's `project_span`). RECURRING sources (#51) need no special handling — the mirror simply reads the source's current own total. **Notification scope caveat**: `notifications::check_and_notify_limits` sums the RAW `category_limit` column and does NOT resolve mirror categories, so a rollup parent's budget-LIMIT alert does not reflect its children's mirror-inclusive total (each source fires its own alerts). This is a known, intentional scope boundary — `computed_budget_total` (the displayed total) and the notification limit check do NOT agree for a rollup parent; notifications.rs is unchanged by #52.
- **Owner-of-both scoping**: linking requires the caller to be Owner of BOTH the parent AND the child (you can only roll up budgets you own into a parent you own); unlink requires Owner of the parent; non-owner → 403. Chat lookups are scoped to `owner_id = user_id`, so a chat user can only roll up their own budgets.
- **Surfacing**: REST — `POST /api/budgets/:id/rollup {child_budget_id}` (owner-only link; creates the mirror + sets the backlink atomically; returns the parent's item), `DELETE /api/budgets/:id/rollup/:child_id` (owner-only unlink; deletes the mirror `WHERE budget_id=parent AND linked_budget_id=child` + clears the backlink; idempotent). `BudgetListItem` carries `rollup_parent_id`, `rollup_child_ids`, `aggregated_base_amount`, `aggregated_effective_amount`; `CategoryResponse` gains `linked_budget_id` (a linked category's `base_amount`/`effective_amount` are the resolved source total, `carried_amount` is 0). The own `base_amount`/`effective_amount` already include resolved mirrors. Chat — `ROLLUP_BUDGET` / `UNROLLUP_BUDGET` actions (owner-only; parent via `target_budget_name`/active, child via `child_budget_name`; audit `AI_ROLLUP_BUDGET` / `AI_UNROLLUP_BUDGET`; offline-router fallback "roll up"/"combine"/"unroll" that does NOT collide with #47's "roll over") manage the same mirror atomically; the RAG "ACTIVE BUDGET DETAILS" shows a "Rolled-up budgets (shown as linked categories): … (combined budget $X, combined spent $Y)" line — combined budget from `computed_budget_total`, combined spent from the parent's own current-period spend PLUS `linked_budgets_spent`. Frontend shows a `Rollup` badge (parent, combined total in its tooltip) or a `Rolled up` badge (child) on the active-budget display, mirroring the #47/#48/#50/#51 badges. (The chat-driven app has no per-category list view, so the linked-category indicator currently surfaces at the budget level via these badges rather than per category.)
- **Tests**: pure guards (`validate_rollup_link`, `rollup_category_name`) are unit-tested; the linked-category behaviour has DB-backed (`--ignored`) tests in `budget::tests` — mirror inclusion in the parent total, unlink removing the mirror and restoring the total, a live source edit flowing through, archived-source exclusion from `linked_budgets_spent` (but not from the resolved total), idempotent double-link (exactly one mirror), and the owner/cycle/relink handler guards.

### 9. Admin Authorization & Token Usage (#140)
- **`is_admin` gate**: `users.is_admin BOOLEAN NOT NULL DEFAULT FALSE` gates the admin-only routes (`/api/admin/*` → 403 for non-admins via `admin_middleware`). The FIRST admin is granted manually via SQL (there is no self-service path): `UPDATE users SET is_admin = TRUE WHERE email = '<email>';`. The standalone admin console (`/admin`) authenticates with the same TOTP flow and only succeeds for users with `is_admin = TRUE`.
- **Per-call token usage**: per-LLM-call token usage is captured into the `llm_usage` table from Gemini's `usageMetadata`. The write is **fail-safe** — a write failure is logged at `warn` and never breaks the chat path.
- **Subscription status surfaced (#340)**: `GET /api/admin/users` (`admin.rs::list_users`) additionally `LEFT JOIN`s `subscriptions` and returns `subscription_status` (raw Stripe status, `NULL` if the user never started checkout **or** a subscription webhook hasn't synced a status yet — `billing::ensure_customer` inserts the `subscriptions` row with `status` unset at the START of checkout, before any `customer.subscription.*` webhook lands, so both cases are indistinguishable here) and `is_pro` (derived via the existing `billing::user_is_pro`, computed in Rust post-fetch rather than duplicated in SQL — single source of truth for the trialing/active entitlement rule). `UsersTable.svelte` renders this as a rightmost, sortable "Subscription" badge column (green Pro/Trialing, amber for a present-but-non-entitled status, neutral "Free" for no status recorded yet) — read-only, no billing action is initiated from the admin console.

### 10. User-level (non-budget-scoped) Audit Trail (#192)
- **Nullable `audit_logs.budget_id`**: `audit_logs.budget_id` is nullable (migration `20260626010000`). A NULL value means the action is **user-scoped** — not tied to any budget. The `budget_id` FK stays `ON DELETE CASCADE` (a NULL FK never cascades); the separate `user_id` FK is `ON DELETE SET NULL`, but account deletion still removes a user's rows explicitly (`account.rs delete_user_data: DELETE FROM audit_logs WHERE user_id = $1`).
- **Two helpers, one writer**: `budget::log_audit(pool, budget_id, user_id, action, details)` (budget-scoped) and `budget::log_user_audit(pool, user_id, action, details)` (user-scoped, NULL budget_id) both delegate to a private `log_audit_row`. Both are **fail-safe** (a write failure is logged at `warn` and never propagated — #168).
- **Issue filing is always user-scoped**: chat `REPORT_ISSUE` writes `AI_REPORT_ISSUE` **always** (it files to the project repo, not a budget, so it is attributed to the user even with no active budget — `chat_report_issue` takes no budget id). The REST issue-filing path (`POST /github/issues`, driven by the `/issues-create` slash command) writes a `REPORT_ISSUE` row on success (the non-`AI_` prefix marks the deliberate user-command path vs the assistant's `AI_REPORT_ISSUE`). Non-budget backfills: `AI_CREATE_REMINDER` (user-scoped when no active budget) and `AI_SET_USER_NAME` (on a successful rename).
- **Export parity (#198)**: the account data export (`account.rs`) surfaces user-scoped (NULL `budget_id`) audit rows at the top level as `AccountExport.user_audit_logs` (`SELECT * FROM audit_logs WHERE user_id = $1 AND budget_id IS NULL`), alongside the per-budget `audit_logs`. To support this, `db::AuditLog.budget_id` and `budget::AuditLogResponse.budget_id` are `Option<Uuid>` (matching the nullable column; serde renders `Some(uuid)` identically to a bare `Uuid`, so budget-scoped responses are unchanged). This closes the prior gap where user-scoped (NULL `budget_id`) rows were erased (`DELETE FROM audit_logs WHERE user_id = $1`) but never exported. (A narrower asymmetry remains by design: budget-scoped rows a user authored in a budget owned by *someone else* are erased by `user_id` but appear in the owner's export, not the actor's.)
- **Testability seam**: `GITHUB_API_BASE` overrides the GitHub API base URL (defaults to the real API when unset/blank) so tests can drive `create_issue_core` against a local mock server. Must remain unset in production.

### 11. Stripe Subscription Billing (#25)
- **Webhooks are the ONLY source of entitlement truth**: the Checkout success redirect grants nothing. Subscription state is synced exclusively by signature-verified Stripe webhooks into the `subscriptions` table; the frontend success page polls `GET /api/billing/subscription` (the entitlement may lag the redirect since it arrives via the async webhook). NEVER grant Pro from a client redirect param.
- **`subscriptions` table — one row per user**: `user_id UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE`, plus `stripe_customer_id` (NOT NULL), nullable `stripe_subscription_id` (UNIQUE) / `status` / `price_id` / `current_period_end`, `cancel_at_period_end`, and `last_stripe_event_at` (the out-of-order/idempotency guard). The Stripe Customer is created lazily at first checkout and persisted immediately (`ensure_customer`, `ON CONFLICT (user_id) DO NOTHING` + re-read prevents two customers per user). Account deletion removes the row via FK cascade (and an explicit `DELETE` in `account.rs::delete_user_data` for symmetry).
- **Routes** (`billing.rs`): `POST /api/billing/checkout` (auth; `{cadence:"monthly"|"annual"}` → hosted Checkout Session URL with `trial_period_days` + `payment_method_collection=if_required` so NO card is required for the trial; returns **409** if the user is already Pro), `POST /api/billing/portal` (auth → Customer Portal URL), `GET /api/billing/subscription` (auth → `{status, price_id, current_period_end, cancel_at_period_end, is_pro}`), and `POST /api/billing/webhook` — **PUBLIC**, mounted OUTSIDE the auth nest (it authenticates via the Stripe signature, not a session) via a third `.nest("/api", billing_public_routes)` in `main.rs`. The webhook handler takes raw `Bytes` (NOT `Json`) because HMAC verification needs the exact bytes; it verifies the signature BEFORE parsing/persisting and fails closed with 400.
- **Entitlement helper**: `billing::user_is_pro(status)` is true ONLY for `trialing`/`active` (every other Stripe status → false). Gate Pro-only features on it. (No existing feature is gated Pro-only yet — #25 delivers the primitive, not a specific gate.)
- **Env-driven config (read at handler time)**: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_ANNUAL`, `STRIPE_TRIAL_DAYS` (default **7**, matching `marketing/src/lib/site.js` — the issue's "14" predates PR #218), `APP_URL`, and the test seam `STRIPE_API_BASE` (mirrors `GITHUB_API_BASE`; unset in prod → `https://api.stripe.com`). Price *amounts* live in Stripe (referenced by price-ID env vars), never hardcoded. The **checkout/portal/webhook** endpoints return **503** when unconfigured, so a deploy without secrets fails loud, not silent (`GET /api/billing/subscription` still returns a free/empty **200** — it reads no Stripe env). Stripe is called via hand-rolled form-encoded `reqwest` (no `async-stripe` crate); signature verification uses `hmac`+`sha2`. Setup checklist: `docs/billing/stripe-setup.md`.

### 12. Fund Categories (#228)
- **`is_fund` flag, independent of rollover**: `categories.is_fund BOOLEAN NOT NULL DEFAULT FALSE` marks an expense category as a "fund" (envelope / sinking-fund). It is orthogonal to `rollover_enabled` (#49) and to `category_type` (a data-layer CHECK, `categories_is_fund_expense_only_check`, restricts it to `category_type = 'expense'`). DEFAULT FALSE keeps every existing category unaffected.
- **Cumulative and bidirectional (NOT #47/#49's single-period clamp)**: `categories.fund_balance DOUBLE PRECISION NOT NULL DEFAULT 0` is a running total across ALL periods since the fund was enabled — unlike #47/#49's `carried_amount`, which looks at only the ONE previous period and clamps at zero. Each period, `fund_balance += (category_limit - period_spent)`; an overspend SUBTRACTS from the balance and can drive it negative. The effective limit for the current period is `budget::fund_effective_limit(is_fund, category_limit, fund_balance)` = `category_limit + fund_balance`, with **no floor**.
- **Materialized, NOT computed-on-read (a deliberate departure)**: every other rollover/carry feature in this codebase (#47/#49/#51 — see §4/§7 above) is computed on demand from the CURRENT limit and a period-windowed spend query, with no scheduler and no persisted running figure. Funds break that pattern on purpose: the effective amount depends on the base limit AS IT WAS in each PAST period, and limits change over time, so a computed-on-read sum would retroactively rewrite history every time a limit is edited. `fund_balance` is instead materialized and advanced incrementally, once per completed period, by a background job — the correctness of that advancement (idempotent, exactly-once per period, safe to run hourly) is the central risk this feature manages.
- **Idempotency marker**: `categories.fund_advanced_through TIMESTAMPTZ` (NULL = never a fund) is the boundary up to which `fund_balance` already reflects completed periods — mirroring #51's `next_renewal_at` pattern, but inverted: it marks a *past* boundary already applied, not a *future* due time. Enabling `is_fund` (via `SET_CATEGORY_FUND` or `CREATE_CATEGORY`) resets `fund_balance = 0` and sets the marker to the CURRENT period's start — periods before the fund existed never count. Disabling preserves both `fund_balance` and the marker (non-destructive, matching #50 archive's "toggle preserves data" precedent); re-enabling resumes from the preserved balance with the marker reset to the (new) current period start.
- **Background job, independent of `auto_renew`**: `budget::advance_fund_categories` runs on the SAME hourly ticker as `renew_due_budgets` (`main.rs`) but is a SEPARATE job selecting `categories.is_fund = TRUE` directly — it must fire for ANY fund category regardless of whether its budget has `auto_renew` on, since `renew_due_budgets` only ever selects `auto_renew = TRUE` budgets (§7 above). Unlike `renew_due_budgets`'s single jump-to-the-next-FUTURE-boundary catch-up, this job walks ONE PERIOD INCREMENT AT A TIME through every completed period the marker hasn't crossed yet (bounded to 24 iterations per category per tick) — because a fund's balance must accumulate per period, not skip straight to the present. Each increment's UPDATE is guarded by `fund_advanced_through = $old_marker`, so a concurrent/repeated tick cannot double-apply (idempotent within a period, same contract as `renew_due_budgets`).
- **Known limitation — limit-change fidelity during catch-up**: there is no historical per-period limit table in this schema, so a multi-period catch-up (e.g. after downtime) applies EACH crossed period's increment using the category's CURRENT `category_limit`, not necessarily the limit that was nominally in effect during that specific past period. A limit edited between a missed boundary and the next hourly tick is applied retroactively to that catch-up increment. Since the job runs hourly and periods are typically monthly, this window is small in practice; a true historical-limit ledger is a natural follow-up, out of scope for #228.
- **Excludes project / closed / archived budgets** (consistent with #47/#48/#49/#51): the job's WHERE filter requires `budget_type = 'time_based' AND closed_at IS NULL AND archived_at IS NULL`. A fund category on an excluded budget simply stops advancing (balance frozen) until the exclusion lifts.
- **Precedence over #49 rollover for the SAME category**: `is_fund` and `rollover_enabled` are independent toggles, but when both are on for one category, the read path (`budget::category_response_with_carry`, the RAG per-category context) uses the fund balance INSTEAD of the #49 one-period carry — never both — to avoid double-counting the same accumulated credit under two labels. The underlying `category_carried` pure helper (#49) is unchanged; only its *use* is superseded for fund categories.
- **Surfacing**: REST — `CategoryResponse.is_fund`/`fund_balance` (read-only *as of #228* — chat was the only write path in that issue's scope, per this app's chat-first convention; **#426 added the REST write path**, `CategoryUpdatePayload.is_fund` on `PUT /budgets/:id/categories/:category_id`, sharing the same `enable_category_fund`/`disable_category_fund` helpers as the chat call sites — see §19). The category table (`build_categories_table_html`) shows a fund badge, the carried balance, and computes Remaining against the effective limit (sums the EFFECTIVE limit, not the bare `category_limit`, in the totals row); negative effective limits/remaining render via the existing `money()` helper's signed formatting, with a deficit CSS class. The RAG per-category context shows `Fund: on | Balance: $X | Effective limit: $Y` (superseding the Rollover/Carried annotation for that category). Chat — `SET_CATEGORY_FUND` toggles a named category or ALL expense categories (audit `AI_SET_CATEGORY_FUND`); `CREATE_CATEGORY` accepts `is_fund` to create a fund in one step; both are documented in prompt rule 2m, distinguishing funds from #49 rollover for the model.

### 13. Per-Budget Budgeting Strategy (#300)
- **Replaces the two global per-user toggles**: `budgets.budget_strategy TEXT NOT NULL DEFAULT 'limit_spent_remaining'` (CHECK constrained to `'zero_based'`/`'limit_spent_remaining'`) supersedes the old `users.show_zero_based_summary`/`show_limit_spent_remaining_summary` columns, which a single global on/off pair could not express per-budget. Both legacy columns, the `PATCH /user/preferences` endpoint, and the Settings "Budget summary" panel are removed outright — not just unused.
- **Exactly two values ship now, by design**: `'zero_based'` (tracks how much of the allocated total is still available to spend) and `'limit_spent_remaining'` (tracks spending against a limit, shown as Budgeted/Spent/Remaining). The issue's "extensible to 50/30/20, envelope, pay-yourself-first later" is a property of the plain-TEXT-plus-CHECK column design (an additive migration adds a third value later), not a requirement to pre-build computation/UI for methodologies with no defined behavior yet — mirrors how `budget_type` (#48) and `amount_mode` (#116) each shipped with their minimal value set first.
- **Migration backfill**: existing budgets migrate to `'zero_based'` when their owner had `show_zero_based_summary = TRUE` (preserving the richer of the two legacy views); every other budget keeps the column default `'limit_spent_remaining'`. This is a one-way, non-retroactive migration — it does not revisit budgets after the fact, and pre-existing `rollup_parent_id` links are not re-validated against the new strategy-match rule below (see next bullet).
- **Rollup compatibility gains a strategy axis (and a latent type gap is closed)**: `budget::validate_rollup_link` (§8 above) now also takes `parent_type`/`child_type`/`parent_strategy`/`child_strategy` and rejects (409) a `budget_type` mismatch OR a `budget_strategy` mismatch, checked AFTER the pre-existing self-link (400) and chain-violation (409) guards so those keep priority. Before #300, `budget_type` was never actually checked in this path at all — rolling up a `project` budget into a `time_based` parent (or vice versa) was silently allowed; #300 closes that gap in the same pass as adding the new `budget_strategy` check. Both call sites (`link_rollup` REST handler, chat `chat_rollup_budget`) already fetch full parent/child `Budget` rows, so no new query was needed.
- **Chat CREATE_BUDGET never silently defaults — enforced server-side, not just via prompt**: the system prompt (rule 2n) instructs the model to ask which strategy the user wants and describe both options before creating a budget with no explicit strategy, but since an LLM can still not comply, the `CREATE_BUDGET` handler itself (the single arm both the online-LLM and offline-router paths share) blocks the INSERT and overrides `response_text` with a plain clarifying question whenever `budget_strategy` is absent — this is NOT routed through the `mutation_error`/`⚠️` warning channel, since a missing strategy isn't a failure, it's a question (an actually-invalid, non-empty value IS a real error and still uses `mutation_error`, matching the `budget_type`/`amount_mode` precedent). `offline_budget_strategy` mirrors `offline_amount_mode`'s explicit-phrase-in-the-same-message matching for the offline router (no conversational memory to hold a pending question across turns). Chat `UPDATE_BUDGET` also accepts `budget_strategy` (an explicit user request always supplies a value, so no "ask" behavior applies there).
- **Surfacing**: REST — `BudgetPayload.budget_strategy` (settable on create/update, absent-on-create defaults to `'limit_spent_remaining'`, absent-on-update preserves via `COALESCE`), `BudgetListItem.budget_strategy`. Frontend — the Settings "Budget summary" panel is gone; the chat status strip (`App.svelte`) shows exactly one row (zero-based or traditional) gated on the ACTIVE budget's own `budget_strategy` instead of the old global toggles; `BudgetDetails.svelte` gained an editable "Strategy" field mirroring the existing "Type" field's click-to-edit affordance.

### 14. Financial Connections Bank Linking (#303)
- **Pro-gated, builds on #25/#195**: a subscriber with `billing::user_is_pro` can link bank account(s)
  via Stripe Financial Connections; imported transactions land in the EXISTING `transactions` table,
  attributed via a new nullable `external_account_id` FK to `linked_accounts` — no separate
  expense-tracking system. `linked_accounts` (one row per linked Stripe FC Account, scoped to a
  budget) is never deleted by a disconnect — only its `status` flips to `'disconnected'`, preserving
  import history per the AC.
- **No hosted redirect (unlike Checkout)**: Financial Connections requires client-side Stripe.js
  (`@stripe/stripe-js`, `stripe.collectFinancialConnectionsAccounts({clientSecret})`) driven by a
  `client_secret` from a server-created session — there is no URL to simply redirect to. The chat
  action `LINK_BANK_ACCOUNT` hands this `client_secret` back through a new `ChatResponse` field
  (`financial_connections_client_secret`) for the frontend to drive the same modal a REST-triggered
  link would.
- **Session completion is verified server-side**: after the client-side modal resolves, the frontend
  sends only a `session_id`; `financial_connections::complete_link_session` re-fetches the session
  with our own secret key and confirms its `account_holder.customer` matches the caller's own Stripe
  customer (`billing::ensure_customer`, widened to `pub(crate)` and reused unchanged — one Stripe
  Customer per user, shared between billing and linking) before persisting anything.
- **Idempotent sync via `provider_transaction_id`** (renamed from `stripe_transaction_id` by #320's
  provider generalization — see §15): `transactions.provider_transaction_id`, uniqueness-scoped per
  `(external_account_id, provider_transaction_id)` (non-imported rows stay NULL) is the dedup key
  `sync_account_transactions` uses (`ON CONFLICT DO NOTHING`) so webhook redelivery or overlapping
  manual/auto refreshes never duplicate a row or clobber a user's edit to an already-imported one.
- **Categorization is a narrow v1 heuristic, not ML**: `financial_connections::guess_category_id`
  case-insensitive-substring-matches a budget's existing category names against the imported
  description; no match leaves `category_id` NULL, surfaced as "Uncategorized" for the user to
  assign. Stripe's FC transaction object carries no spending-category field of its own (unlike
  Plaid). A smarter categorizer is an explicit non-goal for v1.
- **Manual refresh and webhook auto-refresh are the SAME mechanism**: `refresh_linked_account` calls
  Stripe's `POST .../accounts/:id/refresh` and returns immediately (no new data yet); the actual
  import happens moments later when Stripe's `financial_connections.account.refreshed_transactions`
  webhook fires and calls the same `sync_account_transactions` used everywhere else. Manual refresh
  just asks Stripe to check now instead of waiting for Stripe's own schedule.
- **Subscription lapse pauses (never deletes)**: the `refreshed_transactions` webhook handler
  requires BOTH `linked_accounts.status == 'active'` AND the owning user's `billing::user_is_pro`
  before syncing; either check failing is a silent no-op (200, no Stripe retry) that leaves all data
  untouched. The `status == 'active'` check is belt-and-suspenders alongside disconnect being a real
  Stripe-side call (see next bullet) — webhook delivery/ordering isn't guaranteed.
- **Disconnect calls Stripe FIRST, then flips the local flag**: `disconnect_linked_account` calls
  `POST .../accounts/:id/disconnect` (idempotent on Stripe's side) BEFORE writing `status =
  'disconnected'` locally, so a failed Stripe call never leaves us believing an account is
  disconnected when Stripe could still fire refresh webhooks for it. The webhook ALSO handles
  `financial_connections.account.disconnected` (bank-initiated disconnect, independent of our own
  button) the same way. Disconnect is NOT Pro-gated — a lapsed user must still be able to manage
  their own linked data (view + disconnect are ungated; starting a new link and manual refresh are
  the two Pro-gated actions).
- **Own webhook endpoint/secret**: `POST /api/financial-connections/webhook` is a SEPARATE public
  route from `/api/billing/webhook`, with its own `STRIPE_FC_WEBHOOK_SECRET` env var, reusing
  `billing::verify_stripe_signature`/`StripeEvent` (already `pub`) unchanged.
- **Surfacing**: REST — `POST /api/budgets/:id/linked-accounts/session`, `POST
  .../linked-accounts/complete`, `GET .../linked-accounts`, `POST
  .../linked-accounts/:account_id/refresh`, `DELETE .../linked-accounts/:account_id` (Edit-or-Owner
  for all but the GET, which is any budget-view access). Chat — `LINK_BANK_ACCOUNT` /
  `LIST_LINKED_ACCOUNTS` / `UNLINK_BANK_ACCOUNT` / `REFRESH_BANK_ACCOUNT` (system prompt rule 2o;
  `UNLINK_BANK_ACCOUNT` resolves a fuzzy `account_match` locator against institution/display
  name/last4, mirroring `transaction_match`'s ambiguity handling for `EDIT_TRANSACTION`). Frontend —
  a Linked Accounts panel in Settings plus the chat-triggered Stripe.js modal share one code path
  (`frontend/src/lib/linkedAccounts.js`).

### 15. GoCardless Bank Account Data Bank Linking (#320)
- **Second provider, same `linked_accounts`/`transactions` tables, now generalized**: `linked_accounts.provider`
  (`'stripe'` | `'gocardless'`), `provider_account_id`/`provider_ref` (renamed from `stripe_account_id`/
  `stripe_customer_id`), plus GoCardless-only nullable `consent_expires_at`/`country`/`institution_id`/`iban`.
  `transactions.provider_transaction_id` (renamed from `stripe_transaction_id`) is now uniqueness-scoped per
  `(external_account_id, provider_transaction_id)`, not globally — GoCardless transaction ids are bank-assigned,
  not guaranteed globally unique the way Stripe's are. New `transactions.currency` (ISO 4217) column; no FX
  conversion anywhere in this codebase.
- **`bank_provider::Provider` + `bank_linking.rs`**: originally a closed two-member enum (not a `dyn` trait
  object), now a five-member enum (`Stripe`/`GoCardless`/`Belvo`/`Basiq`/`Akahu` — Belvo added by #322 (see
  §16), Basiq and Akahu added by #323 (see §17)) maps country -> provider (`US` -> Stripe; `GB`/`FR`/`DE`/`IT`/
  `ES`/`DK`/`FI`/`NO` -> GoCardless; `MX`/`BR` -> Belvo; `AU` -> Basiq; `NZ` -> Akahu). `bank_linking.rs`'s
  `list_linked_accounts`/`refresh_linked_account`/`disconnect_linked_account` each match on
  `linked_accounts.provider` once and delegate — `rag.rs`'s `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/
  `REFRESH_BANK_ACCOUNT` and the REST list/refresh/disconnect handlers call these instead of reaching into
  `financial_connections::*`/`gocardless::*`/`belvo::*`/`basiq::*`/`akahu::*` directly. `LINK_BANK_ACCOUNT`
  (starting a NEW link) is the one call site that still branches on provider, since each provider's
  start-link response shape is genuinely different (Stripe: client_secret-driven modal; GoCardless/Basiq/
  Akahu: full-page redirect, but to different consent UIs; Belvo: client-side embeddable widget).
- **No GoCardless webhook — polled instead**: GoCardless Bank Account Data has no per-transaction webhook
  (unlike Stripe FC). A scheduled poll job (`gocardless::poll_active_accounts`, `main.rs` ticker, default every
  `GOCARDLESS_POLL_INTERVAL_HOURS=8`) syncs every active GoCardless account whose owner is still Pro — one
  GoCardless call per account per cycle (3/day at the default), staying under GoCardless's ~4-calls/day/account
  guidance with headroom for the initial link-time sync and manual refreshes.
- **Redirect-based consent, our own pending-session table**: `bank_link_sessions` persists `budget_id`/
  `user_id`/`requisition_id`/`institution_name` keyed by a UUID we generate and embed OURSELVES in the redirect
  URL (`{APP_URL}/?gc_ref=<id>`) handed to GoCardless — GoCardless redirects the browser back to exactly that
  URL, appending nothing of its own. `App.svelte` picks up `gc_ref` on mount (and `ChatResponse.bank_link_redirect_url`
  for the chat-triggered flow) and calls `POST /api/budgets/:id/gocardless/complete`, which re-fetches the
  requisition server-side (never trusts the redirect alone) before persisting anything.
- **PSD2 ~90-day consent expiry is explicit, not silent**: `access_valid_for_days`/`max_historical_days` default
  to 90 (env-configurable), clamped to each institution's own `transaction_total_days` cap. Expiry is detected
  from the transactions call's own 409/403-class error response (no separate status call, to keep the poll job
  to one GoCardless call per account, and deliberately excluding 401 — which more likely indicates our own
  bearer-token cache is stale, not that the user's bank consent lapsed) and flips the local row to
  `status = 'consent_expired'` — surfaced distinctly by `LIST_LINKED_ACCOUNTS` (REST + chat) and short-circuited
  (no GoCardless call) by manual refresh with a clear "reconnect it" message. Re-consent reuses the same link
  flow; `complete_link_session` reconciles onto an existing `consent_expired` row for the same budget+institution
  by IBAN match when available, preserving transaction history — no IBAN match falls back to a new row
  (documented, bounded v1 limitation, no data loss either way).
- **Institution selection**: chat uses a fuzzy case-insensitive substring match (`gocardless::find_institution_id`,
  mirroring `UNLINK_BANK_ACCOUNT`'s `account_match` pattern) over `GET /institutions/?country=`; the REST/frontend
  flow additionally offers a real `<select>` of the country's institutions. The offline (no-`GEMINI_API_KEY`)
  chat router's `offline_country_hint` recognizes a small set of explicit country-name phrases in the SAME
  message (no conversational memory), using whole-word matching for the short "uk"/"us" codes specifically to
  avoid false-positiving on longer words that merely contain those letters (e.g. "previous bank").
- **Surfacing**: REST — `POST /api/budgets/:id/gocardless/session`, `POST .../gocardless/complete`,
  `GET /api/gocardless/institutions?country=`, plus the now-shared `GET/POST/DELETE .../linked-accounts...`
  routes (provider-agnostic since `bank_linking.rs`). Chat — `LINK_BANK_ACCOUNT` gained `country`/
  `institution_query` params (system prompt rule 2o); `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/
  `REFRESH_BANK_ACCOUNT` unchanged in shape, now provider-agnostic under the hood.
  `ChatResponse.bank_link_redirect_url` (alongside the existing `financial_connections_client_secret`) carries
  the GoCardless redirect URL to the frontend, which does a full-page `window.location.href` navigation on
  seeing it. Frontend — a country + bank `<select>` in the existing Linked Accounts panel (guarded against
  out-of-order institution-list responses if the user switches country quickly), a "Reconnect needed" badge for
  `consent_expired` accounts, and success/error feedback on returning from the GoCardless redirect.

### 16. Belvo Bank Account Data Bank Linking — Mexico, Brazil (#322)
- **Third provider, same `linked_accounts`/`transactions` tables**: `linked_accounts.provider` gains
  `'belvo'` alongside `'stripe'`/`'gocardless'`; `bank_provider::Provider` is now a closed three-member
  enum (`US` -> Stripe; the 8 GoCardless countries -> GoCardless; `MX`/`BR` -> Belvo). A third provider
  costs one match arm per dispatch site in `bank_linking.rs`, not a rewrite — reaffirming §15's "a
  hypothetical third provider would warrant revisiting this" note; it didn't. See
  `docs/superpowers/specs/2026-07-06-belvo-bank-account-data-design.md` for full rationale.
- **HTTP Basic auth per request, no bearer-token cache**: unlike GoCardless's cached bearer token
  (§15), `belvo.rs` sends `BELVO_SECRET_ID`/`BELVO_SECRET_PASSWORD` as HTTP Basic auth on every API
  call — Belvo's auth model has no token-mint-and-refresh step to cache in the first place (spec
  Assumption 1). The one exception is the widget-token mint itself (`POST /api/token/`), which takes
  the secret pair in the JSON body rather than as a Basic-auth header, per Belvo's own docs.
- **Client-side widget flow, our own `belvo_link_sessions` table**: unlike GoCardless's full-page
  redirect (§15), Belvo's Connect Widget runs entirely client-side and renders its own institution
  picker and bank-authentication UI — there is no requisition/agreement bookkeeping to persist and no
  redirect URL to hand back. `belvo_link_sessions` (`id`/`budget_id`/`user_id`/`country`/`status`) is
  therefore much thinner than `bank_link_sessions`: it exists purely to anti-replay-verify who
  completed a widget session, keyed by a UUID we generate and embed as the widget token's
  `external_id`. `belvo::start_link_session` mints a short-lived `access_token` scoped to a country and
  returns it (plus the session id) to the caller; the frontend uses it to initialize Belvo's embeddable
  widget script (`cdn.belvo.io`) inline — no full-page navigation, unlike GoCardless. Once the widget
  resolves client-side to a `belvo_link_id`, `belvo::complete_link_session` re-fetches the Link and its
  accounts server-side (never trusting the client-supplied id alone), checks the Link's own
  `external_id` against the pending session (403 on mismatch), and persists/reconciles each account.
- **Webhook-driven auto-refresh — the opposite end of the spectrum from GoCardless's poll job**: Belvo
  has real per-Link webhooks, so unlike GoCardless (§15, polled every `GOCARDLESS_POLL_INTERVAL_HOURS`
  because it has none), Belvo needs no poll job at all. `belvo::webhook` is a PUBLIC route mounted
  outside the auth nest, authenticated by a Basic-auth header configured when the webhook URL was
  registered in Belvo's dashboard (`BELVO_WEBHOOK_USER`/`BELVO_WEBHOOK_PASSWORD`, verified by
  `verify_webhook_auth` — NOT HMAC-signed like Stripe's). On any payload naming a `link_id`, it
  resyncs every active Belvo `linked_accounts` row for that Link via the same
  `sync_account_transactions` used by initial-link and manual refresh — one function, three callers,
  same shape as both existing providers — skipping accounts whose owner has since lapsed from Pro
  (silent no-op, mirroring §14's Stripe FC webhook belt-and-suspenders check). Between the two
  providers, this codebase now has a worked example of both a webhook-driven and a poll-driven
  bank-linking integration.
- **Currency fallback is by-country, not a blanket default — and that's correct, not an
  inconsistency**: GoCardless (§15) defaults a transaction missing its own `currency` field to a
  blanket `"EUR"`, which is safe there because every GoCardless launch country uses EUR (or a
  currency the transaction always specifies otherwise). That default would be actively WRONG for
  Belvo: Mexico and Brazil are two different currency zones, so `belvo::currency_for_country` derives
  the fallback from the LINKED ACCOUNT's own country (`MX` -> `MXN`, `BR` -> `BRL`) instead (spec
  Assumption 9). The `_ => "USD"` arm is defensive and practically unreachable, since
  `Provider::for_country` only ever resolves `Belvo` for `MX`/`BR`.
- **Reconciliation is last4 + institution based, not IBAN based**: GoCardless's re-consent flow
  (§15) reconciles onto an existing `consent_expired` row by IBAN match, falling back to a new row
  with no match. Mexican and Brazilian accounts don't expose an IBAN, so
  `belvo::complete_link_session` instead matches on `(budget_id, institution_id, last4)` against an
  existing `consent_expired` row for the same budget — preserving the local row id (and therefore
  transaction history) instead of inserting a disconnected-looking duplicate (spec Assumption 11),
  with the same no-match-falls-back-to-a-new-row behavior as GoCardless otherwise.
- **PSD2-style expiry detection, reusing the same status value**: like GoCardless, an invalid/expired
  Belvo Link is detected from the transactions call's own error response (`is_link_invalid_error`, a
  loose case-insensitive substring check over a 400/404/409-class body — Belvo's exact error shape is
  a documented-but-unverified assumption, spec §8 Risks) and flips the local row to the SAME
  `status = 'consent_expired'` value GoCardless's PSD2 expiry already established (spec Assumption 12),
  rather than inventing a Belvo-specific status. Manual refresh short-circuits on an already-expired
  account with a "reconnect it" message, without calling Belvo at all — identical to GoCardless.
- **Disconnect calls Belvo FIRST, then flips the local flag**: `belvo::disconnect_linked_account`
  deletes the Belvo Link (`DELETE /api/links/:id/`) before writing `status = 'disconnected'` locally —
  same ordering as both existing providers. Not Pro-gated, matching §14's rationale (a lapsed user
  must still be able to manage their own linked data).
- **Surfacing**: REST — `POST /api/budgets/:id/belvo/session`, `POST .../belvo/complete` (no
  institutions-list endpoint — the widget renders its own picker), plus the same shared
  `GET/POST/DELETE .../linked-accounts...` routes as the other two providers. Public — `POST
  /api/belvo/webhook`. Chat — `LINK_BANK_ACCOUNT` gained a third branch: for `MX`/`BR` it mints a
  widget session and returns it via new `ChatResponse` fields (`belvo_widget_access_token`,
  `belvo_link_session_id`) instead of asking for a bank name the way the GoCardless branch does — the
  system prompt tells the model not to ask for an institution for Mexico/Brazil, since the user picks
  it inside the widget. `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/`REFRESH_BANK_ACCOUNT` are
  unchanged in shape, already provider-agnostic under `bank_linking.rs`. Frontend — a Belvo widget
  loader (`cdn.belvo.io`'s script injected lazily, cached, and retried on load failure) added to the
  existing country/bank picker in both Settings and the chat surface, alongside the GoCardless
  `<select>` and Stripe modal — `createWidget(token, config).build()` is assumed (not yet verified

### 18. Plaid Bank Linking — Canada (#321)
- **Sixth `bank_provider::Provider` variant, added without touching the enum-vs-`dyn`-trait
  choice #320 made**: `Provider::Plaid`; `for_country("CA")`. `bank_linking.rs`'s
  `refresh_linked_account`/`disconnect_linked_account` each gained one `"plaid" => ...` arm;
  `rag.rs`'s `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/`REFRESH_BANK_ACCOUNT` needed ZERO
  changes (already provider-agnostic since #320). `LINK_BANK_ACCOUNT` (starting a new link) is
  the one call site that branches on provider, same documented exception #320/#322/#323 carry.
- **New anti-replay table, `plaid_link_sessions`** — the same idea as Belvo's own
  `belvo_link_sessions`/`ChatResponse.belvo_link_session_id` (#322): a raw Plaid `public_token`
  carries no recoverable binding to the user/budget that started the link, unlike Stripe's
  `client_secret` (verified against the caller's own Stripe customer) or GoCardless's
  `bank_link_sessions` row. `POST .../plaid/link-token` creates a `plaid_link_sessions` row
  (budget_id, user_id, status) alongside the Plaid `link_token`; `POST .../plaid/complete`
  requires the matching `session_id` (404 if unknown) and 403s on a budget_id/user_id mismatch,
  409s if already completed — checked via an atomic completion-claim `UPDATE ... WHERE status =
  'pending'` (not a plain read-then-write), closing a TOCTOU race between two concurrent
  completion attempts for the same `session_id`.
- **Dedicated `plaid_item_id`/`plaid_cursor` columns, unlike Belvo/Basiq/Akahu's pure column
  reuse**: those three (§16/§17) reuse the fully-generic `provider_account_id`/`provider_ref`
  columns with no new schema. Plaid genuinely needs two dedicated fields instead:
  `plaid_item_id` is the correlation key Plaid's webhook payloads carry (a webhook fires
  per-Item, not per-account, and one Item can back multiple `linked_accounts` rows sharing one
  `provider_ref` access_token) — no existing generic column represents "this account's parent
  Item." `plaid_cursor` is this row's own `/transactions/sync` cursor (per-row, not per-Item, so
  `sync_account_transactions` stays shaped like every other provider's per-linked-account sync
  function) — a documented, idempotent-safe v1 tradeoff that makes redundant Plaid calls when
  one Item backs multiple rows (negligible at typical 1-3-accounts-per-bank linking volumes),
  guarded by a bounded pagination loop (`MAX_SYNC_PAGES` cap + a no-progress abort if `has_more`
  is true with no advancing `next_cursor`) so a malformed/adversarial response can't loop forever.
- **Manual refresh is synchronous, unlike Stripe/GoCardless/Belvo/Basiq/Akahu**: Plaid has no
  "please check now" endpoint separate from `/transactions/sync` itself, so
  `plaid::refresh_linked_account` awaits the sync directly and returns once it completes — a
  genuine behavioral asymmetry from the other providers' "kick off, webhook/poll delivers later"
  shape.
- **Disconnect is Item-wide, not per-account**: Plaid's `/item/remove` revokes the WHOLE Item (no
  partial removal), so `plaid::disconnect_linked_account` flips EVERY `linked_accounts` row
  sharing the disconnected row's `plaid_item_id` to `disconnected`, surfaced in the frontend's
  Canada picker copy (`disconnectPlaidSiblingsNote`).
- **`ITEM_LOGIN_REQUIRED` maps onto the existing `consent_expired` status** (#320's GoCardless
  PSD2-expiry state, reused rather than adding a Plaid-specific one) — `LIST_LINKED_ACCOUNTS`/the
  frontend badge/manual-refresh's short-circuit handle it with zero Plaid-specific code. An
  unknown `item_id` in any webhook payload is logged at `warn` (no matching row, 200 no-op).
- **Webhook verification is JWT/ES256/JWK, not HMAC** — the one house-style exception in this
  integration (Belvo/Basiq/Akahu's webhooks all use HMAC/Basic-auth variants): `jsonwebtoken`
  (new dependency) verifies the `Plaid-Verification` header against a JWK fetched via
  `POST /webhook_verification_key/get` and cached process-wide by `kid`, checking `iat` freshness
  and a `request_body_sha256` body-hash claim. A JWK reporting `expired_at` is rejected and never
  cached (key-revocation safety); a bounded, TTL-swept negative cache for failed `kid` lookups
  prevents an attacker-controlled JWT header from driving unlimited outbound Plaid API calls.
- **Big-5 Canadian banks require Plaid's OAuth flow**: Plaid Link can navigate the browser away to
  the bank's own OAuth/Interac page and back to `PLAID_REDIRECT_URI` (`{APP_URL}/` by default)
  with an `oauth_state_id` param. Resuming requires reusing the SAME `link_token` used to open the
  original session AND passing `receivedRedirectUri` (the full return URL, captured before
  `history.replaceState` scrubs it) to `Plaid.create` — persisted in `localStorage` (a shared
  `PLAID_LINK_RESUME_KEY` constant, cleared via `try/finally` on every in-modal settle path so a
  later unrelated link attempt can't clobber an in-flight OAuth-redirect's resume data) and read
  back by `App.svelte`'s `handlePlaidOAuthReturn` on mount.
- **Fixed a pre-existing bug found while writing this migration**: `20260707000000_basiq_akahu_bank_linking.sql`
  had silently dropped `'belvo'` from `linked_accounts_provider_check`'s allowed values (it
  chained off the ORIGINAL 2-value list instead of Belvo's own 3-value list, since both migrations
  were authored concurrently against an unmerged base). This migration's `DROP`/`ADD CONSTRAINT`
  restores `'belvo'` alongside adding `'plaid'`.
- **Surfacing**: REST — `POST /api/budgets/:id/plaid/link-token` (returns `{link_token,
  session_id}`), `POST .../plaid/complete`, plus the now-shared `GET/POST/DELETE
  .../linked-accounts...` routes (unchanged); `POST /api/plaid/webhook` (public, folded into the
  same `bank_webhook_public_routes` nest as Basiq/Akahu). Chat — `LINK_BANK_ACCOUNT` gained
  `country: "CA"` support (no new params); `ChatResponse.plaid_link_token`/`plaid_link_session_id`
  carry the Link token/session through to the frontend — a NEW field pair, NOT a reuse of
  `bank_link_redirect_url`, since Plaid Link is a client-side modal (mirroring
  `financial_connections_client_secret`'s and Belvo's `belvo_widget_access_token`'s precedent)
  rather than a redirect. Frontend — a "Canada" option in the existing country `<select>`;

### 19. Categories View (#426)
- **A new JSON endpoint backs the page, not a server-rendered table**: `GET /api/budgets/:id/categories-view` (`budget::categories_view`) returns a `CategoriesViewResponse` envelope — `categories` rows plus `currency`, `time_frame`, `closed_at`, `permission_level` ("owner"/"edit"/"view", so the client can mirror the server's guards instead of guessing them), and the budget's own `rollover_enabled` + `budget_type` (see the rollover-gating bullet). It COMPOSES the pre-existing `budget::category_table_rows` — which already windows spend to the CURRENT period and resolves #52 rollup mirrors to their source budget's real limit/spend (§8, nels#298) — with the #49 carry that read path does NOT compute. The previous-period spend query and the mirror-name lookup are each skipped entirely when they cannot matter (the budget's rollover master switch is off or it is a `project` budget; the budget has no mirror rows), so an ordinary budget's read pays for neither.
- **`budget::category_carry_for` is the single source of the carry rule**: a pure helper extracted from `category_response_with_carry`, encoding the #228 fund-over-rollover precedence (§12) — a fund carries its materialized `fund_balance` and NEVER the #49 one-period carry, and a #52 mirror or any non-expense category never carries at all, returning `(0.0, 0.0)`. BOTH the REST `/categories` read path and `/categories-view` call it, so the two surfaces cannot disagree about a category's effective amount. A limit-less category keeps `effective_limit = None` even when it is a fund with a balance — the frontend needs "no limit" to render as no meter, not as a meter with a zero denominator.
- **`/budgets/:id/categories-table` is deprecated but RETAINED one release**, so a stale cached PWA client does not 404 into an error state. The HTML BUILDER is NOT deprecated — only the endpoint is: `rag.rs` still renders `build_categories_table_html` into chat bubbles for `LIST_CATEGORIES` and `CATEGORY_BALANCE`, and the `:global(.cat-table …)` CSS in `App.svelte` still styles exactly that path. Do not delete the builder or its styles when the endpoint goes.
- **Fund helpers moved into `budget.rs`**: `enable_category_fund` moved verbatim from `rag.rs` (pure move, SQL unchanged) and `disable_category_fund` was extracted from the inline statement in `chat_set_category_fund`. Both are IDEMPOTENT IN SQL — `WHERE id = $… AND is_fund = FALSE` / `AND is_fund = TRUE` — so a repeat call is a 0-row no-op that leaves `fund_balance`/`fund_advanced_through` exactly as they stand. Three callers now share them instead of a third copy of the semantics: `chat_set_category_fund`, `chat_create_categories`, and the REST `update_category`.
- **The REST fund toggle is called UNCONDITIONALLY, with no stale-read gate (deliberate)**: `update_category` invokes the helper whenever `payload.is_fund` is present, never gated on the `current` row snapshot it read earlier. Letting the SQL guard decide removes a lost-update race — two concurrent PUTs can share a pre-image, and a `&& current.is_fund` gate would make the second silently skip the write it explicitly asked for while still returning 200. The snapshot is a VALIDATION input only; a stale read there can at worst produce a spurious 400, never a silent wrong write. Do not "optimize" the gate back in.
- **`CategoryUpdatePayload.is_fund` is funds' first REST write path** (absent = unchanged, matching the COALESCE semantics of every other field on that payload). Write ORDERING in `update_category` is load-bearing: the invalid combination (`is_fund` on a non-`expense` target type) is rejected with a 400 BEFORE any write; a DISABLE runs BEFORE the main UPDATE; an ENABLE runs AFTER it, when the type is guaranteed `'expense'`. So `categories_is_fund_expense_only_check` can never be transiently violated and no validation error leaves a partial write. When the payload touched the flag at all, the row is re-read once afterwards, because the main UPDATE's `RETURNING *` image predates the enable. **The whole sequence is ATOMIC**: the disable, the main UPDATE, the enable and that re-read all run inside one `state.db.begin()` transaction, so a request either applies in full or leaves the row untouched — a rename that trips `unique_category_name_per_budget` returns 409 with the fund still ON, rather than 409 with the fund silently already switched off and its accrual stopped (regression guard: `update_category_rolls_back_the_fund_disable_when_the_rename_conflicts`). `enable_category_fund` / `disable_category_fund` therefore take a generic `sqlx::Executor` rather than `&AppState`, so they compose inside that transaction as well as against the bare pool (the two chat callers pass `&state.db`). Ordering is still load-bearing on top of the transaction because the CHECK is IMMEDIATE. A duplicate category name is a **409 with the same message on BOTH write paths** — `create_category` and `update_category` share `duplicate_category_name_error`; neither may let `internal_error` flatten it into a 500, since the client cannot tell which field is wrong from one and retrying can never succeed.
- **Currency is DERIVED, not modeled**: `budgets` has no currency column, so the envelope's `currency` is the modal non-NULL `transactions.currency` for the budget (`GROUP BY currency ORDER BY COUNT(*) DESC LIMIT 1`), with the frontend falling back to USD when it is None. The query filters on `transactions.budget_id` DIRECTLY and must NOT join through `categories` — `transaction.category_id` is NULLABLE and bank-synced rows (the only rows that carry a currency at all) arrive UNCATEGORIZED pending review, so joining through categories would drop exactly the population that carries a currency and silently render a budget of unreviewed EUR imports as USD. A real `budgets.currency` column is the honest long-term fix.
- **Deliberate divergence from the chat table**: this view includes the #49 carry in a category's effective limit (`category_limit + carried`), whereas `build_categories_table_html` computes only `fund_effective_limit(is_fund, limit, fund_balance)` and ignores the carry entirely. The two surfaces therefore CAN show different effective limits for a rollover-carrying non-fund category. The new surface is the more accurate one; reconciling the chat table is a follow-up, not a bug in this endpoint.
- **Rollover UI is gated on the BUDGET-level master switch, never on the per-category flag alone**: `categories.rollover_enabled` is `DEFAULT TRUE` while `budgets.rollover_enabled` is `DEFAULT FALSE`, and `category_carried` returns 0 whenever the master switch is off OR the budget is `project` (#48). So the per-category flag is INERT on the default budget, and gating on it alone would badge every category with a mechanism that does nothing. The envelope therefore carries the budget's `rollover_enabled` and `budget_type`; the page derives `rolloverActive = rollover_enabled === true && budget_type !== "project"` and (a) renders the Rollover badge only when `rolloverActive && cat.rollover_enabled && categoryCarryKind(cat) === "rollover"`, via the exported `showsRolloverBadge(row, rolloverActive)` helper in `categoriesView.js` — which `CategoriesView.svelte` calls at BOTH the badge-block wrapper condition and the inner badge condition, so those two cannot drift, and which `CHIP_PREDICATES.rollover` mirrors with the SAME `categoryCarryKind` term, though still only BY CONVENTION: they are two separately authored expressions and neither calls the other, and the chip deliberately omits the `rolloverActive` term because (b) already handles it — since #474 a parity test pins the pair over a plain / fund / fund+mirror / mirror / income / savings matrix rather than the fund clause alone, but the `rolloverActive` asymmetry is still unpinned, so change both; (b) drops the Rollover filter chip from the rendered strip entirely when `!rolloverActive`, or when `chipCounts().rollover` is 0, since after #474 a budget whose only rollover-enabled categories are funds, mirrors or non-expense rows would otherwise carry a permanent `Rollover 0` control that can select nothing — `chipCounts`/`filterByChip` stay chip-agnostic and still cover every key, only the strip narrows — and (c) keeps the editor's rollover checkbox functional but adds a hint under it saying WHY it currently does nothing: `categories.rolloverInactive` when the budget-level switch is off, `categories.rolloverSupersededByFund` when the switch is ON but the category is a fund, since telling a fund's owner "rollover is off for this budget" would send them to flip a switch that changes nothing. The FUND half of (a) and (c) is #433: per the `category_carry_for` bullet above, a fund's carry comes from its materialized `fund_balance` and never the #49 one-period carry, so badging it "Rollover" too rendered the same number twice under two mechanisms, only one of which is real. Take that bullet's qualification literally — only a NON-MIRROR EXPENSE fund reaches the `(0.0, fund_balance)` arm. **#474 completed the alignment**: `categoryCarryKind(row)` in `categoriesView.js` now reproduces `budget::category_carry_for` arm for arm — `"fund"` for a non-mirror expense fund, `"rollover"` for a non-mirror expense non-fund, `"none"` for everything else — and `showsRolloverBadge`, `showsFundBalance` and `CHIP_PREDICATES.rollover` all read it, so the page suppresses every carry claim the backend does not perform rather than accreting one exclusion per bug. The SHAPE of those arms is load-bearing: `!is_linked` is a conjunct of the FUND arm itself, not merely of the rollover arm below it, so a fund that is ALSO a #52 mirror fails both non-terminal arms, is `"none"`, and carries nothing at all (`category_carry_for_mirror_is_zero`) — it keeps its Fund badge, since `is_fund` is genuinely true, but NOT the `Balance: $X` line, since that number is not what the row carries. The conjuncts within an arm commute; what matters is which arm each appears in, and that the fund arm precedes the rollover arm — the rollover arm's guard is a strict superset of the fund arm's, so swapping them would make the fund arm unreachable and every fund would take the #49 carry. Dropping `!is_linked` from the fund arm is the exact mutation that resurrects the bug, and a frontend test pins it. Note "does not apply the #49 carry" is not "carries nothing": a non-mirror fund does carry, just its `fund_balance` under the Fund badge. All of these qualifiers ORIGINATE in the chat CATEGORIES context, which renders "Rollover: off (budget rollover disabled)" / "Rollover: n/a (project budget)" and, for a fund, `Fund: on | Balance: $X | Effective limit: $Y` INSTEAD of any rollover annotation — the whole string gated on `c.category_type == "expense" && c.linked_budget_id.is_none()` in `rag.rs`, which already covers all four: non-expense and mirror via that gate itself, funds via the inner `is_fund` short-circuit, and the budget-level switch via the `project` / `!rollover_enabled` branches inside it. #433 and #474 together align the page TO chat rather than diverging from it. They are not byte-identical for a fund+mirror row: chat gates its whole annotation, fund line included, on that same `rag.rs` condition and so shows such a row no fund annotation at all, while the page keeps a standalone Fund badge chat has no equivalent for. What the two agree on is the rule that matters — neither surface asserts a carry `category_carry_for` does not perform. They must not drift on that.
- **A ZERO effective limit is "no denominator", not "over"** — one rule shared by `meterPercent` and `healthStatus`, documented once above both in `categoriesView.js`. A limit of exactly 0 is explicitly permitted (`validateLimit` accepts `n >= 0`, and the copy says "Enter a number of 0 or more") and is also reachable for a fund whose `category_limit + fund_balance` lands on zero, since #228 has no floor. Both helpers return the neutral result there (`0` / `"none"`); only a genuinely NEGATIVE effective limit — a real overdrawn fund — is `"over"` with a saturated meter. They previously disagreed, painting a red icon, "Over limit" and `$0.00 left` over a `width:0%` bar with `aria-valuenow="0"`. A test pins the invariant: whenever `healthStatus` is `"over"`, `meterPercent` is `100`.
- **A limit cannot be CLEARED once set, and the editor says so instead of swallowing the edit**: `update_category` does `category_limit = COALESCE($3, category_limit)`, so a null means "unchanged" — the server genuinely cannot remove a limit. `validateLimit` therefore FAILS with `categories.limitNotClearable` ("set it to 0 instead") when the box is emptied in edit mode on a category that already has a limit. Create mode is untouched: `editing` is null there, where an empty box legitimately means "no limit". Without this the save produced no field, no error and no hint — the dialog just closed as though it saved, and a simultaneous rename would land while the cleared limit silently did not.
- **Frontend split follows the repo's test harness, not preference**: pure helpers live in `frontend/src/lib/categoriesView.js` (`meterPercent`, `healthStatus`, `groupCategories`, `searchCategories`, `filterByChip`, `chipCounts`, `expenseSummary`) and are unit-tested in `categoriesView.test.js`; `CategoriesView.svelte` itself has NO component test because vitest runs node-env in this repo (see "Frontend (Svelte 5)" below — `npm run build` is the component-level gate). `formatAmount` moved to `frontend/src/lib/money.js` and is now shared with the #403 transactions list, RE-EXPORTED from `transactionsView.js` so existing importers are unaffected. Locale parity for the `categories` namespace is enforced by a dedicated `describe` block in `i18nLocales.test.js` (every required key present in all six locales, and no locale with an extra or missing key vs `en`).
- **A zero-row `delete_category` is a 404, not a 204 (#434)**: the handler reads the category's name and then issues a SEPARATE `DELETE`, so `rows_affected() == 0` means THIS request removed nothing; it is now surfaced as `404 "Category not found"` plus a `tracing::warn!` carrying `budget_id`/`category_id`/`user_id`, with the `DELETE_CATEGORY` audit row suppressed. Same shape and rationale as `set_default_budget`'s `rows_affected` guard. The 404 body is deliberately IDENTICAL to the existence check's, since the caller's remedy is the same either way — which makes the warn, not the response, the only thing separating the two, so it is contract and a test captures its fields. **Do not over-read the window this guard covers**: it is exactly those two statements, microseconds wide, and the SAME for every caller. The long human-scale gaps — the chat flow's confirmation modal (`rag.rs`'s `DELETE_CATEGORY` is resolve-only and hands a `PendingDeletion` to the frontend, which then calls this endpoint) and the equally unbounded gap between the categories page loading its rows and the user tapping delete — are covered by the EXISTENCE CHECK's pre-existing 404, not by this guard, and neither surface is more exposed to it than the other. A concurrently deleted BUDGET usually never reaches it either, since `check_permission` returns 403 first. The race is deliberately REPORTED, not CLOSED — no transaction, no `FOR UPDATE`, no `DELETE … RETURNING name` — so do not "fix" it by closing the race. Suppressing the audit row prevents a false claim; it does NOT guarantee the disappearance is recorded anywhere, since a cascading `delete_budget`, a deleted rollup source, `unlink_rollup` and `cleanup_orphaned_auto_category` all remove `categories` rows without writing `DELETE_CATEGORY`. No frontend change was needed: both callers already surface a non-2xx.
- **Surfacing**: REST — the new `GET /budgets/:id/categories-view`, plus `is_fund` on `CategoryUpdatePayload`; edit / create / delete all go through the PRE-EXISTING `update_category` / `create_category` / `delete_category` handlers, so no new write endpoint ships here. Note REST `create_category` does NOT accept `is_fund`, so creating a fund from this page is a two-step create-then-toggle. Chat — unchanged; `LIST_CATEGORIES` / `CATEGORY_BALANCE` still render the HTML table (see the deprecation bullet above). Frontend — `CategoriesView.svelte` renders grouped Income / Savings / Expense cards with per-category meters, Fund / Rollover / Rollup badges, name search, up to six filter chips (`all`, `over`, `near`, `nolimit`, `funds`, and `rollover` only when rollover is active for the budget) with live counts, and a bottom-sheet editor gated on `permission_level` and `closed_at`. Mirror rows are never editable, matching `update_category`'s 409.

### 20. Retirement Balance Sheet — Assets, Holdings, Securities (#464)
- **`assets` is `user_id`-scoped, NOT `budget_id`-scoped — the deliberate break, do not "restore consistency"**: `backend/migrations/20260728163000_retirement_assets.sql` creates `assets` with `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE` and NO `budget_id` column at all, breaking the pattern every other financial table follows (`linked_accounts.budget_id`, `goals.budget_id`, `transactions.budget_id`, …). The break is load-bearing. Budgets are SHAREABLE, and the per-module `require_edit_or_owner` guards are written to grant a collaborator access to **everything beneath the budget** — which is the correct meaning of sharing for categories, transactions and goals. Retirement balances are not that kind of data: a budget-scoped `assets` would mean that sharing a household budget with a spouse, a roommate, an adult child or a financial coach silently hands them the full contents of one person's retirement accounts, and every existing guard would authorize it as correct. Scoping on `user_id` removes the share edge from the table entirely. Practical consequence for everything built on this: filter on `user_id`, never on `budget_id`, and never join through `budgets` to reach these rows. The route is `/api/assets`, deliberately not `/api/budgets/:id/assets`, for the same reason. The `ON DELETE CASCADE` on `user_id` chains through `asset_holdings.asset_id` and `asset_balance_history.asset_id`, which is what keeps `account.rs::delete_user_data` complete without naming any of the three new tables — it deletes the `users` row and the database does the rest. A future child table hanging off `assets` with anything other than CASCADE quietly breaks that.
- **Entitlement is `require_caller_tier`, NOT `require_tier`**: `assets::list_assets` gates on `access::require_caller_tier(&state.db, user_id, Tier::Pro)` — the CALLER's own subscription. `require_tier` resolves a BUDGET OWNER's subscription, and there is no budget in scope here by design, so there is nothing for it to resolve. Reaching for the familiar `require_tier` in a future assets handler means inventing a budget lookup, which is precisely the join this table exists to avoid.
- **The composite same-user FK is a data-layer invariant, not a convention**: `assets_linked_account_same_user_fkey` references the PAIR `(user_id, linked_account_id)` against `linked_accounts (user_id, id)` — which is why the migration first adds the unique index `linked_accounts_user_id_id_idx`, since PostgreSQL requires a unique constraint behind any FK target. It makes "an asset's linked account belongs to the same user as the asset" something the DATABASE enforces rather than something each writer must remember. What it prevents: every existing sync path in this codebase derives ownership from a linked account's BUDGET, so a holdings sync that follows that familiar pattern would, on a household budget shared by two people, file one member's retirement holdings under the OTHER member's `user_id` — after which `WHERE user_id = $1` serves the wrong person's retirement account to the wrong person, faithfully and silently. `MATCH SIMPLE` (PostgreSQL's default for multi-column FKs) means the constraint is skipped entirely when `linked_account_id IS NULL`, so manual assets are exempt with no partial constraint or trigger. `ON DELETE SET NULL (linked_account_id)` is the COLUMN-LIST form on purpose: plain `SET NULL` would null `user_id` too, and `user_id` is NOT NULL, so deleting a linked account would abort instead of orphaning the asset cleanly. That form needs PG15+; production and local dev are both PG16.
- **`owner_member_id` GOT its foreign key in a THIRD migration owned by neither issue — see §22 (#500), which is now the authoritative account of the link**: it references `retirement_profiles` (which household member an asset belongs to), but the FK was deliberately absent from BOTH migrations below because two conditions had to hold at once. (1) ORDERING ON A FRESH DATABASE — sqlx applies migrations in version-sorted order, not merge order (the sort happens once during source resolution, `sqlx-core-0.7.4 src/migrate/source.rs:137`; `Migrator::iter()` merely walks the already-sorted vector). #465 occupies `20260728093000`, which sorts BEFORE this file's `20260728163000`, so on a fresh database #465 runs first and `assets` does not exist yet — an FK declared there fails outright, and symmetrically an FK declared here fails wherever #465 has not run. The FK migration must therefore sort strictly AFTER both `20260728093000` and `20260728163000`. (2) MERGE ORDER IS NOT RELEASE ORDER — deploys here are release-gated, so "#465 merged first, therefore its table exists" does not follow; the FK migration must be authored in a PR that MERGES after both #464 and #465 are on main. Both conditions together meant a standalone third PR owned by neither issue, which is #500 / `20260728174500_assets_owner_member_fk.sql`. Do NOT edit either of the two migrations below to "add the FK where it belongs" — sqlx checksums applied migrations and any edit raises `VersionMismatch` on every existing database.
- **`asset_type` × `tax_treatment` are two ORTHOGONAL axes, not one enum**: `asset_type` is a COUNTRY-NEUTRAL wrapper taxonomy (`retirement_account`, `brokerage`, `cash`, `pension`, `annuity`, `real_estate`, `other`) — it names the KIND of container, never a national account product, because the geography decision on the epic #454 forbids baking US constants into the schema and `401k`/`ira`/`403b` mean nothing to a UK ISA/SIPP, a Canadian RRSP/TFSA, an Australian super fund or a NZ KiwiSaver, all of which this product already has bank-linking connectors for. The US specifics live in `tax_treatment` (`pre_tax`, `roth`, `taxable`, `hsa`, `other`): a 401(k) is `(retirement_account, pre_tax)`, a Roth IRA is `(retirement_account, roth)`, a taxable brokerage is `(brokerage, taxable)`. Collapsed into one column this would be a roughly twenty-value US-only enum that still could not express a non-US wrapper; kept orthogonal, adding a country widens `tax_treatment` alone. `tax_treatment` is NOT NULL and cannot be deferred — per decision 5 on #454 it is not derivable from the balance, the institution or the vendor payload, so adding it later means re-asking every user account by account. All taxonomies are TEXT + CHECK rather than PG ENUMs so they widen with a `DROP CONSTRAINT` / `ADD CONSTRAINT` swap — the same swap `linked_accounts.provider` has been through four times. **Both axes are TYPED in Rust, and the decode strictness differs on purpose**: `assets::AssetType` and `assets::TaxTreatment` are `#[derive(sqlx::Type)]` enums (`type_name = "TEXT"`, `rename_all = "snake_case"`) that decode STRICTLY from the TEXT columns — an unrecognised value fails the query and 500s, because the migration explicitly plans to widen `tax_treatment` per country and a widened CHECK reaching #467's projection maths as a bare `String` produces no compile error, just silently mis-taxed money in a number people plan their lives around. `assets::SecurityType` is the opposite: `SecurityType::from_db` is LENIENT, mapping an unknown value to `Other` with a `tracing::warn!`, because an unknown security type has an honest home (`Other` genuinely means "we do not know") while an unknown tax treatment has none. `classify_security_type` takes a `SecurityType` with **no `_ =>` wildcard**, so widening the `securities` CHECK is a COMPILE ERROR at exactly the one place that must decide the new instrument's bucket. `Etf` and `MutualFund` stay distinct from `Equity` even though all three currently bucket the same, because #468 may need to tell a bond fund from a stock. `currency` gained `CHECK (currency ~ '^[A-Z]{3}$')` — it was the one taxonomy column with no CHECK, leaving `'usd'`, `'dollars'` and `''` all storable; shape-only rather than a full ISO 4217 list, which would need a migration every time ISO publishes a change.
- **Non-finite floats are rejected in the SCHEMA, and the guard in code is `is_finite()` FIRST**: PostgreSQL's `double precision` genuinely ACCEPTS `'NaN'`, `'Infinity'` and `'-Infinity'`, so every money column carries a `..._finite_check` — `assets.current_balance`, `asset_holdings.market_value`, `asset_holdings.quantity`, `asset_balance_history.balance`. The CHECK shape is `col <> 'NaN'::float8 AND col <> 'Infinity'::float8 AND col <> '-Infinity'::float8`, which works precisely because PostgreSQL departs from IEEE 754 and defines `NaN = NaN` as TRUE; an IEEE-semantics `col = col` test would NOT work here. Verified empirically on PG16. The reason this matters beyond tidiness: Rust's `NaN <= 0.0` evaluates to FALSE, so a NaN sails straight past any bare `<= 0.0` guard, and `serde_json` serializes a non-finite `f64` as JSON `null` rather than raising — the user sees a missing number and NOTHING is logged anywhere. `Allocation::fractions` therefore checks `!total.is_finite()` FIRST and as a SEPARATE condition from the magnitude test; never reject a non-finite value with an ordered comparison.
- **Money comparisons use `RECONCILIATION_EPSILON` (0.005, half a cent), NOT a float epsilon**: real balances break the naive version — `18504.06 + 30199.96` evaluates to `48704.020000000004`, so reconciling against a reported `48704.02` yields a residual of `-7.28e-12`, and this module's contract reads a NEGATIVE residual as "the balance looks stale, surface it or trigger a refresh". Two figures that are the same money would raise a data-quality alarm on the user's screen; symmetrically a `+1e-12` residual would fold a picodollar sliver into `Other`. `allocate_reconciled` treats `|residual| < RECONCILIATION_EPSILON` as exactly zero and folds nothing, and `fractions()` uses the same constant as a floor so a `1e-12` total left over from long/short cancellation cannot produce fractions in the millions. The quantity is money, not an abstract real, and money has a natural resolution — the minor unit.
- **`Allocation` has NO stored `total` field — `total()` is a METHOD**: `equity + fixed_income + cash + other` is computed on demand, which makes "the total is the sum of the buckets" a THEOREM rather than a maintained convention. This crate is a binary, so #467 and #469 are in-crate callers who could otherwise construct or mutate an `Allocation` whose stored total disagreed with its buckets with nothing to catch it. The positive-residual branch of `allocate_reconciled` consequently adds to `other` ALONE and the total follows. `AllocationPct` was renamed `AllocationFractions` and `percentages()` to `fractions()` because the values are fractions (`0.6` = sixty percent), never pre-multiplied percents — and its real invariant is that the four fields sum to 1.0 but are **NOT** individually bounded to `0.0..=1.0`: a short position (which vendor data does contain) with a positive total yields one field negative and another above 1.0.
- **`assets.current_balance` is NULLABLE, exactly as `balance_as_of` is**: `NOT NULL DEFAULT 0` would conflate "no balance has ever been reported" with "the custodian reported zero". A balance and the date it was taken on are one fact, so it would be incoherent for the date to admit "never reported" while the number could not. Concretely, a freshly synced asset with holdings but no balance yet would read as 0 and `allocate_reconciled` would compute `residual = -holdings_total` — a large negative residual, i.e. the false stale-balance signal above, on EVERY new asset. `Asset.current_balance` is `Option<f64>` and `allocate_reconciled(holdings, None)` degrades to plain `allocate` with a zero residual. Note this makes `current_balance` nullable in the `GET /api/assets` JSON; `asset_type` and `tax_treatment` serialize byte-identically to the bare `String`s they replaced, pinned by an assertion in the router test.
- **UNHANDLED: multi-currency allocation**: `allocate` adds every holding's `market_value` as a bare number, which is only meaningful if all holdings share one currency, and NOTHING checks it. `securities.currency` is nullable and per-row, so a genuinely mixed-currency account — a UK employer plan holding a US-listed fund — would silently total two different units. Today no write path can create one, so the assumption holds vacuously; it stops holding the moment #468's holdings sync writes real vendor data. #468/#467 must then either convert to the asset's `currency` before summing or refuse to allocate a mixed-currency asset. Silently applying an FX rate inside `allocate` would be the worst of the three.
- **`securities` is a shared non-personal cache; `asset_holdings` deletes RESTRICT into it**: `securities` holds instrument metadata keyed on `(provider, provider_security_id)` with no `user_id` and no per-user rows ("VTSAX is a mutual fund" is the same fact for everyone). `asset_holdings.security_id` is the ONLY `ON DELETE RESTRICT` in this schema — nothing in the product deletes from `securities`, and if some future path tries, RESTRICT surfaces it as a failed DELETE rather than shredding every user's holdings (CASCADE) or leaving unattributable ones behind (SET NULL). The GDPR export in `account.rs::fetch_account_export` therefore exports `assets`, `asset_holdings` and `asset_balance_history` — all filtered on `user_id`, the latter two via a JOIN back to `assets` — and deliberately does NOT export `securities`, which would ship a global vendor catalog into one person's DSAR response; each holding carries `security_id` if a reader needs to resolve the rest.
- **Obligations #468 inherits (holdings sync)**: take `user_id` from the SESSION, never from the linked account's budget — the FK will reject the cross-user insert, but the intent has to be right before the constraint is the thing catching it. Set `updated_at` in APPLICATION code: there is no trigger on any of these tables, so `updated_at` currently equals `created_at` forever. Widen the `securities.provider` CHECK (currently `'plaid'` only) if the US provider decision changes. A batch variant of `assets::upsert_balance_history` must ensure its SELECT yields AT MOST ONE row per `(asset_id, as_of)` conflict key, or PostgreSQL raises "ON CONFLICT DO UPDATE command cannot affect row a second time". **Two access-control denials are typed and MUST be surfaced, never swallowed.** `upsert_balance_history` returns `#[must_use] BalanceWrite` — `Written` or `NotOwned` — rather than the raw `rows_affected()`; `u64` is not `#[must_use]`, so `upsert_balance_history(...).await?;` used to compile cleanly while discarding the one bit that said the write had been REFUSED, on a table whose entire access control is the `user_id` filter. `holdings_for_asset` returns `Option<Vec<HoldingValue>>` where `None` means "no asset with that id belongs to this user" and `Some(vec![])` means "you own it and it genuinely has no holdings"; collapsing those two (the old signature returned a bare `Vec` and used the empty vec for both) turns a denied read into an all-zero `Allocation` that renders as "$0, no allocation" — a refusal presented to the user as a fact about their money and handed to #467 as real data. Both denials log a `tracing::warn!` server-side: silence toward the CALLER is the security property, silence in the LOGS is just a blind spot. Handle the composite FK's `foreign_key_violation` DELIBERATELY rather than letting it surface as a 500 — note that `linked_accounts.user_id` is "whoever linked it first" (the re-link path upserts on the globally-unique `provider_account_id` and preserves the existing `user_id`), so in a shared household budget the FK will force an asset under the ORIGINAL linker's `user_id` and reject the other member's attempt; that is a real product situation needing a real message, not an internal error.
- **Surfacing**: REST — `GET /api/assets` (`assets::list_assets`, Pro-gated via `require_caller_tier`, user-scoped, returns each caller's OWN assets ordered by `created_at`). It returns an EMPTY LIST for every real user until #468 provides a write path; there is no create/update/delete endpoint in #464. Chat — **NONE**, deliberately: there is nothing to surface until #468 writes data and #469 renders it, and the compliance decision on #454 forbids LLM prose about retirement figures, so no `rag.rs` action arm ships here and none should be added ahead of those issues. Frontend — **NONE**.
- **Tests**: the pure allocation helpers in `backend/src/assets.rs` (`SecurityType::from_db`, `classify_security_type`, `allocate`, `allocate_reconciled`, `Allocation::total`, `Allocation::fractions`) have 32 always-run unit tests. The old "buckets sum to total" cross-cutting test is gone as tautological — `total()` is now derived — and is replaced by `reconciliation_matrix_obeys_the_residual_contract`, which over the same matrix asserts the still-falsifiable part: a positive residual makes `total()` equal the REPORTED balance, a non-positive one leaves it at the holdings total, only `other` ever moves, and `None` never reconciles anything. Also pinned: that a NaN/Infinity total yields `None` from `fractions()` (with the `NaN <= 0.0` trap itself asserted so the rationale cannot rot), that the `18504.06 + 30199.96` vs `48704.02` cancellation case reports EXACT agreement rather than a stale-balance signal while a one-cent discrepancy is still reported, that `None` and `Some(0.0)` reported balances behave differently, that fractions are not bounded to `0.0..=1.0` under a short position, and that all three enums serialize to their CHECK literals character for character. DB-backed (`--ignored`) tests cover the security property the issue exists for: an `edit` collaborator on the owner's budget reads NONE of the owner's assets while still reading their own (asserted both by calling the handler directly and through a real axum service with the `oneshot` + `from_fn` harness `admin.rs`/`usage.rs` use), the Pro gate, `holdings_for_asset` user-scoping in all four states (owned-with-holdings, owned-but-empty `Some(vec![])`, foreign-asset `None`, unknown-id `None`), `upsert_balance_history` idempotency and its `BalanceWrite::NotOwned` rejection on a foreign asset id, the composite FK rejecting a cross-user linked account with SQLSTATE 23503 while the same-user insert succeeds, and an `information_schema` assertion that `assets` has NO `budget_id` column and a NOT NULL `user_id`. That last one pins the acceptance criterion at the schema level — the consequence-level tests stay green for a while after a `budget_id` column is added back, and by then the first natural-looking join through it has reintroduced the share edge. Note the router test necessarily re-declares the `/assets` path literal: `protected_routes` is a local `let` binding inside `#[tokio::main] async fn main()`, not an item, so no inline test can mount the shipped router.
### 21. Retirement Profile & Assumptions (#465)
- **A NEW `retirement_profiles` table, deliberately NOT columns on `users`** (`backend/migrations/20260728093000_retirement_profiles.sql`): this is a correction to the #454 epic's own decomposition text, which said "needs a `users`/profile migration". Two reasons, both recorded in the migration's header comment. First, `users` has already accreted single-purpose columns through FOUR separate column-adding `ALTER TABLE users` migrations, and bolting eleven more planner-only columns onto the row that every authenticated request loads makes that worse. Second — and this is the one that actually forecloses the option — columns on `users` cannot express the per-household-member shape #454 decision 6 requires: one user may eventually have two retirement members, and only a row-per-member avoids that becoming a table restructure later. `git diff` for this issue shows zero new columns on `users`; keep it that way.
- **Keyed `(user_id, member_ordinal)` with a `UNIQUE` constraint, so a second household member is a new ROW and never a schema change** (#454 decision 6). v1 only ever writes `member_ordinal = 1`, and NO surface can create a second: the ordinal is absent from `RetirementProfileInput` entirely — so neither the REST payload nor the chat params can name it — and it is pinned as the SQL literal `1` in `upsert_profile`'s `INSERT`, with `get_profile`'s `SELECT` pinning `member_ordinal = 1` the same way rather than parameterising it. `CHECK (member_ordinal >= 1)` and the `retirement_profiles_user_id_idx` index are there for the future second row. Joint-household behaviour — combined projections, survivor assumptions, anything that reads two members at once — is DELIBERATELY deferred, so record the caveat honestly: a single-person v1 profile OVERSTATES readiness for a couple, because it prices one person's retirement and one person's income. `#500` added `assets.owner_member_id` referencing `retirement_profiles (user_id, id)` — see §22 — which is the whole reason the ordinal exists now instead of later. **Do not fold `UNIQUE (user_id, member_ordinal)` into that FK's `(user_id, id)` index or vice versa**: they are separate keys serving separate purposes, and the FK depends on the latter existing independently.
- **`country` is EXPLICIT and USER-SET, never inferred from linked accounts** (#454 decision 2): a user can legitimately link accounts in several countries, and the frontend's `selectedCountry` is transient UI state that is never persisted anywhere. This column is the ONLY place in the database that records where a *user* lives — everything else records where an *account* or an *institution* lives — and it is the single gate for the whole planner feature. `retirement::retirement_supported_country(cc) -> bool` is `matches!(cc.to_uppercase().as_str(), "US")`, mirroring `bank_provider::Provider::for_country`'s closed-set, case-insensitive style DELIBERATELY: adding a country later costs one match arm, not an abstraction. **A non-US profile SAVES and is reported `supported: false`** — the gate is a RENDERING gate (#469 / epic AC 5), not a write gate. Rejecting `country = "FR"` at the write would leave the column unable to record where the user actually lives, which is the column's entire stated purpose. `RetirementProfileResponse` flattens the row and carries the derived `supported` alongside it (the `goals::GoalDetail` `#[serde(flatten)]` precedent) so no consumer re-derives the US-only rule and drifts from it.
- **UNITS are load-bearing, not incidental** — the stored numbers deliberately MIX percent-scale and fraction-scale, and #467's projection math is wrong BY A FACTOR OF 100 if any of them is misread. The migration's header, every constant's doc comment, the `RetirementProfile`/`ResolvedProfile` doc comments, the LLM params schema and prompt rule 21d all restate this list; keep them in step:
  - `contribution_rate_pre_tax` — **PERCENT** of gross (`6.0` = 6%); default `0.0`, nothing assumed
  - `contribution_rate_roth` — **PERCENT** of gross (`3.0` = 3%); default `0.0`, nothing assumed
  - `expected_real_return` — **PERCENT** per year, REAL and already net of inflation, not nominal (`5.0` = 5%); default `5.0`
  - `inflation_rate` — **PERCENT** per year (`2.5` = 2.5%); default `2.5`
  - `target_replacement_ratio` — **FRACTION** of gross, NOT a percent (`0.75` = 75%); default `0.75`
  - `target_retirement_age` / `life_expectancy_age` — whole years; defaults `65` / `90`
  - `current_gross_income` — absolute ANNUAL dollars
  - `MatchTier.employee_pct_up_to` — **PERCENT** of gross, cumulative; `MatchTier.match_pct` — **PERCENT** of the covered band; `annual_dollar_cap` — absolute dollars, `None` = uncapped
  The two contribution rates are percent-scaled because the issue's own validation rule is "contribution rates summing above 100", which is only meaningful on a percent scale; `target_replacement_ratio` is fraction-scaled because the issue calls it a *ratio* and gives `0.75`. That inconsistency is inherited from the spec, not invented here — do not "normalize" one to the other without changing every site in the list above plus #467.
- **The defaults are named Rust constants, and the assumption columns carry NO SQL `DEFAULT`** — `DEFAULT_TARGET_RETIREMENT_AGE = 65`, `DEFAULT_EXPECTED_REAL_RETURN = 5.0`, `DEFAULT_INFLATION_RATE = 2.5`, `DEFAULT_LIFE_EXPECTANCY_AGE = 90`, `DEFAULT_TARGET_REPLACEMENT_RATIO = 0.75`, plus `default_employer_match()`. Duplicating those numbers in the migration would give two sources of truth that drift silently, so the columns are `NOT NULL` with no default and the Rust write path ALWAYS supplies a value; `member_ordinal` keeps its SQL `DEFAULT 1` because it is structural, not an assumption. Each numeric constant's doc comment carries the exact string **"conventional planning figure, not a Nels forecast"** — that phrase is the provenance #454 decision 3 and the AC's "labelled with where the default came from" require, and #469 renders it, so do not paraphrase it away. A unit test pins all of the values so a change has to be deliberate. Note the two contribution rates are NOT constants: `resolve_input` falls back to a literal `0.0` because nothing at all is assumed about what a user contributes.
- **Employer match is tiered JSONB with a pure cumulative-band evaluator** — not free text and not a single percentage. `EmployerMatch { tiers: Vec<MatchTier>, annual_dollar_cap: Option<f64> }` is stored in `employer_match_formula JSONB`; tiers are ORDERED and CUMULATIVE, so `employee_pct_up_to` is the cumulative employee-contribution percentage at which a tier STOPS and tier *i* covers the band `(previous_up_to, up_to_i]` and only that band. `employer_match(gross, employee_pct, &formula) -> dollars` sums `gross × (band_pct / 100) × (match_pct / 100)` over the tiers, then applies `matched.min(cap).max(0.0)` when a cap is present and `matched.max(0.0)` otherwise — one composed expression, so the negative-cap clamp and the cap clamp are not two rules a reader has to reconcile. Worked example, "100% of the first 3%, then 50% of the next 2%" on a $100,000 gross while contributing 5%: tiers `[{3, 100}, {5, 50}]` give `100000 × 3% × 100% = 3000` plus `100000 × 2% × 50% = 1000`, i.e. **$4000**; contributing 10% still yields $4000, because the excess above the top tier is unmatched. Negative gross, negative employee percentage, negative `match_pct` and a negative cap all collapse to `0.0`, and there is no division by any input. **The stored default is ZERO tiers, not a fabricated one.** The issue's "Default is a single tier" is read as a statement about the SHAPE users edit into — one tier is the common case, do not force multi-tier — and NOT as a licence to assume a match percentage nobody stated. Inventing a match would OVERSTATE retirement readiness, which is precisely the direction of error #465's own employer-match paragraph warns against; the evaluator handles 0..N tiers and one tier is simply its ordinary case. If the intent really was one seeded tier, that is a one-line constant change plus a test.
- **`employer_match`'s formula ASSUMES a strictly-increasing tier list, and `validate_profile` is what enforces that invariant** — the evaluator subtracts the PREVIOUS tier's ceiling rather than a running maximum, which is exactly the formula #465 specifies, but on a list like `[{5,100},{3,100},{7,100}]` it charges 9 percentage points of match against a top ceiling of only 7, i.e. it OVER-states the match. Rather than quietly diverge from the documented formula, `validate_profile` rejects any non-strictly-increasing tier list (plus negative `employee_pct_up_to`, negative `match_pct` and a negative cap), and it runs on EVERY write path, so a pathological formula cannot reach storage. The consequence for future code: **anything that deserializes an `EmployerMatch` straight out of the JSONB column and evaluates it without re-validating must validate first** — the guarantee lives in the validator, not in the type and not in the evaluator.
- **`validate_profile` carries UPPER plausibility bounds as well as lower ones, and each is a named constant documented as a plausibility guard and NOT a forecast.** `MAX_PLAUSIBLE_TARGET_REPLACEMENT_RATIO = 2.0`, `MAX_PLAUSIBLE_EXPECTED_REAL_RETURN = 30.0`, `MAX_PLAUSIBLE_INFLATION_RATE = 50.0`, `MAX_PLAUSIBLE_LIFE_EXPECTANCY_AGE = 130`, `MAX_PLAUSIBLE_CURRENT_GROSS_INCOME = 100_000_000.0`. None of them says anything about what a return, an inflation rate or a lifespan will be; they exist because `validate_profile` is the ONLY choke point between a caller and #467's math, and the rate fields had a floor but no ceiling at all. The failure they catch is the SCALE CONFUSION the UNITS bullet above warns about: `target_replacement_ratio: 75.0` — a user or a model saying "75%" on the field that is a FRACTION — passed every other rule and stored a number 100x off, with the projection then wrong by that factor and no signal anywhere. Every message NAMES the expected scale so the caller can fix the input rather than guess, the comparison is strictly greater-than so the constant itself is accepted, and each bound is tested on both sides. Keep them far outside any real value: these must only ever fire on a mistake, never on an unusual but honest plan.
- **The "target retirement age must be in the future" rule is gated on `target_retirement_age_is_being_set`, and MUST stay gated.** `validate_profile` runs on the MERGED profile, so an unconditional rule re-judges a STORED, historical value on every later write. A profile created legally at 64 with a target of 65 then became permanently uneditable from the user's 65th birthday — not their income, not their assumptions, via neither REST nor chat, because a partial update touching only `inflation_rate` still re-checked the old age against today. `ResolvedProfile` therefore carries `target_retirement_age_is_being_set` (true on every create; on an update only when the caller actually supplied the field) alongside the older `target_retirement_age_was_defaulted`. The rule still rejects explicitly SETTING an age at or below the current age. The life-expectancy rule stays UNCONDITIONAL on purpose: it compares two stored values to each other and has no dependence on the clock, so it can never start failing merely because time passed. Any future clock-dependent rule needs the same treatment. **nels#533 added the third branch: a SUBSTITUTED default (a first-time create that omitted the age, so the 65 default was applied) that lands in the past is NO LONGER a rejection at all.** Before #533 it was a hard 400 that discarded the whole gathered create (country / birth date / income accumulated across several turns); now it SAVES and surfaces the problem as a WARNING via the new pure helper `stale_defaulted_age_warning` (fires only when `target_retirement_age_is_being_set && target_retirement_age_was_defaulted && target_retirement_age <= current_age`, so it never re-judges a stored value on an unrelated edit — the C1 rule applied to warnings as well as rejections). The warning travels on BOTH surfaces from the single `upsert_profile` write: `RetirementProfileResponse.warning` on REST (omitted from the JSON when `None`), and appended to the chat success log exactly like the non-US note. `upsert_profile` now returns `Result<(RetirementProfile, Option<String>), _>` — the second element is the warning — so every call site destructures the pair; a follow-up turn that names a real age merges onto the saved row (one row, no re-gathering).
- **`upsert_profile` is the ONE write path**, shared by the REST `PUT` handler and the chat `SET_RETIREMENT_PROFILE` arm. That structural sharing — not a review convention — is why the two surfaces cannot drift on defaults, merge semantics or validation: there is no second piece of SQL to keep in step. It runs read → merge (`resolve_input`) → validate (`validate_profile`) → a single `INSERT … ON CONFLICT (user_id, member_ordinal) DO UPDATE … RETURNING *`. `resolve_input` is pure and separately unit-tested: on a CREATE, `country`, `birth_date` and `current_gross_income` are required (400 naming the first missing one) because they are the only three fields that cannot be defaulted without fabricating a fact about the user, and everything else falls back to its named constant; on an UPDATE every absent field falls back to the STORED value, the COALESCE semantics `goals::update_goal` already sets as the house pattern. `country` is trimmed and uppercased there, which is load-bearing: the DB CHECK is `^[A-Z]{2}$` while `validate_profile` accepts either case, so without it a lowercase `"us"` would pass validation and then fail the constraint as a 500 instead of saving. Validation reads the MERGED result, so a partial update cannot half-write its way into an invalid state. A decode failure on the stored `employer_match_formula` JSONB is a **500**, never a 400 — corrupt JSONB in our own table is our bug, and silently defaulting it to "no match" would understate a real employer match with no signal at all.
- **`EmployerMatch` is the LENIENT input type; `StoredEmployerMatch` is the STRICT storage type, and the storage side must never use the lenient one.** They are deliberately near-identical structs, and the difference is the whole point: `EmployerMatch` carries `#[serde(default)]` on both fields, `StoredEmployerMatch` carries none and adds `deny_unknown_fields`. A missing `tiers` key means two OPPOSITE things on the two sides — "I am not telling you about tiers" on input, and "this row's match has been lost" in storage. When `upsert_profile` decoded the column through the lenient type, a stored `{"annual_dollar_cap": 5000}` or `{}` — a hand-edited row, a half-finished migration, a future writer that forgets a key — decoded CLEANLY to zero tiers, and the very next `DO UPDATE` wrote that fabricated no-match back over the user's real formula with a `200` and no log line; #467 would then consume it as fact. Understating a match is the exact direction of error this module exists to refuse, so the storage decode is strict and fails loudly instead. Our own writer always emits BOTH keys (`serde_json::to_value` renders `annual_dollar_cap: None` as an explicit `null`), so nothing we write is ever rejected. If you add a field to the formula, add it to BOTH types or every existing row stops decoding.
- **`employer_match_formula` is the ONE input field with WHOLE-OBJECT replacement semantics** — every other field on `RetirementProfileInput` is COALESCE-style "absent means leave it alone", and this one is absent-or-TOTAL. Sending it at all replaces the entire stored formula, and any key omitted from the object you send falls to `EmployerMatch`'s own serde defaults. So `PUT {"employer_match_formula": {"annual_dollar_cap": 5000}}` from a caller who meant "add a cap to my existing tiers" WIPES every tier, with a `200` and no warning. That is kept rather than deep-merged because a tier LIST has no per-element identity to merge on — any merge rule would have to invent one, and none of them leaves a way to DELETE a tier — so replacement is the only rule under which every reachable formula is also expressible. It is a REST-only sharp edge: rule 21d forbids the model setting the formula at all. Pinned by `resolve_input_replaces_the_whole_employer_match_rather_than_merging_it`, which deserializes the payload from real JSON because the wipe is precisely a consequence of what serde does with the absent key.
- **The row is locked `SELECT … FOR UPDATE` across the WHOLE read-merge-validate-write, inside one transaction** — and this is NOT the §19 `update_category` precedent, so do not "simplify" it into one. `upsert_profile` merges in Rust and then binds a fully resolved literal for EVERY column; there is no SQL `COALESCE` letting the database resolve "not supplied → keep current" against the live row. Without the lock, two concurrent partial writes — two browser tabs, or a REST `PUT` racing the chat arm — would each read the same pre-image, each resolve the other's untouched fields to the STALE value, and the second commit would silently discard the first writer's change even though that writer already got a `200` showing it. Holding the lock from the read through the write serializes them: the loser blocks, re-reads the winner's committed values, and merges onto those. SQL-level `COALESCE($n, column)` was considered and REJECTED: it closes the lost update, but the invariants here are CROSS-FIELD, not per-column — `life_expectancy_age > target_retirement_age` and `target_retirement_age > current_age` would be validated in Rust against a stale snapshot while the database assembled the final row out of live values, producing a stored row that no writer ever validated. The lock buys both properties at once. §19's `update_category` gets away with the other approach because its contested field is a single independent boolean whose snapshot is a validation input only; this one's is not.
- **Concurrent CREATEs need a SECOND lock, and `pg_advisory_xact_lock` on the user key is it.** `FOR UPDATE` locks nothing when it selects nothing, so for a user with no row yet both callers see `None` and both merge onto the DEFAULTS. `ON CONFLICT` does NOT rescue that — an earlier draft of this section claimed it did, reasoning only about the three fields that cannot be defaulted, and the reasoning was wrong because the loss happens in the EIGHT defaultable ones. Writer A sends the three required fields plus `contribution_rate_pre_tax: 6.0` and gets a `200` echoing `6.0`; writer B sends the three required fields plus `target_retirement_age: 62`, resolves A's untouched rate to its own default of `0.0`, and its `DO UPDATE` overwrites A's value. Both callers saw success and nothing was logged. The advisory lock is taken on the user key BEFORE the `SELECT`, so the no-row case serializes exactly like the existing-row case: the loser blocks, re-reads the winner's committed row, and merges onto that. It is transaction-scoped, so it releases on commit or rollback with no unlock path to forget, and keyed on the user, so it never serializes unrelated users. `concurrent_creates_with_no_existing_row_do_not_clobber_each_other` fails on every run without it.
- **Entitlement is Pro via `require_caller_tier`, NOT `require_tier`** (#454 decision 4): `require_tier` resolves the BUDGET OWNER's subscription, and retirement data is user-scoped with no budget in play at all, so the caller's own subscription is the only correct thing to read. Both the REST `PUT` and the chat arm gate this way, so they cannot diverge. `GET` is deliberately UNGATED, per the §14 precedent that a lapsed subscriber must still be able to see and manage their own data — writing a profile is the gated action, reading your own row back is not. In chat the params-presence check runs BEFORE the Pro gate, so a user who merely mentioned retirement without supplying a single field gets a prompt for the fields rather than a paywall message for a turn in which they asked to write nothing; when the gate does refuse, the refusal is returned as the error half and surfaces as a visible `mutation_error` (`⚠️ System Update`) line, NEVER a silent no-op that would leave the user believing the profile saved.
- **`chat_set_retirement_profile` returns THREE channels, and picking the wrong one is the bug this shape prevents.** `(success_log, error, clarifying_question)`. A clarifying question is NOT a failure and must not travel as one: returned as the error half it renders as `**System Update:** ⚠️ …` appended AFTER the turn's `response_text`, stamping a warning on a turn where nothing was attempted and nothing failed — and offline it is worse, because the router already sets a `response_text` asking for the same fields, so the user is asked twice in one reply and flagged for it once. This is structurally identical to the **#300 `CREATE_BUDGET`-with-no-strategy** case, which resolved it by overriding `parsed_ai_res.response_text` DIRECTLY; the retirement arm follows that precedent, and the dispatch arm assigns the clarifying half to `response_text`. So: the clarifying half carries the two "not enough information yet" cases — no params at all, and `resolve_input` reporting a missing required create field, matched on `retirement::MISSING_REQUIRED_FIELD_SUFFIX`, a constant with exactly one producer so the two ends cannot drift — while `mutation_error` is reserved for the Pro refusal and for genuine validation failures. **nels#533 made the missing-field case acknowledge rather than re-ask**: the reply confirms back WHICH of the three required create fields (`country` / `birth_date` / `current_gross_income`) are already in hand on this turn and requests only the genuinely-missing ones (`english_and_list` + the `present_required_retirement_fields` / `missing_required_retirement_fields` helpers) — the pre-fix copy re-listed all three even when the user had just supplied one or two, which read as the assistant not listening. **Branch on the STATUS, never collapse it**: a `500` gets the friendly retry copy the sibling arms use, because passing its text through verbatim made a corrupt row or a database outage read mid-conversation as a bare `Internal server error`; a `400` is written FOR the user, names the field and its expected scale, and is passed through unchanged.
- **A non-US chat user is TOLD the planner will not work for them yet.** REST carries `supported: false` on the response, but this release ships NO frontend, so without this nothing anywhere disclosed the limit: a French user saved a complete profile, received a confirmation listing every field back to them, and then watched the feature never appear, with no way to tell whether it was them or us. When `!retirement_supported_country(&profile.country)` the success log appends `RETIREMENT_NON_US_NOTE`, one factual sentence saying projections are US-only right now so the details are saved but no projection will be shown. It is a statement of FACT about product behaviour — which rows this build will draw a projection from — and not advice, so it does not conflict with #454 decision 3: it says nothing about the user's numbers, suggests no action, and characterises no assumption. Do not editorialize beyond it, and delete it when #469 renders the gate visibly. `required_perm_for_action` returns `None` for `SET_RETIREMENT_PROFILE` and `chat_action_is_write_gated` (the B3 budget-write gate) therefore does not cover it — which is right: that gate is about writes to a BUDGET, and double-gating here would turn a Pro upsell into a read-only 402.
- **`AiActionParams` nests `retirement_profile` rather than adding fourteen flat fields** — a DOCUMENTED deviation from this file's flat-params house convention. The profile has fourteen settable fields (eleven from #465 plus #466's three Social Security fields), and 14 `AiActionParams { … }` struct literals in `rag.rs` enumerate every field explicitly (the rest close with `..Default::default()` / `..blank_action_params()`), so flat fields would have meant roughly **196 lines of `field: None,`**. Verify the count with `rg -c 'institution_query: None' backend/src/rag.rs` — every enumerating literal ends with that field — before quoting a different number. The nested field reuses `crate::retirement::RetirementProfileInput` DIRECTLY rather than declaring a parallel params struct: sharing the exact type the REST `PUT` deserializes is the other half of what stops chat and REST from drifting. **Watch the `country` NAME COLLISION**: `AiActionParams` already has a flat `country: Option<String>`, also ISO 3166-1 alpha-2, belonging to `LINK_BANK_ACCOUNT` (#320), and the nested object introduces a second one. BOTH the LLM params schema line and prompt rule 21d state explicitly that the retirement country goes INSIDE the `retirement_profile` object and never in the top-level field; without that the model fills the wrong one, the write sees no country, and the user is re-asked for something they just said.
- **Every scalar on `RetirementProfileInput` deserializes through a LENIENT helper, because a strict one throws the whole chat turn away.** A serde failure ANYWHERE inside `AiStructuredResponse` sends the turn through the malformed-response fallback: the user gets a generic apology with no indication which field was wrong, and the model gets no signal to correct itself. This struct is unusually exposed to that — `target_retirement_age` and `life_expectancy_age` are the ONLY integer-typed params reachable from `AiActionParams` (every other numeric there is `f64`), and `birth_date` is its only `NaiveDate`, where the house pattern for a model-supplied date is a lenient `Option<String>` parsed at the use site, as `target_date` does. So the strictest types in the whole params surface sat on the newest action, and `"target_retirement_age": 62.0`, `"62"`, `"current_gross_income": "120000"` and `"birth_date": "1985-06-15T00:00:00Z"` — all routine model formatting, none of it ambiguous — each discarded the user's entire message. `de_lenient_i32` / `de_lenient_f64` / `de_lenient_date` now accept those variants. **Two rules bind any change here.** They widen the accepted FORMAT and never the accepted MEANING: a float with a real fractional part on an AGE field ERRORS rather than truncating, because rounding would silently change what the caller said, and non-finite values are refused so no `NaN` reaches #467's math. And they NEVER silently drop a field — REST shares this exact type, and a quietly ignored key reads as a successful save of a value that was never stored, which is strictly worse than a 400. An explicit `null` still means "leave it alone", the same as an absent key.
- **Test-infrastructure gotcha — seed a Pro user with `status = 'trialing'`, never `'active'`**: `require_caller_tier` resolves through `PriceCatalog::from_env()`, whose `STRIPE_PRICE_PRO_MONTHLY` / `STRIPE_PRICE_PRO_ANNUAL` are UNSET in the test process, so `tier_for()` returns `None` and an `active` row fails safe to `Tier::Basic` — a seeded "Pro" subscription still yields a **402** and looks like a bug in the handler. `entitlement.rs` maps `trialing` to `Tier::Pro` unconditionally with no env var involved, which is the only way a real handler path can be exercised as Pro without mutating process-global env vars (`access.rs`'s own Pro tests dodge this by calling the `*_with` variant with an explicit catalog, which a handler cannot do). Related: `subscriptions.stripe_customer_id` carries a UNIQUE index, so a test seed must bind a PER-USER id such as `cus_test_{user_id}` — a hardcoded literal makes the second concurrently-running test that seeds a Pro user die with a 23505 duplicate key, and cargo runs tests in parallel by default. Both `retirement.rs`'s and `rag.rs`'s `mk_pro` / `seed_active_sub` helpers carry this in a comment; do not "fix" either back.
- **Surfacing**: REST — `GET` / `PUT /api/retirement/profile`, user-scoped with NO `:budget_id` in the path (`main.rs`'s `protected_routes`). `GET` returns `200` with a JSON `null` body when there is no profile, NOT a 404: "not set up yet" is a normal state rather than an error, and a synthesized placeholder would have to fabricate a date of birth, so `null` is the honest answer (`billing::get_subscription` sets the don't-404-an-absent-row precedent but can synthesize a meaningful free-tier response; this one cannot). Chat — `SET_RETIREMENT_PROFILE`, added to the action enum and the `action_params` schema, driven by prompt rule **21d**, handled by `chat_set_retirement_profile`, with `offline_retirement_action` as the offline matcher and an `AI_SET_RETIREMENT_PROFILE` audit row written through `log_user_audit` with a NULL `budget_id` (user-scoped, per §10). Rule 21d forbids the model editorializing, per #454 decision 3 — chat is the cheapest place to emit advice by accident — and carries the specific prohibitions: no telling the user to contribute more or less, no saying whether they are on track / ahead / behind, no ranking or comparing account types such as 401k vs IRA vs Roth, no recommending an action in response to any shortfall, and no characterizing an assumption as good, bad, conservative, aggressive, realistic or optimistic. It also, since nels#533, EXPLICITLY ALLOWS carrying over a value the user stated on an earlier turn of the conversation — and on a first-time create REQUIRES repeating the already-stated required fields — because the pre-#533 "never carry over" wording made a multi-turn create impossible: the model could not repeat country/birth_date/income across turns, the backend will not persist a partial profile, and the user was asked the same questions again and again. Stating a figure back is arithmetic; advising what to do about it is not, and `chat_set_retirement_profile`'s success log holds the same line — it echoes the full stored row so a substituted default is at least VISIBLE, but it does not label which values were defaulted and does not carry the "conventional planning figure" provenance string, which is #469's job on the projection screen. Its TWO additions beyond the stored row are the non-US note `RETIREMENT_NON_US_NOTE` — see the non-US bullet above — and, since nels#533, the stale-defaulted-age warning when a first-time create substituted a 65 target that is already behind the user (the same text REST carries as `RetirementProfileResponse.warning`). `chat_endpoint_routes_set_retirement_profile_and_asks_once_without_a_warning` drives the REAL `chat_endpoint` rather than the helper, so the `match effective_action` arm and the arm's placement in the offline if/else chain are actually executed; every other chat test here calls `chat_set_retirement_profile` directly, and without that one a chain reorder or a rename of the action string could ship with the feature unreachable from chat and the whole group still green. **The AC-6 interpretation, stated plainly**: `offline_retirement_action` ROUTES to the action but deliberately populates NO `action_params` — a keyword matcher has no conversational memory and must not guess a date of birth or an income — so the offline path can never write a row on its own; it always reprompts for the fields. "Chat arm + offline matcher + REST both write the same rows" is therefore satisfied by the ONLINE chat arm and REST sharing `upsert_profile`, with the offline matcher covering ROUTING only. Do not score that AC as unmet. The matcher also refuses interrogatives and the "what is my …" / "when can I …" forms BEFORE considering any phrase, because this action is a Pro-gated WRITE and routing a read question here would answer a question with a paywall message, and it refuses "save for" / "saving for" retirement, which is `CREATE_GOAL`'s phrasing. **Frontend — NOTHING in #465**: no Svelte component, no i18n key, no route. (#466 later added a `retirement` i18n namespace, still with no component consuming it — see §23.) The planner screen is #469, so after this issue the feature is reachable by chat and by REST only, not by clicking, and production verification is REST/chat-level rather than click-level. Two KNOWN GAPS, both deliberate: `employer_match_formula` is REST-only and NOT chat-settable in v1 — tiered formulas are a poor fit for free-text LLM extraction and getting them wrong biases the projection, so rule 21d tells the model not to attempt it and not to ask for match tiers; #469 will make it a form field. And there is NO UI to add a second household member, by design — see the `member_ordinal` bullet above.

### 22. Retirement Asset Ownership FK — `assets.owner_member_id` → `retirement_profiles` (#500)
- **The FK is COMPOSITE on `(user_id, owner_member_id)`, and the composite-ness is the entire point**: `backend/migrations/20260728174500_assets_owner_member_fk.sql` adds `assets_owner_member_same_user_fkey FOREIGN KEY (user_id, owner_member_id) REFERENCES retirement_profiles (user_id, id) ON DELETE SET NULL (owner_member_id)`. A bare `FOREIGN KEY (owner_member_id) REFERENCES retirement_profiles (id)` would prove only that SOME household member exists with that id — not that it is one of THIS asset's owner's members. Since `assets` is `user_id`-scoped and every read filters `WHERE user_id = $1` (§20), a row carrying user A's `user_id` beside user B's `owner_member_id` would be served to A faithfully while attributing A's balances to a member of B's household. The composite form makes that row unrepresentable. This is the identical failure §20's `assets_linked_account_same_user_fkey` closed for `linked_account_id`, and it is the same fix.
- **`owner_member_id` holds `retirement_profiles.id`, NOT `member_ordinal`, and the "composite vs. UUID" dilemma is a FALSE one**: it is tempting to reason that because `retirement_profiles` declares `UNIQUE (user_id, member_ordinal)`, a composite FK must target THAT key, and therefore that going composite means reinterpreting the column as an ordinal. PostgreSQL requires only that the referenced column list be covered by SOME unique index — not that it be the table's declared business key. So the migration adds `CREATE UNIQUE INDEX retirement_profiles_user_id_id_idx ON retirement_profiles (user_id, id)` and points the FK there, keeping the shipped `owner_member_id UUID` meaning intact. `id` is already the PRIMARY KEY, so that index can never reject a row the primary key accepts; it exists solely to make `(user_id, id)` referenceable. **`UNIQUE (user_id, member_ordinal)` is untouched and must stay that way** — it is a separate key for a separate purpose. #464 set the precedent with `linked_accounts_user_id_id_idx` in the very same migration as the FK that uses it.
- **`ON DELETE SET NULL (owner_member_id)`, and the alternatives were ruled out on evidence, not taste.** CASCADE would DESTROY a household member's assets — plus their `asset_holdings` and `asset_balance_history` — in response to what a user reads as an edit. **RESTRICT / NO ACTION would break account deletion unconditionally**: `account::delete_user_data` issues an explicit `DELETE FROM retirement_profiles WHERE user_id = $1` and then `DELETE FROM users`, and never deletes `assets` at all (it relies on the users cascade), so under RESTRICT that explicit statement raises 23503 for any user with a non-NULL `owner_member_id` and aborts the whole erasure transaction — GDPR deletion would fail for exactly the users who had used the household feature. Note a bare `DELETE FROM users` can SURVIVE RESTRICT by cascade-firing-order luck, so a test written that way proves nothing; `account_deletion_still_removes_assets_and_profiles_with_the_fk_in_place` therefore drives the real `delete_user_data`. SET NULL leaves the asset alive with `user_id` intact and `owner_member_id IS NULL` — the "not attributed to a household member" state every asset row is in today — so nothing is orphaned (`user_id` is the only column access control reads) and nothing is destroyed.
- **The COLUMN-LIST form is load-bearing**: plain `ON DELETE SET NULL` nulls EVERY column in the FK's local list, which here includes `user_id`; since `user_id` is NOT NULL, deleting a profile would abort with `null value in column "user_id" of relation "assets" violates not-null constraint` instead of unassigning the asset. `SET NULL (owner_member_id)` nulls only that column. Requires PG15+; prod and local dev are PG16. Same form and same reason as this table's `ON DELETE SET NULL (linked_account_id)`.
- **No backfill, and the column stays NULLABLE — there is nothing to backfill TO**: #465 creates no `retirement_profiles` row for any existing user (`GET` returns `200 null` for everyone), so a backfill would first have to INVENT a profile, i.e. invent `country`, `birth_date` and `current_gross_income` — the three fields #465 deliberately refuses to default because they cannot be supplied without fabricating a fact about the user. `NOT NULL` would also be wrong on the merits later: "an asset not yet attributed to a household member" is a legitimate reachable state in a two-member household. MATCH SIMPLE (PostgreSQL's default for multi-column FKs) skips the check entirely when any referenced column is NULL, which is why this constraint applies to the existing table without a single data repair.
- **The constraint is PROSPECTIVE, and that is deliberate**: `insert_asset` is the only writer and every call site passes `owner_member_id: None`, so until a write path sets it the FK can never fire in production. Landing it before the writer exists is far cheaper than discovering mis-attributed rows afterwards and repairing them. The user-visible surface after this issue is unchanged — this is a schema-integrity guarantee for the household work (#466 / #469), not a feature.
- **Why a THIRD migration at all** — see §20's `owner_member_id` bullet for the full reasoning; in short, sqlx sorts migrations by version rather than merge order, so on a fresh database #465's `20260728093000` runs BEFORE #464's `20260728163000`, and the FK can live in neither. `20260728174500` sorts strictly after both. **Do not edit any of the three migrations** — sqlx checksums applied migrations and an edit raises `VersionMismatch` on every existing database.

### 23. Retirement Social Security Input & Claiming-Age Adjustment (#466)
- **Nels does NOT estimate a Social Security benefit, and this is a binding product decision, not an implementation shortcut** (#454 decision 1). The user ENTERS the figure printed on their own SSA statement. The blocker is data, not math: AIME/PIA needs 35 years of indexed earnings, Plaid and Stripe FC return bank transactions rather than W-2 wage records, and SSA publishes no consumer data API — the only routes are the user typing 35 rows or uploading a statement we would have to parse. The statement already prints the answer at 62, at FRA and at 70. There is also a compliance argument: quoting SSA's own figure is defensible in a way that publishing a competing Nels estimate is not. What Nels builds is the DERIVATIVE — what that figure becomes at a different claiming age — because that is the part that moves when the user changes their mind. **The user supplies the anchor; we supply the slope.** If you are ever tempted to add an estimator, reverse the decision on #454 first.
- **`backend/src/social_security.rs` is a PURE module and its purity is structural** — it imports neither `axum` nor `sqlx`, so nothing in it can reach a pool or a clock. Every function takes its inputs and returns a value, which is what lets #467's projection engine call `claiming_adjustment` from inside a Monte Carlo loop without touching I/O, and what makes the whole module testable with no database.
- **TWO SSA step tables, and the second one is easy to miss.** `full_retirement_age(birth_year)` is the familiar one: 65y0m through 1937, rising two months per birth year to 65y10m for 1942, 66y0m for 1943-1954, rising two months per year to 66y10m for 1959, 67y0m from 1960. `delayed_credit_pct_per_year(birth_year)` is the one that gets hardcoded by mistake: **8%/yr applies only from 1943**, and earlier cohorts earn less, down to 3%/yr for 1924 and earlier. Hardcoding 8% overstates the benefit of delaying for every pre-1943 profile — a wrong number with no signal, which is the failure mode this whole feature area refuses to ship. A mutation test confirmed both tables are pinned: replacing the 1941-42 credit with 8.0 fails two tests, and shrinking the FRA ramp's range to exclusive is a COMPILE error because the match becomes non-exhaustive.
- **`fra_birth_year(birth_date)` exists because SSA's tables do not key on the calendar year.** "Born on January 1 counts as the previous year" applies to BOTH tables, so `claiming_adjustment` takes a `NaiveDate` and calls it internally rather than taking a bare `i32`. That is deliberate: a caller who has a date and passes `date.year()` into an `i32` parameter gets a silently wrong FRA for every 1 January birth, with nothing in the signature to warn them. Taking the date makes the mistake unrepresentable.
- **`adjustment_factor` CLAMPS at 70; `claiming_adjustment` REJECTS above it. Both are correct and they are not in conflict.** Nothing accrues past 70, so the FACTOR at 71 equals the factor at 70 — that is the statute. But a CALLER who says "I will claim at 71" has said something to query rather than silently reinterpret, so the public entry point returns an error. #466's acceptance criteria name both behaviours ("claim at 71 (clamps at 70)" and "rejected with a clear error, not clamped silently"); they are satisfied at the layer each belongs to. Do not "simplify" one into the other.
- **Ages are stored in MONTHS, never whole years, and each months column has an ANCHOR column beside it.** Months because FRA is 65y2m-65y10m for 1938-1942 and 66y2m-66y10m for 1955-1959 — ten cohorts whose FRA is not a whole number — and the FRA figure is the most prominent number on an SSA statement. A 1957 user forced to pick 66 or 67 misstates their implied PIA by about 3% in one direction or the other, silently and forever. The anchor (`'fra'` or `'explicit'`) because storing only the resolved month count loses WHY it has that value: `resolve_input` RE-DERIVES an `'fra'`-anchored age from the MERGED birth date on every write, so correcting a birth date moves it. Without that, a 1957 user who said "claim at my FRA" (798 months) and later fixed their birth date to 1960 would keep 798 while their FRA moved to 804 — so "at FRA" would quietly become "six months early", applying a 3.33% reduction they never asked for and flipping `adjustment_applied` to true for someone who requested no adjustment. Pinned by `an_fra_anchored_age_is_re_derived_when_the_birth_date_is_later_corrected` and its DB-backed sibling.
- **ABSENT IS NOT ZERO, all the way from the column to the wire.** `ss_monthly_benefit` is NULLABLE with no SQL DEFAULT, `Option<f64>` in Rust, and JSON `null` on the response; `SocialSecurityView.benefit_entered` is an explicit boolean so no consumer has to infer absence from a falsy value; and `adjusted_monthly_benefit` is `None` — never `Some(0.0)` — when any of benefit / quoted age / claiming age is missing. #469 renders the absent case as an explicitly labelled "not entered" segment of the stacked income bar, because a zero segment reads as "you get nothing", which is both alarming and wrong. `a_blank_benefit_serializes_as_null_and_is_distinguishable_from_an_entered_zero` asserts the two at the serialization boundary. Do not let `Option` collapse to `0.0` anywhere on this path.
- **NO INFLATION OR COLA ADJUSTMENT IS APPLIED TO THE SOCIAL SECURITY FIGURE, in either direction.** Everything else in the projection runs in today's dollars at a REAL return (§21). Social Security carries a STATUTORY COLA, so an SSA-statement figure is ALREADY in today's dollars: inflating it double-counts the COLA and overstates readiness, deflating it understates. Getting this wrong in either direction moves the headline materially and is a classic error. `claiming_adjustment` has no inflation parameter at all, and its doc comment carries the contract #467's own test should reference.
- **`SsAnchor` has a HAND-WRITTEN deserializer and must never become `#[serde(untagged)]`.** An untagged enum over `i32` and `String` gets both cases that matter wrong. `67.0` — routine LLM float-for-integer — matches neither variant and is a hard serde error inside `AiActionParams`, which discards the ENTIRE chat turn through the malformed-response fallback: exactly the defect §21's lenient deserializers exist to prevent, handed back on the newest fields. And `"67"` does NOT error — the `String` variant swallows it and it becomes the FRA anchor, so for a 1960 birth year "quoted at 62" silently becomes "quoted at FRA 67" and the entered benefit is divided by 1.0 instead of 0.70: a ~43% error in a dollar figure with no error anywhere. `de_lenient_ss_anchor` therefore parses NUMBERS FIRST and only then considers `"fra"`. **The 62-70 range check deliberately lives in `validate_profile`, NOT in the deserializer** — `75` must PARSE and then be rejected as a 400 naming the field and the range, because a range violation raised as a serde error throws the whole turn away and tells the user nothing.
- **No Social Security rule compares an age against the clock, and none may be added.** This is §21's froze-the-profile defect class avoided by construction: a `target_retirement_age <= current_age` rule re-evaluated on every write made a profile created legally at 64 permanently uneditable on its owner's 65th birthday. Claiming age has exactly that shape (62..70 against a birth date), so the bounds here are STATUTORY CONSTANTS rather than clock-dependent comparisons, and a 68-year-old who already claimed at 65 can record it. `a_stored_ss_claiming_age_never_becomes_invalid_merely_because_time_passed` and the DB-backed `a_profile_with_a_claiming_age_stays_editable_as_its_owner_ages_past_it` pin it.
- **`ss_source` is DERIVED, never settable, and exists to make a future estimator a CHECK widening.** v1 has exactly one legal value, `'user_entered'`, so a settable field would be noise now and a lie later; `resolve_input` sets it exactly when a benefit is present (the migration's `ss_source_pairing_check`). If Nels ever does compute its own figure, adding `'estimated'` costs one line rather than a migration on a table that by then has rows. Same TEXT+CHECK style as `linked_accounts.provider` and `assets.tax_treatment`.
- **`social_security_view` is the ONE constructor for the derived block**, called by the `GET` handler, the `PUT` handler AND the chat arm. That structural sharing is `upsert_profile`'s discipline applied to the READ side: there is no second copy of the FRA table or the renormalization to drift. It returns `None` for a profile outside `retirement_supported_country`, so a non-US user keeps every value they entered and never receives a US SSA full retirement age as though it were a fact about their pension — #454 decision 2's "no dial, no empty bar, no zeros" enforced at the API rather than left to the UI.
- **The response carries each fact under exactly ONE name.** The values the user ENTERED stay on the flattened row (`ss_monthly_benefit`, `ss_benefit_at_age_months`, `ss_claiming_age_months`, the anchors, `ss_source`); the DERIVED values live in the nested `social_security` object (FRA, the cohort credit, `adjusted_monthly_benefit`, `adjustment_applied`, `benefit_entered`). Nothing appears in both, and `social_security_derivations_are_nested_and_entered_values_are_not_duplicated` asserts the absence as hard as the presence — two spellings of one fact is how two consumers come to disagree about which is authoritative.
- **`adjustment_applied` means "Nels changed the number the user gave us", not "the number differs from the PIA".** A figure quoted at 62 and claimed at 62 sits 30% below the PIA and yet nothing was applied to it, so telling the user an adjustment was made would be false. #466's compliance rule keys its "we adjusted this" disclosure off exactly this flag, and the chat log and #469 must both show the ENTERED figure alongside the adjusted one — never the adjusted one alone, because the user did not produce it, will not recognise it, and cannot check it against their statement.
- **KNOWN GAP, deliberate and stated rather than discovered later: there is NO way to CLEAR a stored Social Security figure.** Merge semantics follow §21 exactly — absent OR explicit `null` means "leave the stored value alone" — which is right for #465's fields because every one of them always has a value, and is a real limitation for a genuinely optional one. After the first write neither REST nor chat can return a profile to "no benefit entered", so #466's absent state is reachable only before the first save. Correcting a wrong figure works fine; erasing it does not. If #469 needs the absent state to be reachable again, give the three SS fields explicit-null-clears semantics as a DOCUMENTED deviation from the sibling fields, and test it.
- **The ADD_TRANSACTION offline branch now yields to `offline_retirement_action`.** `msg_lower.contains("log") || contains("spent")` sits directly ABOVE the retirement arm in the offline if/else chain, so "log my social security benefit" was claimed there and invented a $15 "Utilities" transaction the user never made. The branch carries an `offline_retirement_action(&msg_lower).is_none()` guard, which subtracts only what the retirement matcher positively claims — retirement-profile wording and nothing else — so no real transaction phrasing loses its arm. `offline_retirement_action_does_not_collide_with_sibling_matchers` asserts the INLINE branches as well as the five helper matchers, because the inline ones are the broader risk.
- **The renormalization error is NOT swallowed, and `adjustment_applied` is gated on the adjusted figure EXISTING.** An earlier draft ended `claiming_adjustment` with `.ok()`, which produced the one state this feature must never reach: a response carrying `adjustment_applied: true` alongside `adjusted_monthly_benefit: null`, contradicting its own contract that where an adjustment was applied BOTH figures are shown — and making the chat arm tell a user who HAD supplied a claiming age to supply their claiming age. A stored row our own math refuses is OUR bug: it is logged at `error` level and flagged as `adjustment_unavailable` on the response, so `None` has exactly one meaning per flag. The flag is gated on `adjusted.is_some()` rather than on the two ages differing, because both ages with NO benefit is a legal half-entered state the migration explicitly permits, and it would otherwise claim Nels changed a number it was never given.
- **`SS_NEEDS_QUOTED_AGE` is the #300 routing marker for "which age is that figure quoted at?"** — the second exported constant of its kind after `MISSING_REQUIRED_FIELD_SUFFIX`, with exactly one producer, matched by `chat_set_retirement_profile`. That message is a CLARIFYING QUESTION, not a rejection: the user gave us something real and we need one more thing to use it. Returned down the error half it rendered as `**System Update:** ⚠️ …` on a turn where the user did nothing wrong. It is highly reachable rather than theoretical — rule 21d tells the model to populate only what the user stated, and the likeliest first utterance, "my statement says $2,400 a month", supplies the benefit alone. Note the consequence that IS kept: the write is still rejected in full, because `validate_profile` is total by design and a partial write would store a state no writer validated. Any new SS validation message that reads as a question needs the same treatment.
- **The Pro-gate failure path checks `status.is_server_error()` too.** `chat_set_retirement_profile` discarded the status from `require_caller_tier` and passed its message through verbatim, so any `subscriptions` query failure — pool exhaustion, a failover — rendered in conversation as `**System Update:** ⚠️ Internal server error`, quietly defeating the very rule this function's doc comment states. The 402 refusal IS written for the user and still passes through unchanged.
- **Validation messages name the PAYLOAD KEY, not just prose.** There are TWO Social Security age keys, and "the age your Social Security figure is quoted at must be between 62 and 70" leaves a REST caller to reverse-engineer which of `ss_benefit_at_age` / `ss_claiming_age` to fix. Every message names the key and the scale, per `validate_profile`'s own stated convention.
- **Surfacing**: REST — the SAME `GET` / `PUT /api/retirement/profile` as §21, no new endpoint. `PUT` accepts `ss_monthly_benefit` (MONTHLY dollars), `ss_benefit_at_age` and `ss_claiming_age` (each a whole age 62-70 or the string `"fra"`); it does NOT accept `ss_source`. Both responses gain the nested `social_security` object, `null` for a non-US profile. Chat — the SAME `SET_RETIREMENT_PROFILE` action as §21, no new action: prompt rule **21d** gains the three fields, their units, and an explicit prohibition on the model ESTIMATING a benefit — chat is where #454 decision 1 leaks, because a model asked "roughly how much will I get?" will produce a plausible dollar amount from its weights and the arm would then save it as a user-entered statement figure. The rule points at ssa.gov/myaccount instead and closes the ballpark loophole (`set_retirement_profile_rule_forbids_inventing_a_social_security_figure`). The chat success log states the ENTERED figure first and the adjusted one second, built from `social_security_view` rather than re-derived inline. `offline_retirement_action` claims "social security" phrasings while its existing `is_question` guard still lets "how much social security will i get" fall through rather than answering a question with a paywall. **Frontend — a `retirement` i18n namespace in all six locales, and NOTHING ELSE**: no Svelte component, no route, nothing rendered. The keys exist so the six files cannot drift before #469 consumes them, and `i18nLocales.test.js` gains `"retirement"` to `NAMESPACES` plus a `#466` parity block. The most important of them is `ssAdjustmentNote`, the one string carrying BOTH `{entered}` and `{adjusted}`: a translator who drops `{entered}` ships a locale showing only the adjusted number, which is precisely what the compliance section forbids, and the token-parity test is what catches it. **So after this issue the Social Security input is reachable by chat and by REST only, not by clicking, and there is still no planner screen and no projection** — the engine is #467 and the dashboard is #469.

### 25. Retirement Projection Engine (#467)
- **`backend/src/retirement_projection.rs` is PURE, and the purity is the design, not a preference.** It imports no `sqlx`, no `reqwest`, no `std::env` and no clock; the current date is `ProjectionRequest.today`. Callers assemble the request from DB rows and hand it over. Same discipline as `entitlement.rs` and `bank_provider.rs`. This is what makes a Monte Carlo testable at all: the sequence-risk assertion, the reproducibility assertion and every degenerate-input case are hand-built fixtures, impossible against a module that reaches for a pool. **Do not add an I/O call to this file.** The I/O half lives in `retirement.rs`, which is also the only place `Utc::now()` appears on this path.
- **The `retirement_projection.rs` / `retirement.rs` split.** `retirement.rs` owns the profile ROW, its validation and its two REST handlers; `retirement_projection.rs` owns the MATHS. They are separate files because the maths has no business knowing about `retirement_profiles` and the row has no business knowing about RMD tables. `build_projection_request` in `retirement.rs` is the ONE bridge, shared by `GET`, `POST` and the chat arm so all three project from identical inputs and cannot drift.
- **EVERYTHING IS IN TODAY'S DOLLARS AT A REAL RETURN.** There is no nominal path anywhere in the engine, and no inflation or COLA adjustment is applied to Social Security — §23's contract, which double-counts if broken in either direction. Do not add an inflation term to this module.
- **Bucket / sub-account model.** Three buckets mirror `assets::TaxTreatment`: `pre_tax`, `roth`, `taxable`, with `Hsa` and `Other` folded into `taxable` (v1 has no HSA withdrawal rule). `pre_tax` is internally two sub-accounts, `pre_tax_own` and `pre_tax_employer`, tracked from the first contribution to the last withdrawal — the OPENING pre-tax balance is entirely `own`, sim-time match dollars are entirely `employer`. The split exists because the stacked bar must separate "your savings" from "employer contributions" and **no post-hoc allocation can reconstruct it**.
- **RMDs are modelled and are the one tax rule that changes the SHAPE of the path.** Start age 73, or 75 for births from 1960, off a static Uniform Lifetime Table. Forced pre-tax withdrawals regardless of need can exhaust the pre-tax bucket earlier than a needs-driven model predicts, which is exactly why they are in v1 while brackets are not.
- **`TaxModel` is a STRUCT, not a trait**, holding one effective rate applied to pre-tax withdrawals. `tax_on_withdrawal(kind, amount, year)` carries a `_year` parameter that is UNUSED in v1 — it is the seam for a future bracket engine, so adding one does not touch call sites. Same closed-set discipline as `bank_provider::Provider`.
- **The `&[f64]` return-series seam is load-bearing.** One per-year real-return series spans the WHOLE horizon and is indexed from today, so the deterministic path and every Monte Carlo path share one loop and a test can hand-build a return sequence. Without it the sequence-risk test — a front-loaded bad decade must produce a strictly worse outcome than the same returns reversed — cannot be written, and a "Monte Carlo" that samples one average return per run is a sensitivity analysis wearing a costume.
- **Monte Carlo conventions.** Lognormal annual real returns, path-major draw order, seeded by `MC_DEFAULT_SEED` with `StdRng` — no `thread_rng`, no entropy, anywhere: same seed plus same inputs gives identical output forever. A single `MC_REAL_RETURN_STD_DEV = 0.1346` for the whole portfolio regardless of the user's actual allocation, sourced to the CFA Institute / Dimson-Marsh-Staunton 2023 US 60/40 real-return volatility. The seam stores RATES, so the lognormal MULTIPLIER is converted back with `exp(...) - 1.0` — storing the raw multiplier compounds the portfolio at ~104% a year instead of ~4%.
- **`MC_DEFAULT_PATHS = 1000` is MEASURED, not guessed** — see `tests::runtime_benchmarks`, an `#[ignore]`d release-build timing test. On the standard fixture: deterministic headline ~21 µs, Monte Carlo ~22 µs per path, so a full 1000-path run is ~22 ms. Below ~500 paths the deciles visibly move between seeds and the band would jitter as a slider moves; above ~2000 the recompute reads as lag. **The #469 recommendation this number exists to settle: recompute the deterministic headline LIVE on every slider input, and the BAND only on settle, debounced.** The two figures are three orders of magnitude apart and must not share a recompute strategy.
- **The headline is the SUSTAINABLE withdrawal, not the target.** `sustainable_annual_w` bisects over `w ∈ [0, w_max]` with a fixed `BISECTION_ITERATIONS = 40`, running the real decumulation with the trial `w` substituted for the target income — SS still offsets it, RMDs still forced. **This is why the dial can exceed 100%**: an over-funded plan sustains more than its target, and `percent_of_goal` is a FRACTION, never pre-multiplied, so `1.24` means 124%. `DEFAULT_W_MAX = 10_000_000.0` is a SEARCH bound, not a policy limit; a plan whose true sustainable withdrawal exceeded it would be silently CAPPED and under-reported, which is why it is set far above any realistic figure rather than near one.
- **`Projection` carries `assumptions`, and that is a compliance requirement, not garnish.** #454 requires every assumption to render on the same screen as the number. The engine hands them back so the UI cannot re-derive one and drift; `ProjectionAssumptions` echoes every request field plus the derived `current_age`, `rmd_start_age`, `mc_sigma`, the SS adjusted benefit and the floored claiming age actually used, `sustainable_annual_w`, the bisection count and `w_max`.
- **`is_finite()` is guarded FIRST for every float, never an ordered comparison** — the §20/#464 trap: `NaN <= 0.0` is false, so a bare magnitude check lets a NaN sail into the math and serialize as JSON `null`. The engine never emits NaN or Infinity and never panics. Degenerate inputs — no assets, retirement age already passed, life expectancy below retirement age, 100% Roth, zero income — are handled explicitly and tested.
- **REST**: `GET` / `POST /api/retirement/projection`, user-scoped with no `:budget_id`, mirroring `/api/retirement/profile`. Both Pro-gated via `require_caller_tier` — the CALLER's own tier, not `require_tier`, since no budget is in scope. Note the asymmetry with §21: reading your own PROFILE is deliberately ungated so a lapsed subscriber can still see their data, but a PROJECTION is the paid feature itself, so the `GET` is gated too. The gate runs BEFORE the profile load, so a free caller is refused without a DB read and is never told whether they have a profile. **`POST` merges `ProjectionOverrides` over the stored profile and PERSISTS NOTHING** — no row, no audit entry; a slider drag that rewrote the stored profile would be data loss dressed as a feature. Override validation is the engine's own `validate`, reached through `run_projection`, so there is no second copy of the range rules to drift.
- **The stored `employer_match_formula` is decoded STRICTLY, through `StoredEmployerMatch`.** §21's rule, now load-bearing for a computed number: under the lenient `EmployerMatch` a stored `{"annual_dollar_cap": 5000}` with `tiers` missing decodes cleanly to "no employer match" and the projection consumes it as fact, UNDERSTATING the user's income with no signal. A decode failure is a **500**. Do not copy the lenient `serde_json::from_value::<EmployerMatch>` fixture pattern here — that leniency is right for test fixtures and for the `POST` override body, which IS an input, and wrong for reading a stored row.
- **Closed assets are excluded and a missing balance falls back to holdings.** `assets.status` is `'active'`/`'closed'` and closing never deletes the row, so summing every row counts a rolled-over 401(k) twice and OVERSTATES readiness — the worst direction for this number to be wrong. `current_balance: None` means no balance was ever REPORTED, not a balance of zero, so those assets fall back to the sum of their holdings' market values.
- **Non-US profiles compute IDENTICALLY.** The engine has no country input; the RMD, SS and tax figures are the user's own entered numbers. `retirement_supported_country`'s `supported: false` is a #469 RENDERING gate, following §21's "the gate is a rendering gate, not a write gate" precedent. A `country = 'FR'` profile projects.
- **The profile has NO tax-rate column**, so `DEFAULT_EFFECTIVE_TAX_RATE = 0.15` supplies one. It is a documented planning convention, not tax advice and not a bracket calculation, surfaced through `assumptions.effective_tax_rate` and overridable on the `POST`.
- **Chat**: a new `RETIREMENT_PROJECTION` action — READ-ONLY, user-scoped, Pro-gated in `chat_retirement_projection`, and never write-gated (`chat_action_is_write_gated` must not cover it, same as `OPEN_INSIGHTS`). It writes no row and no audit entry, because nothing was mutated. **The arm REPLACES `response_text` with a backend-built card** rather than appending to it, which enforces prompt rule **21e** structurally: whatever the model wrote about these numbers never reaches the user. 21e's prohibitions mirror 21d's and matter more — 21d governs figures the USER supplied, 21e governs figures WE computed, and "you're behind, consider contributing more" attached to a projection is regulated investment advice. `build_projection_card_html` performs no escaping and needs none: every value in it is an engine `f64` or a heading spelled out in that function. **If a card ever renders user text, it must go through `budget::html_escape` first.** `ChatResponse.retirement_projection` carries the same projection as DATA so #469 renders the dial without re-parsing the card.
- **The offline forecast branch is REPOINTED for retirement phrasings.** `offline_retirement_projection_action` is deliberately NARROW and sits above the generic spending / save / forecast arms — "will my savings last" contains "save", and the forecast arm's canned reply is a fabricated "$100.00 left over" that has nothing to do with retirement. **The matcher delegates to `offline_retirement_action` and refuses anything that one claims**, rather than re-listing its keywords, so the write matcher keeps "retire at 62" and the read matcher keeps "retirement projection" with no phrase owned twice and no two lists to rot apart. It also refuses `save for`/`saving for` (CREATE_GOAL's), a BARE `projection`/`forecast` (the budget arm's), and interrogatives. `the_two_retirement_matchers_never_claim_the_same_phrase` asserts the partition as a property. Offline mocks the LLM, not the database, so the branch sets the real action and the real arm computes from real rows — it fabricates nothing.
- **Deliberate simplifications, documented rather than discovered later**: one volatility constant regardless of the user's actual allocation; `current_gross_income` held constant in real terms with no salary growth (conservative — never overstates readiness); HSA and Other folded into taxable; the sub-annual claiming-age precision floored to whole years, with the monthly SS figure staying exact and only the START year floored; `percent_of_goal` as a fraction.
- **Surfacing**: REST and chat only. There is still **no planner screen** — the dashboard is #469, which consumes `ChatResponse.retirement_projection` and the two endpoints. Nothing in this issue renders a pixel.
- **Frontend (#469) — the dashboard**: a dedicated `retirement` SPA route (`ROUTES` position 7, MainMenu PiggyBank entry, `open_retirement` auto-navigation) renders `RetirementView.svelte` composing the pure helpers in `frontend/src/lib/retirementView.js` (the only unit-tested part; the component is gated by `npm run build`). It hits `GET /retirement/profile`, `GET /assets`, `POST /retirement/projection` (ephemeral overrides via `buildProjectionOverrides`) and `PUT /retirement/profile` (via `buildProfileSaveBody`, which STRIPS `effective_tax_rate` — the profile has no tax-rate column). The four #454 compliance constraints are load-bearing in the SHAPE of the helpers and the markup: (1) the headline is the 10th-90th percentile band (`bandRange`), with the median and the percent-of-goal dial secondary inside the same card — `bandParts` returns a PAIR and returns null on NaN, `dialBand` maps the band onto the target using the engine's OWN `percent_of_goal` (never a re-derived target), and the dial's arc is clamped while `percentLabel` is not, so an over-funded plan reads 124%; (2) assumptions render AND are editable on the same screen — the read-only rows draw from the echoed `assumptions` struct, and four what-if sliders recompute via a trailing-edge `debounce` (150ms) keeping the last-good projection rendered and dimmed while in flight; (3) the fixed hypothetical-illustration disclosure renders directly under the band from `DISCLOSURE_KEY`/`SLIDER_DISCLOSURE_KEY`; (4) no recommendation is emitted anywhere — the non-US "register your interest" button is a `mailto:support@nels.money` fact-statement, not advice. `viewStateFor`'s ORDER is load-bearing: error (Pro-gate 402 → proRequired upgrade card) > noProfile > unsupported (full-page US-only, no dial/no empty bar/no zeros) > noAccounts (never a $0 projection) > loaded. The connect flow drives the #468 investments endpoints (`/investments/link-token` → Plaid Link modal → `/investments/complete` → a NON-dismissible classify `<dialog>` requiring per-account `asset_type`/`tax_treatment` before the `assets` row exists; classify is the ONLY consumer of `assetTypeLabelKey`/`taxTreatmentLabelKey`, whose unknown-value fallback keeps a widened CHECK from rendering a raw key). The stacked income bar uses `incomeSegments` so a missing Social Security figure renders as a labelled hatched/absent marker, never a $0 slice (#466). **Blocking AC: human sign-off on the disclosure copy and the band-first headline treatment was REQUIRED before ship — confirm with the user that `retirement.disclosure`/`sliderDisclosure` copy is accepted.**

### 26. Plaid Investments — Retirement Asset Linking (#468)
- **A dedicated investments-only Plaid Link, deliberately NOT a `bank_provider::Provider` variant, and NOT wired into chat**: `plaid_investments.rs` is a standalone module whose only Plaid products are `["investments"]` (Link token body literal, `country_codes: ["US"]`), a SEPARATE access token/Item from the #321 cash-flow Link. It does not extend `bank_provider::Provider` (§15) at all — that enum routes country → provider for budget-scoped cash-flow linking, and retirement assets are neither country-routed nor budget-scoped (§20's deliberate break, which this module is the first real consumer of). There is NO `rag.rs` chat arm and NO webhook in #468: the surface is REST-only and refresh is poll-driven (see below). The user flow is client-side Plaid Link modal → `public_token` exchange, exactly like #321, but with zero budget in scope.
- **User-scoped routes, NO `:budget_id`** — `POST /investments/link-token`, `POST /investments/complete`, `POST /investments/classify`, `GET /investments/accounts`, `POST /investments/accounts/:account_id/refresh`, `DELETE /investments/accounts/:account_id` (all auth-wrapped in `main.rs`, mirroring the `/api/assets` routing comment: retirement data belongs to a person, not a budget). - **The two-step "classify" is REQUIRED, and the `assets` row only appears on the second step**: completing the link writes ONLY the `linked_accounts` rows (access token encrypted via the cipher into `provider_ref`, `plaid_item_id` set, `institution_name` best-effort via `institutions/get_by_id`, failing soft with a `tracing::warn!`). A second call `POST /investments/classify {session_id, accounts: [{linked_account_id, asset_type, tax_treatment}]}` takes the user's enum choices per account and only then inserts the `assets` row (`assets::insert_asset`, `linked_account_id` set) AND runs the initial holdings sync. The enums are user-entered precisely because `assets.asset_type`/`tax_treatment` are NOT NULL and §20/§21 forbid deriving them from a vendor payload — Plaid's `accounts/get` does not know whether a brokerage is a Roth IRA. `complete_investment_link`'s doc comment is explicit: "Writes NO `assets` row — that is the classify step's job."
- **`classify_investment_accounts` requires a COMPLETED session, and does not consume it**: it re-fetches the session with `SELECT user_id FROM investment_link_sessions WHERE id=$1 AND status='completed'` — a fresh `pending` session 404s. That verification is existence+owner ONLY (the completed session may be reused across classify calls — this is pinned by tests), so it does not close any TOCTOU window; the atomic claim is entirely in `complete_investment_link`'s `UPDATE ... WHERE status='pending'` (same anti-replay shape as #321's `plaid_link_sessions`). Each classified account's asset row is guarded by the §20 composite same-user FK on `linked_account_id`, so a cross-user attempt surfaces as a 23503 you must handle deliberately rather than a 500.
- **`provider_account_id` is GLOBALLY unique and `ON CONFLICT (provider_account_id) DO UPDATE` never rewrites `user_id`** — the #468 test-infrastructure gotcha. The upsert (on `complete_investment_link`) preserves the ORIGINAL `user_id` of the first writer, so any test that reuses a `provider_account_id` across tests leaves a stale row keyed to the first test's user; a later test seeding the same id for a different user silently hits the conflict path and produces `(403, "This investment account does not belong to you")` on classify. Every test uses a DISTINCT id (`acc_atomic`/`acc_persist`/`acc_sessrej`/`acc_classify`/`acc_idem`/`acc_unclass`/`acc_refresh`/`acc_disc`/`acc_poll`). Do not "fix" the upsert to update `user_id` — that would rebind a live access token to whoever re-runs the link first (a real cross-user hijack vector); unique test ids are the intended contract.
- **Pro gating is `require_caller_tier` on THREE of the four write/read handlers — and disconnect is the deliberate exception**: `link-token`, `complete`, and `classify` are Pro-gated (the caller's own tier, no budget in scope, so `require_tier` cannot be used — same reasoning as §20's entitlement bullet). `GET /investments/accounts` is UNGATED (§14's precedent: a lapsed user must still be able to see their own data) and `DELETE` (disconnect) is UNGATED too. The scheduled poll (`poll_investment_accounts`, `main.rs` ticker alongside the GoCardless poll) selects accounts via `JOIN assets a ON a.linked_account_id = la.id AND a.user_id = la.user_id AND a.status='active'` — i.e. only CLASSIFIED accounts with a live asset — and short-circuits each account when the owner's `subscriptions.status` fails `user_is_pro` (a silent skip with a `tracing::info!`), so a subscription lapse PAUSES sync and never deletes data.
- **Disconnect is Item-wide, mirrors #321's ordering, and closes assets**: `disconnect_investment_account` calls Plaid `POST /item/remove` FIRST (the whole Item — a partial removal is impossible), then in one transaction flips EVERY `linked_accounts` row sharing the disconnected row's `plaid_item_id` to `status='disconnected'` AND sets those rows' `assets` rows to `status='closed'` (the §20/§25 closed-asset state the projection engine excludes). A failed Plaid call aborts before any local write, so a lapsed user can never be told their data is gone while Plaid still holds the Item.
- **`INVESTMENTS_POLL_INTERVAL_HOURS` (default 8, `.max(1)` floor) + `PLAID_API_BASE` (default `https://production.plaid.com`) are the two env seams** — both read through `plaid.rs`'s `env_opt`/`plaid_api_base` (both `pub(crate)`). The poll cadence mirrors GoCardless's (`GOCARDLESS_POLL_INTERVAL_HOURS`), and the base-URL seam mirrors `GITHUB_API_BASE`/`STRIPE_API_BASE`: tests point `PLAID_API_BASE` at a local wiremock, so every Plaid call in this module goes through `plaid_post` and is mockable. The root `.env.example` is the maintained source for these (backend/.env.example lacks the bank-linking blocks) — `INVESTMENTS_POLL_INTERVAL_HOURS=8` with a comment noting the same `PLAID_CLIENT_ID`/`PLAID_SECRET`/`PLAID_API_BASE` as §321, that the investments Link is US-only, and to leave `PLAID_API_BASE` unset in prod. **Do not "clean up" the poll's asymmetry**: unlike #321's Plaid cash-flow sync (webhook + manual), investments has no webhook at all and manual refresh is SYNCHRONOUS (`/investments/holdings/get` awaited inline) — the poll is the only background sync.
- **`sync_investment_holdings` writes through the §20 helpers and swallows nothing**: holdings (`/investments/holdings/get`, filtered per-account via `options.account_ids`) upsert securities into the shared `securities` cache with the `'plaid'` provider literal (key `(provider, provider_security_id)`, §20's `upsert_security`), then `assets::replace_holdings_for_asset` (returns `Option<()>` — `None` is a loud 403 denial, never `$0`), then `update_reported_balance` for the account's `balances.current`. Security types decode LENIENTLY through `SecurityType::from_db` because Plaid uses values beyond the CHECK (`"crypto"`, `"derivative"`, …) — the lenient read side §20 documented as intentional, bucket any unrecognised value into `Other` with a warn. A NON-FINITE reported balance is skipped with a `tracing::warn!` rather than written (the §20 `is_finite()`-first rule), and `as_of` prefers the per-holding `institution_price_as_of` date, falls back to the balance date, then to `Utc::now()`.
- **The test module drives the real handlers against wiremock and real Postgres**: link-token body is asserted to contain `"products": ["investments"]` and `"country_codes": ["US"]`; complete/classify/list/refresh/disconnect are exercised through axum `oneshot` harnesses with `PLAID_API_BASE` set to the mock. Because `complete_one` (the helper) is Pro-gated, tests that need a NON-Pro user's account (e.g. refresh-rejects-another-user) seed via the direct-SQL helpers `mk_direct_investment_setup`/`mk_direct_classified_setup` rather than the HTTP path; tests that complete a link FOR a Pro owner call `mk_pro_subscription` on that owner (status `'trialing'`, per the §21 gotcha — `'active'` fails safe to Basic in the test process). Run with `cargo test --bin backend plaid_investments -- --ignored`.
- **Surfacing**: REST only, user-scoped, no `:budget_id`, no chat, no frontend, no webhook — #468 is the ingestion half of the retirement epic; #469 (the dashboard) will be the first consumer of the `/assets` + `/retirement/projection` data it produces. After this issue, a Pro US user can link an investment account, classify it, and see it listed; the data is real but nothing renders it yet.

### 27. Model Providers & Bring-Your-Own-Key (nels-oss#3)
- **`backend/src/llm.rs` is the ONLY place that talks to a model API, and the only non-test code that reads `GEMINI_API_KEY`** (`llm::nels_gemini_key()`). It holds the `Provider` enum (`gemini` / `openai` / `anthropic`, the same three TEXT + CHECK literals used in the schema), one adapter per provider (`generate_json`, `generate_text`, `embed`, `validate_key`), credential resolution, and usage accounting. Chat, titles, suggested questions and embeddings in `rag.rs`, the report narrative in `reports.rs`, and the transaction embeddings in `budget.rs` and `backfill.rs` all call it; none of them builds a provider URL or reads a key. **Keys go in HEADERS, never URLs**: Gemini `x-goog-api-key` (never the `?key=` query parameter), OpenAI `Authorization: Bearer`, Anthropic `x-api-key` plus `anthropic-version: 2023-06-01`. A key in a URL leaks through `reqwest::Error`'s `Display`, so even with header auth every logged `reqwest::Error` goes through `.without_url()`. `LlmCredentials` has a hand-written `Debug` that prints `<redacted>` for the key, and its `api_key()` accessor is `pub(crate)`. Keys must never appear in logs, audit rows, `llm_usage`, API responses, `Debug` output or panics. Adapter timeouts: chat JSON 30s; title, suggested question and narrative 20s; embedding 20s; key validation 10s. Gemini reports a bad key as HTTP 400 with reason `API_KEY_INVALID` rather than 401, and that case is special-cased to `LlmError::Auth` so the save-time check and `last_error` work.
- **`llm::resolve_for_user(db, cipher, user_id)` decides which credentials a request uses, through the pure, unit-tested `resolve_from` decision table** (spec §5.1). No `user_ai_providers` row and `GEMINI_API_KEY` set → Nels-hosted Gemini (`KeySource::Nels`). No row and no key → `Resolved::Offline`, the existing offline router, where no data leaves the server. A row → that provider with the decrypted key (`KeySource::Byo`). An unrecognized stored provider or a key that fails to decrypt → `Err(KeyUnavailable)`. **A DB error on the lookup is NEVER read as "no row"**: it is also `Err(KeyUnavailable)`, because mapping it to Nels-hosted would silently send a BYO user's data to Google on Nels's key. Every `KeyUnavailable` also marks the row `last_error = 'key_unavailable'` (fail-safe, guarded write). **Resolve ONCE per request** and pass `&Resolved` down to every call it makes; do not re-resolve inside helpers, or one turn can mix two providers.
- **There is NO fallback from a BYO key, ever** (spec A8). A 401/403, 429, 5xx, timeout or `KeyUnavailable` on a user's key is never retried on Nels's key or on another provider. Silently re-routing to Google is exactly the data flow the user opted out of. The chat turn surfaces it as `ChatResponse.ai_provider_error`, which carries a stable error CODE from `LlmError::code()` (`auth_rejected` | `rate_limited` | `unavailable` | `key_unavailable`), not a provider name; the frontend turns the code into copy with a link to Settings. Title, suggested-question and narrative calls degrade quietly to their existing non-AI output (`fallback_title`, `DEFAULT_SUGGESTED_QUESTION`, `template_narrative`) and never surface an error. `llm::observe` keeps `user_ai_providers.last_error` in step for BYO calls only: an auth failure sets `'auth_rejected'`, a success clears it with a guarded `UPDATE … WHERE last_error IS NOT NULL` so a healthy turn adds no write, and transient errors leave it alone. `last_error` only ever holds `NULL`, `'auth_rejected'` or `'key_unavailable'` (a CHECK), never an upstream body.
- **Only Gemini embeds** (spec A6, `Provider::can_embed`, `Resolved::embedder`). Embeddings use `gemini-embedding-001` with `outputDimensionality: 768`, so Nels-hosted and BYO-Gemini vectors share one space with the existing `vector(768)` rows. **BYO OpenAI and Anthropic users get NO embeddings**: new rows store a NULL embedding, and semantic memory, `SEARCH_TRANSACTIONS` and embedding-based transaction lookup degrade exactly as they already do with no key. Anthropic has no embeddings API; OpenAI's vectors live in a different space and mixing them into one column would silently corrupt cosine search; and sending the text to Nels's Gemini would break the user's choice. Existing embeddings are left alone when a user switches provider (A7). `llm::embed_for` is best-effort and never errors. The backfill `backfill_transaction_embeddings` is a one-shot job spawned at boot, and only when `BACKFILL_TRANSACTION_EMBEDDINGS=1`; it is not on the hourly ticker. It resolves the BUDGET OWNER and carries a SQL pre-filter (`LEFT JOIN user_ai_providers p ON p.user_id = b.owner_id`) that selects only owners who can embed: no row while `GEMINI_API_KEY` is set, or a `provider = 'gemini'` row. BYO OpenAI and Anthropic owners' rows, which are NULL by design, are therefore never selected, never sent anywhere, and never counted as "remaining". `main.rs` runs the backfill whenever `BACKFILL_TRANSACTION_EMBEDDINGS=1`, with or without `GEMINI_API_KEY`, so BYO Gemini owners are backfilled even without a Nels key.
- **`llm_usage` gains `provider` and `key_source` (`'nels'` / `'byo'`)** so admins can tell Nels-paid tokens from user-paid ones. `llm::record_usage` is the one writer and stays fail-safe (a `warn`, never a broken chat path). **Report narratives are now recorded** as `call_type = 'narrative'`; before #3 they were the one call type recorded nowhere. Gemini keeps the historical `models/<id>` label in `llm_usage.model`; OpenAI and Anthropic store the bare model id. The two CHECKs are added `NOT VALID` in `20260925000000_user_ai_providers.sql` and validated in `20260925000100_validate_llm_usage_checks.sql`. The split is load-bearing: `llm_usage` is the highest-write table and migrations run automatically during rolling restarts; a plain `ADD CONSTRAINT … CHECK` would hold ACCESS EXCLUSIVE for a full-table scan, and sqlx wraps each migration in its own transaction, so a `VALIDATE` in the first file would still run under that lock. In its own migration it takes only SHARE UPDATE EXCLUSIVE, which does not block inserts. Do not merge the two files, and do not edit either (sqlx checksums applied migrations).
- **Storage and REST.** `user_ai_providers` holds one row per user who chose BYO (no row = Nels-hosted): `user_id` PK with `ON DELETE CASCADE`, `provider`, `encrypted_key` (a `SecretCipher` `encv1:` blob, the same AES-256-GCM cipher as TOTP secrets and bank tokens), `key_last4`, `last_verified_at`, `last_error`. The model is NOT stored; it resolves from env or the default at call time, so a server-wide model bump reaches everyone. Routes live in `ai_provider.rs`, user-scoped with no `:budget_id`: `GET /api/user/ai-provider` returns `{mode: "nels"|"byo"|"offline", provider, model, key_last4, last_verified_at, last_error, embeddings_enabled, available_providers}` and never the key. `PUT {provider, api_key}` trims the key, rejects an empty or over-512-character key and any provider not in `ENABLED_BYO_PROVIDERS` (400), enforces 10 validation attempts per user per rolling hour via `ai_key_validation_attempts` (429, failing closed on a DB error; rows older than an hour are purged by the hourly task), calls `llm::validate_key` (rejected key → 400, unreachable provider → 502), then encrypts, upserts, and writes a user-scoped `SET_AI_PROVIDER` audit row with the provider only. `DELETE` is idempotent (204) and writes `REMOVE_AI_PROVIDER` only when a row was actually removed. The account export includes an `ai_provider` block with provider, model, `key_last4` and timestamps, **never the key or its ciphertext**. Account deletion removes both tables through the `users` cascade. The Settings "AI provider" card is the frontend (copy in the `aiProvider` i18n namespace, all six locales).
- **The eval gate and `ENABLED_BYO_PROVIDERS`.** A provider is offered only after it passes the live eval (spec A16, §7): 53 fixtures in `backend/evals/chat_actions.jsonl` (at least one per chat action, plus `NONE` cases where the prompt says to ask instead of act), with one shared context in `backend/evals/context.json`, run through the real `build_system_instructions` and the real adapters by a manual, paid `#[ignore]` test, one provider at a time (`EVAL_PROVIDER`, `EVAL_API_KEY`), writing its results to `docs/evals/`. The bar is ≥95% JSON-parse rate and ≥90% action accuracy. The live eval does not run in CI (it costs money, needs secrets and is nondeterministic). `ENABLED_BYO_PROVIDERS` (comma-separated, case-insensitive, unknown values dropped) is what enforces the result: it drives `available_providers` and the PUT's provider check. **When unset or blank it defaults to all three providers**, so the production rollout MUST set it explicitly to the providers that passed; leaving it unset ships every provider regardless of its eval result. Removing a provider from the list stops new saves only: `resolve_from` does not consult the list, so users who already saved a key for that provider keep using it until they remove it. Setting the variable to nothing but unrecognized values offers no BYO providers at all.
- **Server-side BYO is NOT end-to-end encryption, and the product must never claim it is** (spec A1). The server still builds every prompt from plaintext database rows and forwards it; a user's own key changes WHICH provider account receives the prompt and under whose terms, not whether Nels sees the data. The privacy page (`marketing/src/routes/privacy/+page.svelte`) says exactly this. An end-to-end claim needs client-side chat (the later "local data" work), which will reuse these adapters. Do not write "end-to-end", "zero-knowledge" or "Nels can't see your data" copy on the strength of this feature.
- **Shared budgets, both directions (spec A10 and §8), a documented known limitation.** Request paths (chat, title, suggested question, report narrative, REST transaction create and update) resolve the AUTHENTICATED CALLER's provider; only the embedding backfill resolves the budget OWNER. So (1) a Nels-hosted collaborator chatting about an owner's BYO budget sends that budget's context to Google through Nels, even though the owner opted out of Google; and (2) a BYO collaborator chatting about someone else's budget sends the OWNER's budget context to a provider account the collaborator controls, under the collaborator's terms (low added risk, since the collaborator can already read that data). The privacy page and Settings disclosure say "chats about budgets shared with you use your provider choice". A per-budget AI policy owners can impose on collaborators is deferred (spec Q2).
- **Env vars** (all in the root `.env.example`, commented and unset). `GEMINI_API_BASE`, `OPENAI_API_BASE` (default `https://api.openai.com`) and `ANTHROPIC_API_BASE` (default `https://api.anthropic.com`) are test seams through `Provider::api_base()`: trimmed, a trailing `/` stripped, blank means the default, and they must stay unset in production. `LLM_MODEL_GEMINI`, `LLM_MODEL_OPENAI` and `LLM_MODEL_ANTHROPIC` override the server-wide model per provider (defaults `gemini-2.5-flash`, `gpt-4.1-mini`, `claude-haiku-4-5`; trimmed, blank means the default); a changed model should pass the eval gate before it ships. `ENABLED_BYO_PROVIDERS` is described above. Every test that mutates any of these holds `crate::rag::GEMINI_ENV_LOCK` (see §2).
- **Data-use disclosure.** The privacy page states that Nels-hosted chat goes to Google's Gemini API under Nels's PAID account (the production key is a Tier 2 Google AI Studio key with billing enabled, confirmed 2026-09-25, so Google's paid-service terms apply), quotes Google's current paid-service data-use and logging wording verbatim with a link to https://ai.google.dev/gemini-api/terms, and links OpenAI's data controls at https://developers.openai.com/api/docs/guides/your-data (the older policy URL returns 403). If the production key ever moves off billing, Google's unpaid-service terms apply instead and that copy becomes false; re-read the terms and update the page whenever Google revises them, quoting rather than paraphrasing.
