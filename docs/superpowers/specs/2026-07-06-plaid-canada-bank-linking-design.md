> (then-unmerged) `issue-320-gocardless-bank-account-data` branch, assuming Stripe (#303) and
> GoCardless (#320) were the only two prior providers. Before this branch's PR was opened, the
> maintainer merged #303, #320, #322 (Belvo/Mexico+Brazil), **and** #323 (Basiq/Australia +
> Akahu/New Zealand) into `main` — in two separate waves, the second (#322) landing mid-rebase
> after the first pass had already accounted for #303/#320/#323. This branch was rebased onto the
> final `main` and Plaid re-integrated as a **sixth** provider variant (not third) alongside
> Stripe/GoCardless/Belvo/Basiq/Akahu — the assumptions below are otherwise unchanged and still

## 1. Brief (verbatim from the ticket)

**As a** Nels Pro subscriber banking in Canada
**I want** to link my bank account via Plaid (covers ~99% of Canadian deposit accounts, including all Big 5 banks)
**So that** my transactions import automatically, matching the experience #303 provides for US subscribers via Stripe.

**Acceptance Criteria**
- A Pro subscriber with a bank account in Canada can start a Plaid Link session and link one or more accounts to a budget.
- A non-Pro user is blocked from starting the link flow and shown an upgrade prompt, same as #303.
- Linked accounts' transactions import into the existing `transactions` table, attributed to the user's active budget at import time, recording a `currency` of `CAD` on each imported row — no FX conversion; budget-level multi-currency handling is out of scope for this ticket.
- Transactions refresh automatically via Plaid's transactions webhook, plus a manual refresh action.
- A user can view linked accounts and disconnect one; disconnecting stops future imports without deleting previously-imported transactions, same as #303.
- Linking and "what's linked" status are reachable from the chat co-pilot, using Plaid Link's embeddable JS modal (similar integration shape to Stripe.js in #303).
- If a subscription lapses, automatic refresh stops for Plaid-linked accounts without deleting them, same as #303.

**Notes**: Prerequisite: this story implements Plaid against the `BankProvider`/`bank_linking.rs` interface #320 already introduced (`linked_accounts.provider`/`provider_account_id`, the `bank_provider::Provider` enum, `bank_linking.rs` dispatch) — it does NOT redo that generalization, it adds Plaid as a third provider variant alongside Stripe and GoCardless. Part of the multi-country bank-sync epic.

## 2. Assumptions

1. **Plaid as a third `Provider` variant, not a new abstraction.** `bank_provider::Provider` gains `Plaid` alongside `Stripe`/`GoCardless`; `for_country("CA") -> Some(Provider::Plaid)`; `supported_countries()` gains `("CA", "Canada")`. #320's own spec (Assumption 8 there) frames the enum-vs-`dyn`-trait choice as sized for "exactly two providers and no plan for a third in this ticket" — that framing is a documented judgment call for a FUTURE maintainer to weigh if a FOURTH provider ever appears, not a requirement THIS ticket must act on: the ticket explicitly instructs "add Plaid as a third provider variant... do not re-do that generalization work," not "generalize to a trait object." Each `match` in `bank_linking.rs` gains one `"plaid" => crate::plaid::*` arm; no interface reshaping.
2. **New module `backend/src/plaid.rs`**, mirroring `financial_connections.rs`'s/`gocardless.rs`'s "own HTTP client, own env-driven test seam" convention: JSON-bodied (Plaid's API takes `client_id`/`secret` as fields in every JSON request body, not a bearer token or per-session credential — simpler than GoCardless's cached-bearer-token layer, closer to Stripe's per-call secret-key usage). `PLAID_API_BASE` env var (default `https://production.plaid.com`; sandbox/CI point it at a local `wiremock` server), mirroring `STRIPE_API_BASE`/`GOCARDLESS_API_BASE`.
3. **Plaid Link is a client-side embeddable JS modal, like Stripe.js — but with one genuine wrinkle Stripe's FC modal doesn't have: Canada's Big 5 banks (RBC, TD, Scotiabank, BMO, CIBC) authenticate through Plaid's OAuth flow**, which can navigate the browser away to the bank's own OAuth/Interac login page and back, rather than resolving entirely inside the modal the way Stripe.js and most non-Big-5 Canadian institutions do. This is a Plaid/bank protocol requirement, not a design choice — the ticket's explicit "all Big 5" coverage makes this unavoidable, so the frontend must handle both cases:
   - Non-OAuth institution: `Plaid.create({...}).open()` resolves entirely in-modal, `onSuccess(public_token, metadata)` fires without navigation — behaves exactly like Stripe.js from the app's perspective.
   - OAuth institution (Big 5 + others): Link navigates the browser to the bank/Plaid OAuth page and back to a registered `redirect_uri` with an `oauth_state_id` query param. Per Plaid's documented pattern, the SAME `link_token` used to open the original Link session must be reused (Plaid does not allow creating a new token for this resumption) — Plaid recommends persisting it in `localStorage` before the navigation and re-invoking `Plaid.create({token: storedLinkToken, receivedRedirectUri: window.location.href}).open()` on return, which auto-resumes and fires `onSuccess` without user interaction. `PLAID_REDIRECT_URI` env defaults to `{APP_URL}/` (registered in the Plaid Dashboard) — reusing the SPA's existing root URL, exactly like #320's `bank_link_sessions` redirect handling reuses the root URL rather than standing up a dedicated callback route (Assumption 17 there).
4. **`link_token` creation is per-budget-linking-attempt, with a server-persisted pending-session row for anti-replay** — unlike Stripe (whose `client_secret` round-trips session identity via Stripe's own servers, verified against `account_holder.customer` at completion) and GoCardless (whose `bank_link_sessions` row is looked up by the `gc_ref` WE embed in the redirect URL), a Plaid `public_token` carries no recoverable `client_user_id`/budget binding at exchange time — nothing server-side otherwise stops a `public_token` obtained in one context from being exchanged against a different user's budget via `POST .../plaid/complete`. To close this the same way both sibling providers do (spec review finding), a new table `plaid_link_sessions` (`id UUID PRIMARY KEY`, `budget_id`, `user_id`, `status TEXT DEFAULT 'pending' CHECK (status IN ('pending','completed'))`, `created_at`) gets one row per `create_link_token` call. `POST /budgets/:id/plaid/link-token` (Pro-gated 402, Edit-or-Owner-gated 403, not-closed-gated 409 — mirrors `create_link_session`'s guard order `require_edit_or_owner` -> `require_pro` -> `ensure_not_closed` exactly) inserts this row, calls Plaid's `POST /link/token/create` (`client_id`, `secret`, `client_name`, `language: "en"`, `country_codes: ["CA"]`, `user: {client_user_id: <our user id as a string>}`, `products: ["transactions"]`, `webhook: "{APP_URL}/api/plaid/webhook"`, `redirect_uri: PLAID_REDIRECT_URI`; returns `{link_token, expiration}`, ~4h validity), and returns `{link_token, session_id: <the row's id>}` to the frontend — the frontend threads `session_id` back through both the in-modal and the OAuth-resumption paths (Assumption 3) and supplies it again at completion.
5. **Public-token exchange + account fetch happens server-side, exactly mirroring `complete_link_session`'s "never trust the client alone" posture, anti-replay included.** Frontend calls `POST /budgets/:id/plaid/complete` with `{session_id, public_token}` (Plaid's Link `onSuccess` callback's `metadata` is NOT trusted for institution/account labels — the plan pins re-deriving them server-side via `/accounts/get`/`/institutions/get_by_id`, same rationale as before). `complete_link_session` (same three gates as Assumption 4) looks up the `plaid_link_sessions` row by `session_id`: 404 if it doesn't exist, 403 if its `budget_id`/`user_id` don't match the caller's request (anti-replay — the actual fix for the gap above), 409 if `status != 'pending'` (no double-complete, mirrors GoCardless's requisition-session reuse guard). On success it exchanges `public_token` -> `{access_token, item_id}` via `POST /item/public_token/exchange`, calls `POST /accounts/get {access_token}` for the authoritative account list (id, name/official_name, mask, type/subtype) and `POST /institutions/get_by_id {institution_id, country_codes:["CA"]}` for the institution's display name, persists one `linked_accounts` row per Plaid account (mirrors the existing per-account row model: `provider_account_id` = Plaid `account_id`, globally unique per Plaid's docs; `provider_ref` = the Item's `access_token`, this module's "provider-side reference used for subsequent API calls," matching #320 Assumption 9's generalized meaning of that column — Stripe's is a Customer id, GoCardless's is a Requisition id, Plaid's is an access token; `institution_id` = Plaid's institution id, e.g. `ins_109508`; `country` = `'CA'`; `display_name`/`last4` from the account's `name`/`mask`), and flips the `plaid_link_sessions` row to `'completed'`.
6. **Two new nullable `linked_accounts` columns are needed that no existing provider's columns fit**: `plaid_item_id TEXT` (Plaid's `item_id` — the correlation key Plaid's webhook payloads carry; NOT the same value as `provider_account_id`, since a webhook fires per-Item, not per-account, and one Item can cover multiple linked accounts) and `plaid_cursor TEXT` (this row's own `/transactions/sync` cursor — see Assumption 7 for why it's per-row, not per-Item). Both always `NULL` for Stripe/GoCardless rows, following the exact precedent set by #320's GoCardless-only `iban`/`consent_expires_at` columns (always `NULL` for pre-#320 Stripe rows). `provider` CHECK widens to `('stripe', 'gocardless', 'plaid')`. The new `plaid_link_sessions` table (Assumption 4) is provider-scoped to Plaid only, mirroring how #320's `bank_link_sessions` table is scoped to GoCardless only.
7. **Per-account `/transactions/sync` cursor, not a per-Item table, at the cost of some redundant Plaid calls when one Item has multiple linked accounts.** Plaid's own transactions-sync model is per-Item (one cursor covers every account under that Item), but this codebase's sync abstraction (`bank_linking::sync`, mirroring both `financial_connections::sync_account_transactions` and `gocardless::sync_account_transactions`) is per-`linked_accounts`-row. Rather than introduce a new Item-level table purely for Plaid, `plaid::sync_account_transactions(pool, linked_account)` calls `/transactions/sync` using **that row's own** `plaid_cursor`, filters the returned `added`/`modified` transactions to `account_id == linked_account.provider_account_id`, and advances **that row's own** `plaid_cursor` to the response's `next_cursor` — discarding (not persisting) any sibling account's transactions in the same page. If a budget links N accounts under one Item, one webhook delivery triggers N independent `/transactions/sync` calls (each redundant over the same underlying delta), rather than 1. This is a documented, bounded v1 inefficiency (not a correctness bug — idempotent `ON CONFLICT DO NOTHING` on `(external_account_id, provider_transaction_id)` means no double-import is possible even with redundant fetches), mirroring the "documented v1 limitation, no data loss" precedent set by #320 Assumption 11's IBAN-reconciliation fallback. Typical linking sessions (1-3 accounts per bank) keep the redundancy negligible in practice.
8. **Categorization reuses the existing description-substring heuristic, not Plaid's own category field.** Plaid's transaction object carries `personal_finance_category` (unlike Stripe FC's transaction shape, which #303 Assumption 7 notes has none) — but this codebase's `categories` are user-defined free-text names (e.g. "Groceries", "Netflix") with no defined mapping to Plaid's fixed taxonomy (e.g. `FOOD_AND_DRINK_GROCERIES`). Building that mapping is out of scope for v1 (mirrors #303 Assumption 7's explicit non-goal: "a smarter categorizer is an explicit non-goal for v1"). `plaid::sync_account_transactions` calls the SAME `financial_connections::guess_category_id(description, categories)` pure function (widened from `pub(crate)` — already `pub(crate)`, so no visibility change needed) against Plaid's `name` field, exactly as GoCardless does against its own description field.
9. **Amount normalization is its own pure function, not shared** (mirrors #320 Assumption 20's reasoning for GoCardless): Plaid's `amount` is a **decimal float already in major currency units** (e.g. `12.34`, not cents, and not a string) with a sign convention where **positive = money leaving the account (a debit/expense) and negative = money coming in (a credit/deposit)** — the OPPOSITE sign convention from how most people intuitively read "positive," but explicit and documented in Plaid's API reference. Since this codebase always stores `transactions.amount` as an unsigned magnitude (`amount.abs()`, matching #303/#320's own normalization contract), `plaid::normalize_amount(amount: f64) -> f64` is `amount.abs()` — trivial, but kept as its own named, unit-tested pure function (not reusing `financial_connections::normalize_amount`, which takes integer cents) so the "Plaid's amount is already float-major-units, not integer-cents" distinction is visible at the type/signature level, not just in a comment.
10. **Currency is hardcoded to `'CAD'` for Plaid imports, matching the AC's explicit "no FX conversion" requirement** — mirrors #303's Stripe path hardcoding `'USD'` (Assumption 9 there: "Stripe FC in this codebase is US-only, so hardcoding is a correct, not guessed, value"). Plaid's transaction object DOES carry its own `iso_currency_code` field; using the AC's explicit `CAD` literal rather than trusting that field is a deliberate choice — this integration is scoped to Canada only (Plaid country_codes always `["CA"]`), so the two should always agree, and hardcoding avoids a `NULL` currency on the rare row where Plaid returns `iso_currency_code: null` (its documented behavor for certain unsettled/foreign-currency edge cases) and keeps this path's behavior as unconditional as Stripe's.
11. **Plaid webhooks are JWT-signed (ES256/JWK), not HMAC like Stripe's — this requires a real crypto-verifying dependency, not a hand-rolled check.** Every existing provider integration in this codebase hand-rolls its signature verification (`billing::verify_stripe_signature` via `hmac`+`sha2`) rather than pulling in a crate, but that precedent is specifically about **symmetric HMAC**, which is simple and safe to hand-roll. Plaid's webhook verification is **asymmetric** (a JWT in the `Plaid-Verification` header, signed with ES256 over a P-256 elliptic curve, with the signing key fetched on demand via `POST /webhook_verification_key/get {key_id}` — extracted from the JWT header's own `kid` claim before verification, then cached in-process, matching #320 Assumption 2's cached-token precedent — Plaid states these keys rotate infrequently and recommends caching for up to 24 hours) — hand-rolling ECDSA signature verification is a materially different (and materially riskier to get subtly wrong) undertaking than HMAC, so this ticket adds the `jsonwebtoken` crate (a well-maintained, widely used dependency with built-in `DecodingKey::from_ec_components` support for exactly this JWK shape) rather than hand-rolling P-256 ECDSA. This is a deliberate, documented exception to the "no `async-stripe`, no external SDKs" house style, scoped narrowly to signature verification. Verification steps: decode the JWT header (unverified) for `kid` and confirm `alg == "ES256"`; fetch/cache the JWK for that `kid`; verify the JWT signature using `jsonwebtoken::decode` with a `DecodingKey` built from the JWK's `x`/`y` coordinates; check the JWT's `iat` claim is within 5 minutes of now (reject stale/replayed payloads); compute SHA256 of the **raw** request body (so the handler takes `Bytes`, not `Json<_>`, exactly like `billing::webhook`/`financial_connections::webhook`) and compare its hex encoding to the JWT payload's `request_body_sha256` claim.
12. **Plaid webhook payload dispatch**: `POST /api/plaid/webhook` is PUBLIC (mounted outside the auth nest, alongside `billing::webhook`/`financial_connections::webhook`) with its own env credentials (Plaid webhook verification needs no separate secret beyond `PLAID_CLIENT_ID`/`PLAID_SECRET`, already required for all Plaid calls — the `webhook_verification_key/get` call is authenticated the same way as every other Plaid API call). The handler parses `{webhook_type, webhook_code, item_id, ...}` and dispatches:
    - `webhook_type: "TRANSACTIONS"`, `webhook_code` in `{"SYNC_UPDATES_AVAILABLE", "DEFAULT_UPDATE", "INITIAL_UPDATE", "HISTORICAL_UPDATE"}` -> look up every `active` `linked_accounts` row with this `plaid_item_id` whose owner is still Pro (mirrors the Stripe webhook's per-account `status == 'active' AND user_is_pro` gate exactly, just applied per-row across however many rows share the Item) and call `bank_linking::sync` (== `plaid::sync_account_transactions`) on each; a lapsed-Pro or non-active row is a silent no-op (200, no Plaid retry), same as Stripe.
    - `webhook_type: "ITEM"`, `webhook_code: "ERROR"` with `error.error_code == "ITEM_LOGIN_REQUIRED"` -> this is Plaid's analogue of GoCardless's PSD2 consent expiry (the bank requires the user to re-authenticate) — flip every `linked_accounts` row with this `plaid_item_id` to `status = 'consent_expired'` (the SAME status value #320 introduced, reused rather than adding a Plaid-specific one, since the UX meaning — "reconnect this account" — is identical). `LIST_LINKED_ACCOUNTS`/the frontend badge/manual-refresh's short-circuit all already handle `consent_expired` generically from #320 with zero Plaid-specific code, by construction (they operate on `linked_accounts.status`, not on `provider`).
    - Any other `webhook_type`/`webhook_code` -> logged at `debug`, 200 (ignored), mirroring `map_fc_webhook_event`'s `None` arm.
13. **Manual refresh calls `/transactions/sync` directly (not "request a refresh, wait for a webhook" like Stripe's `.../refresh` endpoint)** — Plaid's API has no separate "please check now" endpoint the way Stripe FC does; `/transactions/sync` IS the pull, synchronous and immediate. So `plaid::refresh_linked_account` (called by both REST manual-refresh and the chat `REFRESH_BANK_ACCOUNT` arm via `bank_linking::refresh_linked_account`) directly awaits `sync_account_transactions` and returns once it completes, rather than firing an async request and relying on a later webhook — this is a real behavioral difference from Stripe/GoCardless's "kick off, webhook/poll delivers later" shape, called out explicitly here and in the plan/AGENTS.md so it doesn't read as an oversight. It is still Pro-gated (402) and short-circuits with a clear "reconnect it" message on a `consent_expired` row without calling Plaid at all, mirroring GoCardless's manual-refresh guard (Assumption 10 there) exactly.
14. **Disconnect calls Plaid's `/item/remove` (not a per-account call — it revokes the whole Item, all accounts under it) BEFORE flipping the local row(s) to `disconnected`.** Mirrors #303's "call the provider first, then flip locally" ordering. Because one Item can back multiple `linked_accounts` rows (Assumption 7), disconnecting ANY one of the sibling rows removes the whole Item on Plaid's side (Plaid does not support partial-Item removal), so `plaid::disconnect_linked_account` flips **every** `linked_accounts` row sharing that row's `plaid_item_id` to `disconnected`, not just the one the caller targeted — this is called out explicitly in the UI copy (`linkedAccounts.disconnectPlaidSiblingsNote`) and in the plan, since silently leaving sibling rows "active" pointing at a now-revoked access_token would make their next sync attempt fail with a confusing Plaid error rather than an expected, already-surfaced "disconnected" state. NOT Pro-gated (view + disconnect stay ungated for a lapsed user, same as every other provider).
15. **Chat surface**: `LINK_BANK_ACCOUNT`'s existing `country` param now also accepts `"CA"`, resolving to `Provider::Plaid` via `bank_provider::Provider::for_country`. Unlike GoCardless, Plaid needs no `institution_query` — Plaid Link's own in-modal search UI handles institution selection, so the chat flow only needs the country. `ChatResponse` gains two new fields: `plaid_link_token: Option<String>` and `plaid_link_session_id: Option<Uuid>` (the `plaid_link_sessions.id` from Assumption 4 — the frontend must round-trip this back to `/plaid/complete`, same as the REST-button flow), both set only when `LINK_BANK_ACCOUNT` resolves to `Provider::Plaid` (alongside the existing `financial_connections_client_secret` for Stripe and `bank_link_redirect_url` for GoCardless) — the frontend opens the SAME Plaid Link modal this token would drive from the REST-button flow (mirrors how `financial_connections_client_secret` shares `startLinkFlow` between the chat and REST call sites). The system prompt (rule 2o) is extended to name Canada (Plaid) alongside the existing 9 countries; no new clarifying-question shape is needed since Plaid requires no institution name upfront.
16. **REST surfacing**: `POST /api/budgets/:id/plaid/link-token` (create a Link token + `plaid_link_sessions` row; Pro+Edit-or-Owner+not-closed-gated, mirrors `POST .../linked-accounts/session`; returns `{link_token, session_id}`) and `POST /api/budgets/:id/plaid/complete` (`{session_id, public_token}` -> anti-replay check against the session row, exchange, persist accounts; same gates, mirrors `POST .../linked-accounts/complete` and GoCardless's `.../gocardless/complete`). The already-shared, provider-agnostic `GET .../linked-accounts`, `POST .../linked-accounts/:id/refresh`, `DELETE .../linked-accounts/:id` (all going through `bank_linking::*` since #320) need ZERO changes — this is the entire point of #320's dispatch layer, and this ticket's success criteria include confirming that stays true.
17. **No marketing site changes** — authenticated-app feature only, same as #303/#320.
18. **Plaid sandbox/test seam**: `PLAID_API_BASE` (Assumption 2) lets integration tests point at a local `wiremock` server, mirroring `STRIPE_API_BASE`/`GOCARDLESS_API_BASE` exactly, so `plaid.rs`'s `#[ignore]` DB+HTTP integration tests follow the identical pattern as `financial_connections.rs`'s and `gocardless.rs`'s own suites.
19. **Frontend Plaid Link script loading mirrors the `loadStripe`-injection pattern for testability.** There is no ESM npm package equivalent to `@stripe/stripe-js` for vanilla (non-React) Plaid Link — Plaid ships a CDN script (`https://cdn.plaid.com/link/v2/stable/link-initialize.js`) that defines a global `Plaid.create(...)`. `linkedAccounts.js` exports a small `loadPlaidLink()` helper that dynamically injects that `<script>` tag (idempotent — a second call resolves immediately if `window.Plaid` already exists) and resolves to `window.Plaid`; the actual link-driving function (`startPlaidLinkFlow`) takes an **injected** `loadPlaidLink` parameter (default `loadPlaidLink` itself, overridable in tests), exactly mirroring `startLinkFlow`'s injected `loadStripe` parameter, so tests supply a fake `{create: () => ({open: ...})}` without touching a real script tag or network call.

## 3. Goal & Success Criteria

Pro subscribers with a Canadian bank account can link one or more accounts via Plaid Link (covering ~99% of Canadian deposit accounts, including Big 5 OAuth institutions), with transactions landing in the existing `transactions` table tagged `currency = 'CAD'` (no FX conversion). Auto-refresh happens via Plaid's transactions webhook (with manual refresh also available), Plaid's `ITEM_LOGIN_REQUIRED` error state maps onto the existing `consent_expired` UX #320 introduced, and view/disconnect/chat-reachability match #303/#320's established UX. Plaid is added as a third `bank_provider::Provider` variant with matching `bank_linking.rs` dispatch arms — `rag.rs`, the REST list/refresh/disconnect handlers, and the frontend's account list require ZERO Plaid-specific branching beyond what #320's dispatch layer already provides, except at the point of starting a brand-new link (same documented exception #320 already carries for GoCardless).

Success criteria:
- [ ] A Pro user in Canada can complete an end-to-end link (Link token -> Plaid Link modal, including a Big-5 OAuth-redirect institution -> `onSuccess` -> server-side exchange+persist) via REST, and the resulting account(s) appear via chat's `LIST_LINKED_ACCOUNTS` indistinguishably from a Stripe/GoCardless-linked account (same response shape, `provider: "plaid"`).
- [ ] A non-Pro user's attempt to start a Plaid link (REST or chat) is rejected with a clear upgrade prompt and makes zero Plaid API calls.
- [ ] A verified Plaid `TRANSACTIONS` webhook triggers an idempotent sync for every active, Pro-owned `linked_accounts` row sharing the notified `item_id`; an unverified/invalid-signature webhook is rejected (400) before any DB access.
- [ ] A Plaid `ITEM_LOGIN_REQUIRED` error webhook flips every `linked_accounts` row sharing that `item_id` to `consent_expired`, surfaced by `LIST_LINKED_ACCOUNTS`/the frontend badge exactly as #320's GoCardless consent-expiry is, with zero Plaid-specific code in those shared paths.
- [ ] Manual refresh on an active Plaid account performs an immediate `/transactions/sync` and returns newly imported rows synchronously (not "kicked off, arrives later" like Stripe/GoCardless); manual refresh on a `consent_expired` Plaid account short-circuits with a clear reconnect message and makes zero Plaid calls.
- [ ] Disconnecting one Plaid-linked account calls `/item/remove` once and flips every sibling `linked_accounts` row sharing that Item's `plaid_item_id` to `disconnected`, preserving all their historical transactions.
- [ ] A `public_token` exchange attempted with a `session_id` whose `budget_id`/`user_id` don't match the calling user is rejected (403) before any Plaid call is made; re-using an already-`completed` `session_id` is rejected (409).
- [ ] Existing #303/#320 Stripe and GoCardless tests all still pass, with one explicit, narrow exception: `bank_provider.rs`'s `parse_rejects_unknown` (currently asserts `Provider::parse("plaid") == None`) and `supported_countries_lists_all_nine` (currently asserts exactly 9 entries) are UPDATED, not left unchanged, since Plaid is now a real, parseable provider and a 10th supported country — every other existing test in both suites passes unchanged. Plaid is additive to `bank_provider::Provider`/`bank_linking.rs` beyond that.
- [ ] All new pure logic (amount normalization, currency hardcoding, JWT/JWK webhook-signature verification's pure pieces, `for_country("CA")`) is unit tested; DB/HTTP-touching flows have `#[ignore]`+`wiremock` integration tests mirroring `financial_connections.rs`'s/`gocardless.rs`'s existing style.

## 4. Scope

**In scope**: migration adding `'plaid'` to the `linked_accounts.provider` CHECK, `plaid_item_id`/`plaid_cursor` columns, and the new `plaid_link_sessions` table; `backend/src/plaid.rs` (Plaid HTTP integration: link-token creation, public-token exchange with anti-replay, accounts/institution fetch, `/transactions/sync`-based sync with per-row cursor, refresh, disconnect via `/item/remove`, webhook JWT/JWK verification + dispatch); `backend/src/bank_provider.rs` (add `Provider::Plaid`, `for_country("CA")`, `supported_countries()` entry); `backend/src/bank_linking.rs` (add Plaid dispatch arms to `refresh_linked_account`/`disconnect_linked_account`); `backend/src/rag.rs` (`LINK_BANK_ACCOUNT`'s new `Provider::Plaid` arm, new `ChatResponse.plaid_link_token`/`plaid_link_session_id`, system prompt rule 2o naming Canada); `backend/src/main.rs` (new Plaid REST routes + public webhook route + env); `Cargo.toml` (add `jsonwebtoken`); `.env.example`; frontend (`linkedAccounts.js` Plaid functions + `loadPlaidLink` script-loader, `LinkedAccounts.svelte` "Canada" option + Plaid Link invocation + OAuth-redirect resumption, `App.svelte` OAuth-redirect-return handling + chat `plaid_link_token` handling, i18n strings); `AGENTS.md` new §16; tests throughout.

**Out of scope**: any country beyond Canada for Plaid (the US stays on Stripe per the existing architecture — this ticket does not migrate US linking to Plaid even though Plaid also covers the US); mapping Plaid's `personal_finance_category` onto user categories (reuses the existing substring heuristic, Assumption 8); consolidating multi-account-per-Item sync into a single per-Item cursor/call (Assumption 7's documented v1 redundancy); FX conversion or multi-currency aggregation/display; a generic `dyn BankProvider` trait-object refactor (explicitly deferred by #320 and by this ticket's own instructions); admin console changes; marketing site changes.

## 5. Architecture

**New module**: `backend/src/plaid.rs` — mirrors `financial_connections.rs`'s/`gocardless.rs`'s internal shape (module-local `reqwest` client, `env_opt`/`plaid_api_base` test seam, `require_edit_or_owner`/`require_pro` guards). ## 6. Error Handling & Edge Cases

- Unsupported country for Plaid's own coverage is not this ticket's concern (Plaid Link itself only offers Canadian institutions since `country_codes: ["CA"]`) — a caller from an unsupported country never reaches `plaid.rs` at all (`bank_provider::Provider::for_country` returns `None`/routes elsewhere first).
- Link-token creation failure (Plaid API/network error) -> 502, logged, mirrors `stripe_post`'s `BAD_GATEWAY` convention.
- `complete_link_session` with a `public_token` that fails to exchange (expired/already-used/invalid) -> 502 (via the shared `plaid_post` helper's `BAD_GATEWAY` convention, matching `financial_connections.rs`/`gocardless.rs`'s analogous failures) with Plaid's error surfaced generically ("Could not complete bank linking — please try again"), no partial `linked_accounts` row persisted.
- `complete_link_session` with a `session_id` that doesn't exist -> 404; one that exists but whose `budget_id`/`user_id` don't match the caller -> 403 (anti-replay, Assumption 5); one already `status = 'completed'` -> 409 (no double-complete) — all three checked BEFORE any Plaid call is made.
- Plaid account already linked to a different budget -> 409, mirrors #303's exact `existing_budget_id != budget_id` guard (Assumption 5 reuses that check verbatim, generalized to any provider — it's already provider-agnostic since it queries `linked_accounts` by `provider_account_id` regardless of `provider`).
- Invalid/missing `Plaid-Verification` webhook header or JWT verification failure (bad signature, stale `iat`, body-hash mismatch) -> 400, before any DB access, mirrors `financial_connections::webhook`'s `verify_stripe_signature` failure path.
- Webhook for an unknown `item_id` (no matching `linked_accounts` row) -> logged at `warn`, 200 (Plaid should not retry indefinitely for data we don't have).
- Manual refresh / disconnect on a nonexistent/foreign account id -> 404, same as every existing provider.
- Manual refresh on a `consent_expired` Plaid account -> 409 with a clear "reconnect it" message, zero Plaid calls, mirrors GoCardless exactly.
- Closed budget -> every mutating path (link-token creation, complete, manual refresh, webhook-driven sync) no-ops/rejects, mirroring #303/#320's closed-budget guard exactly (`ensure_not_closed` on the two REST-invoked paths; the closed-budget check inside `sync_account_transactions` itself for the webhook-invoked path, identical to `financial_connections::sync_account_transactions`'s own internal check).
- Plaid rate-limit (HTTP 429) during a webhook-triggered sync -> logged, that row's `plaid_cursor` NOT advanced (so the next webhook/manual refresh retries from the same position), no retry-storm.
- A Plaid Item shared by multiple `linked_accounts` rows where disconnect is called on one -> ALL sibling rows flip to `disconnected` (Assumption 14), not just the targeted one — covered by an explicit integration test, not just documented prose.

## 7. Testing Approach

- Unit tests (no DB/HTTP): `Provider::for_country("CA")`/`parse("plaid")`/`supported_countries()` includes Canada; `plaid::normalize_amount` (abs-value, sign-flip cases); JWT-verification's pure pieces (body-hash comparison, `iat`-staleness check, JWK `x`/`y` -> `DecodingKey` construction) with a hand-built test JWT/keypair (mirrors `billing::verify_stripe_signature`'s existing unit-test style of constructing a valid signature offline and asserting both accept and tamper-reject cases); offline chat-router "canada"/"ca" phrase recognition.
- `#[ignore]`+`wiremock` DB-integration tests, mirroring `financial_connections.rs`'s/`gocardless.rs`'s existing suites: Pro-gate rejection (zero Plaid calls made), full link->sync happy path, idempotent re-sync via cursor advancement, webhook dispatch to every sibling row sharing an `item_id`, `ITEM_LOGIN_REQUIRED` flipping every sibling row to `consent_expired`, disconnect flipping every sibling row + calling `/item/remove` exactly once, closed-budget guards on every mutating path, already-linked-to-a-different-budget 409, `plaid_link_sessions` anti-replay (mismatched `budget_id`/`user_id` -> 403, already-`completed` -> 409, unknown `session_id` -> 404 — all before any Plaid call).
- A migration-only smoke: run the new migration against a #320-seeded DB, confirm existing Stripe/GoCardless rows read back unaffected (`plaid_item_id`/`plaid_cursor` both `NULL`) and a `provider = 'plaid'` row can be inserted.
- Frontend: `linkedAccounts.test.js` gains Plaid link-token/complete/OAuth-resumption cases (with `loadPlaidLink` and Plaid Link's `create`/`open` injected, mirroring the existing `loadStripe`-injection tests); component test for the Canada option in `LinkedAccounts.svelte` and the OAuth-redirect-return flow in `App.svelte`.

## 8. Risks & Open Questions

- **The per-account `/transactions/sync` cursor (Assumption 7) makes redundant Plaid API calls when one Item backs multiple linked accounts** — bounded and documented, not a correctness risk (idempotent inserts prevent duplication), but a maintainer revisiting this for API-quota reasons at higher account-per-Item volumes may want to introduce a per-Item table later.
- **OAuth-redirect resumption (Assumption 3) depends on `localStorage` surviving the round-trip to the bank's OAuth page and back** — a user who clears storage or uses a private/incognito window mid-flow will need to restart linking from scratch (Plaid does not support resuming with a stale/lost `link_token` past its ~4h expiration either way); this is a known Plaid Link constraint across all integrators, not specific to this implementation.
- **`jsonwebtoken` is a new dependency**, a deliberate, narrow exception to this codebase's hand-rolled-crypto house style (Assumption 11) — justified by ES256/ECDSA verification being materially riskier to hand-roll correctly than the HMAC every other webhook here uses.
- **Sandbox Plaid behavior may differ from documented production behavior** for OAuth flows and `ITEM_LOGIN_REQUIRED` triggering — the `wiremock`-based tests validate this codebase's own handling of documented response/webhook shapes, not live sandbox parity (same caveat #303's and #320's specs each carry for their own providers).
- **`provider_ref` stores Plaid's raw `access_token` in plaintext** (Assumption 5) — Plaid's own guidance treats an access token as a longer-lived, more sensitive secret than Stripe's Customer id or GoCardless's Requisition id (closer to a password than an opaque reference). This inherits #320's existing plaintext-`TEXT`-column design for `provider_ref` (Stripe's Customer id and GoCardless's Requisition id sit in the same unencrypted column today) rather than introducing new encryption-at-rest machinery scoped to one provider — not a regression this ticket introduces, but worth flagging for a future encryption-at-rest pass across all three providers' `provider_ref` values.
- **Disconnecting one account in a shared Item silently affects its siblings (Assumption 14)** — surfaced via UI copy and covered by a test, but a user who links 3 accounts from the same bank and disconnects "just one" via chat's fuzzy `account_match` may be surprised all 3 stop syncing; this is a genuine Plaid platform constraint (no partial-Item removal), not a gap in this implementation.
