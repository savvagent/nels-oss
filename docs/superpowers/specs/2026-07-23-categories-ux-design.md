# Categories UX Rebuild — Design (#426)

## 1. Brief (verbatim from the issue)

**Title:** Redesign the categories UX: replace the server-rendered table with a manageable budget-health view

**Problem (quoted):** `frontend/src/lib/CategoriesView.svelte` is 91 lines that fetch `GET /budgets/:id/categories-table` and drop the response into `{@html}`. Every visual and structural decision lives in Rust, in `build_categories_table_html` (`backend/src/budget.rs:5413`). Consequences: (1) the page is a read-only printout — no create/rename/re-limit/toggle/delete; (2) no visual budget health; (3) rich per-category state (`is_fund`/`fund_balance` #228, `rollover_enabled` #49, `linked_budget_id` #52) is flattened or dropped; (4) money is whole-dollar and currency-blind (`money()` at `backend/src/budget.rs:5352`); (5) the page can't participate in the design system; (6) it is visibly out of step with Transactions (#403/#407). No search, sort, filtering, drill-in, or useful empty state.

**Acceptance criteria (verbatim):**
- [ ] `CategoriesView.svelte` renders from JSON data, not `{@html}`; the server-rendered HTML table path is retired or explicitly retained only where chat still needs it, with that decision written down.
- [ ] Amounts render in the budget's real currency with cents via a shared frontend formatter — no hard-coded `$`, no whole-dollar rounding.
- [ ] Every category row shows a progress meter plus remaining, with distinct healthy / near-limit / over-limit treatment that is not conveyed by color alone.
- [ ] Fund (#228), rollover (#49), and rollup-mirror (#52) categories are visually distinguishable, and their special semantics (fund balance, carried amount, linked budget) are readable on the row.
- [ ] Income / Savings / Expense grouping is preserved with per-group totals and a top-level expense rollup summary.
- [ ] Instant search plus filter chips (at least Over limit, No limit, Funds) with live counts.
- [ ] A category's name and limit can be edited, and rollover/fund toggled, from this page; permission checks and audit logging are preserved, and non-editor viewers get a read-only view.
- [ ] i18n keys added for every new string in all six locales (en, de, es, fr, it, pt).
- [ ] Chat-driven reachability is preserved: the `LIST_CATEGORIES` intent and the `/categories-list` command still land on this view and it still self-fetches for the active budget, including on a chat-driven budget switch.
- [ ] Gates: helper-level TDD in a `categoriesView.test.js` (pure helpers only — no Svelte component tests) plus a clean `npm run build`; `cargo test --bin backend` if the API changes.

## 2. Assumptions (decisions made without asking)

| # | Assumption | Rationale |
|---|---|---|
| A1 | **Keep `GET /budgets/:id/categories-table` and `build_categories_table_html`; add a NEW sibling JSON endpoint `GET /budgets/:id/categories-view`.** | `build_categories_table_html` is NOT dead: `rag.rs:4025` (LIST_CATEGORIES) and `rag.rs:4068` (CATEGORY_BALANCE single-category chat bubble) both call it, and `App.svelte` renders `msg.categories_table_html` via `{@html}`. The HTML path must survive. The `/categories-table` **route** becomes unused by the frontend but is retained one release as stale-service-worker insurance (this is a PWA; an old cached client hitting a removed route would 404 into an error state). Marked deprecated in a comment. This satisfies the AC's "retained only where chat still needs it, with that decision written down." |
| A2 | **The `.cat-table` `:global()` CSS in `App.svelte` (block starts at line 2969) STAYS.** | It styles the chat-bubble `{@html}` table (`msg.categories_table_html`), not just `CategoriesView`. Deleting it would silently break the CATEGORY_BALANCE bubble. |
| A3 | **Endpoint name is `/budgets/:id/categories-view`, not `/categories`.** | `GET /budgets/:id/categories` already exists (`list_categories` → `Vec<CategoryResponse>`) and is consumed elsewhere. A new name avoids a breaking change to an existing contract. |
| A4 | **Reuse `budget::category_table_rows` as the data source.** | It already resolves #52 rollup mirrors to their source budget's real limit/spend (`resolve_linked_source_totals_and_spend`), windows spend to the current period, and excludes `excluded_from_budget` transactions. Re-deriving that in a new query would risk divergence between the chat table and the new view. |
| A5 | **Currency: `budgets` has NO currency column** (only `transactions.currency`, nullable, added by the GoCardless migration). The endpoint returns a budget-level `currency` resolved as the **modal (most frequent) non-NULL `transactions.currency`** for that budget, else `null`. | The AC's "budget's real currency" has no schema backing; adding a `budgets.currency` column is scope creep with a migration and a backfill question. This is a **variant of** — not identical to — the precedent in `transactionsView.js:244-253`, which picks the *first non-excluded row's* currency per group; modal is the stabler choice for a whole-budget rollup. One cheap scalar query, and `null` → the shared formatter's USD default. |
| A6 | **Formatting moves to the frontend via `formatAmount(amount, currency)`, reused from `transactionsView.js`.** | It already does locale-aware `Intl.NumberFormat` with cents and a bad-code fallback. The real defect is Rust string-concatenating `$` with whole-dollar rounding; moving to `Intl` fixes symbol, placement, grouping, and cents in one step. The helper is **moved to `frontend/src/lib/money.js`** and re-exported so transactions and categories share one implementation rather than duplicating it. |
| A7 | **Fund toggle IS in scope and gets a REST write path.** The enable path is **already** a shared helper — `rag.rs::enable_category_fund` (`rag.rs:5643`), called by BOTH `chat_set_category_fund` AND `chat_create_categories` per #228 §5.5. The work is therefore: **move** `enable_category_fund` to `budget.rs` (unchanged behavior), **add** a sibling `disable_category_fund` extracted from the inline disable branch in `chat_set_category_fund`, repoint **both** existing rag.rs callers, and call them from `update_category`. | AGENTS.md §12's "no REST-write path" records #228's scope boundary, not a permanent prohibition; the AC explicitly asks for the toggle. Moving to `budget.rs` avoids a `budget → rag` back-reference (rag already depends on budget). **Correcting an earlier misreading:** enable does NOT unconditionally zero the balance — it is `fund_balance = CASE WHEN fund_advanced_through IS NULL THEN 0 ELSE fund_balance END` (zero only if the category was NEVER a fund; a re-enable resumes from the preserved balance), guarded by `WHERE id = $2 AND is_fund = FALSE` for idempotency. That behavior must be preserved verbatim. |
| A8 | **Editing uses the EXISTING `PUT /budgets/:id/categories/:cid` (`update_category`)** for name, limit, and rollover. Only `PUT` is routed (`main.rs:291` — `put(update_category).delete(delete_category)`); there is no PATCH route, so no client may call one. | Already supports `name`, `category_type`, `category_limit`, `rollover_enabled` via `COALESCE`; already enforces Owner-or-Edit permission, `ensure_not_closed`, mirror rejection (409), and unique-name violation (409). No new endpoint needed for those three. |
| A9 | **Rollup mirror rows are NOT editable from the page** — they render with a `Rollup` badge, the source budget's name, and a disabled/absent edit affordance. | `update_category` already 409s on a mirror with a specific message. Surfacing an edit control that always fails is a worse UX than not offering it. |
| A10 | **Category create and delete ARE in scope** via the existing `create_category` / `delete_category` REST handlers. Note: REST `create_category` does **not** accept `is_fund` (only chat `CREATE_CATEGORY` does, via `AiCategorySpec.is_fund`), so creating a fund from this page is a two-step create-then-toggle. Not an AC requirement; recorded so it isn't "discovered" mid-implementation and fixed by scope creep. | The issue's "the one screen dedicated to categories is the one place you can't manage them" is the core complaint; edit-only would leave it half-solved. Both handlers already exist with permission + closed-budget guards. |
| A11 | **Read-only when `activeBudget.permission_level === "view"`, or when the budget is closed (`closed_at != null`).** | Mirrors the backend guards exactly (`perm != Owner && perm != Edit` → 403; `ensure_not_closed` → 409). Hiding controls the server will reject is the correct client mirror. `permission_level` is already on `activeBudget` (a `BudgetListItem` from `/budgets`). |
| A12 | **"Near limit" threshold is ≥ 80% of the effective limit and < 100%.** | Conventional budgeting default; no repo precedent found. Encoded as a single named constant in the helper module so it is trivially tunable. |
| A13 | **Meters measure spend against the EFFECTIVE limit**, where effective = base + carried, and **carried follows the fund-over-rollover precedence rule**: if the category is a fund → `carried = fund_balance` (and `prev_period_spent = 0`); else if it is a non-mirror expense category → `carried = category_carried(...)` (#49); else `carried = 0`. Fund and #49 carry are **never stacked**. | Showing progress against the bare `category_limit` would contradict the "Remaining" figure on the same row and misreport every fund. The precedence rule is copied from `category_response_with_carry` (`budget.rs:3348-3357`), which documents it as anti-double-counting. **Correcting an earlier claim:** this does NOT match `build_categories_table_html`, whose `push_category_row` uses `fund_effective_limit` only and ignores #49 carry entirely. The new view is therefore deliberately *more* accurate than the chat table for a rollover category; see Risk 5. |
| A17 | **Carry needs a data source `category_table_rows` does not provide.** The endpoint additionally fetches the budget's `rollover_enabled`/`budget_type`, computes previous-period windows, and calls the existing batched `budget::period_category_expense_spent_many` (`budget.rs:1663`) for per-category `prev_period_spent` — no N+1. The (prev, carried) selection in `category_response_with_carry` is **extracted into a pure `budget::category_carry_for(...)` helper** used by BOTH that function and the new endpoint. | The AC requires "carried amount" readable on the row, but `CategoryTableRow` has no carry field and `category_table_rows` never computes one. Extracting the selection rather than reimplementing it guarantees `/categories` (REST) and `/categories-view` can never disagree about a category's effective amount. |
| A14 | **No new design tokens, palette, or font.** The rebuild uses the app's existing daisyUI v5 theme + Inter. | `ui-ux-pro-max --design-system` proposed a fresh indigo/violet palette and Cormorant Garamond — appropriate for a greenfield product, wrong for an established app with a shipped theme. Its *applicable* output (density 8 spacing, subtle 150–300ms motion, the pre-delivery a11y checklist) IS adopted. |
| A15 | **Income/Savings/Expense grouping always renders as groups, including the single-type case.** | `build_categories_table_html` deliberately flattens to a generic table when only one `category_type` is present, because four generic columns had to serve all three semantics. A card layout has no shared column header to compromise, so the reason for the special case disappears. The AC asks for grouping to be "preserved"; always-group is the simpler invariant. |
| A16 | **The `/categories-view` endpoint is additive; no migration.** | Every field it returns already exists in `categories`/`budgets`/`transactions`. |

## 3. Goal & Success Criteria

Replace the server-rendered categories printout with a Svelte-native, mobile-first budget-health view that shows at a glance which categories are healthy, tight, or over — and lets an editor fix a limit, rename, toggle rollover/fund, add, or delete without leaving the page.

Measurable:
1. `CategoriesView.svelte` contains no `{@html}` and no call to `/categories-table`.
2. Every category row renders a meter with an accessible name and `aria-valuenow/min/max`, plus an icon **and** text status — over-limit is never signalled by hue alone.
3. Amounts render with cents and a locale-correct currency symbol from one shared formatter used by both transactions and categories.
4. Fund, rollover, and rollup-mirror rows are distinguishable at a glance and readable in their own terms (balance / carried / source budget).
5. An editor can complete rename, re-limit, rollover toggle, fund toggle, create, and delete from the page; a viewer sees none of those controls and a closed budget disables them.
6. The rebuilt component keeps the `$effect(() => { activeBudget; load(); })` self-fetch and the in-flight `budgetId` capture-and-compare guard, so `LIST_CATEGORIES` / `/categories-list` still land here and a chat-driven budget switch still refreshes (AC 9).
7. `pnpm test` (vitest) and `pnpm run build` pass in `/frontend`; `cargo test --bin backend` passes in `/backend`.

## 4. Scope

**In:** new JSON endpoint; `category_carry_for` extraction; fund enable/disable helper move + repointing both rag.rs callers; `is_fund` on `CategoryUpdatePayload`; shared money formatter; `categoriesView.js` pure helpers + tests; full `CategoriesView.svelte` rebuild (meters, groups, badges, search, 5 chips, summary); row editor (name/limit/rollover/fund); create; delete; read-only + closed-budget states; i18n across 6 locales; AGENTS.md update.

**Out (explicit non-goals):** custom category ordering / drag-to-reorder; bulk create; redesigning the budget-level rollover master switch; swipe gestures; a `budgets.currency` column; changing `build_categories_table_html` or the chat bubble's appearance; category drill-in to a filtered transactions list (deferred — it needs a transactions-view filter contract that does not exist yet); editing rollup mirrors.

## 5. Architecture

### Backend (`/backend`)

1. **`budget::category_carry_for(...) -> (prev_spent, carried)`** — pure helper extracted from `category_response_with_carry` (`budget.rs:3348-3357`), encoding the fund-over-rollover precedence. Called by `category_response_with_carry` (behavior unchanged) and by the new endpoint. Unit-tested.
2. **`CategoryViewRow` + `CategoriesViewResponse` (`budget.rs`)** — per row: everything `CategoryTableRow` carries, plus `carried_amount`, `prev_period_spent`, `effective_limit` (= base + carried), `linked_budget_name: Option<String>`, `is_mirror`. Envelope: `currency: Option<String>`, `time_frame`, `closed_at`, `permission_level`.
3. **`GET /api/budgets/:id/categories-view`** — `check_permission` → 403 on `Permission::None`. Composes: (a) `category_table_rows` (current-period spend + #52 mirror resolution); (b) one query for the budget's `rollover_enabled`/`budget_type`/`time_frame`; (c) `previous_period_window(time_frame, now)` (`budget.rs:911`) + `period_category_expense_spent_many` (`budget.rs:1663`) for `prev_period_spent`. **Call shape (important):** that helper takes a slice of **`(budget_id, start, end)`** tuples — NOT per-category windows — and returns a map **keyed by category id**. Pass a single-element slice `&[(budget_id, prev_start, prev_end)]`, exactly as `update_category` already does at `budget.rs:3476`. Building a per-category window vector would silently mis-join; (d) `category_carry_for` per row; (e) one batched query for mirror source names; (f) one scalar query for modal currency.
4. **Fund toggle plumbing** — **move** `enable_category_fund` from `rag.rs:5643` to `budget.rs` verbatim; **add** `disable_category_fund` extracted from the inline disable branch in `chat_set_category_fund`; repoint the **two** existing callers (`chat_set_category_fund`, `chat_create_categories`); call both from `update_category`. Both helpers take a generic `sqlx::Executor` rather than `&AppState`, so they run either against the pool (the two chat callers, unchanged) or inside a caller's transaction (see 5).
5. **`CategoryUpdatePayload.is_fund: Option<bool>`** — additive; `None` = unchanged (existing callers unaffected). Reject non-expense categories with a 400 before writing, mirroring the `categories_is_fund_expense_only_check` data-layer constraint, and reject mirrors (the existing mirror 409 already covers this path). **`update_category` is ATOMIC**: the fund disable, the main UPDATE, the fund enable and the reconciling re-read all run in ONE `state.db.begin()` transaction. This is required, not optional, because the editor sends `name` and `is_fund` in the same request — without it, a rename onto a taken name returns 409 from the main UPDATE with the disable already committed, leaving the fund switched off and its accrual stopped while the client is told only that the name was taken. The pre-write validation and the disable-before-UPDATE / enable-after-UPDATE ordering are still required on top of the transaction: `categories_is_fund_expense_only_check` is IMMEDIATE, so a bad order fails inside the transaction too, just with a less actionable status.

### Frontend (`/frontend`)

6. **`lib/money.js`** — becomes the single home of `formatAmount(amount, currency)` (moved from `transactionsView.js`, which re-exports it for its existing importers). `fmtMoney` retained for the status strip.
7. **`lib/categoriesView.js` (pure, unit-tested)** — `meterPercent(spent, effectiveLimit)`, `healthStatus(spent, effectiveLimit)` → `"none" | "healthy" | "near" | "over"` (with `NEAR_LIMIT_THRESHOLD = 0.8`), `groupCategories(rows)` → ordered Income/Savings/Expense groups with per-group totals, `filterCategories(rows, {query, chip})`, `chipCounts(rows)`, `expenseSummary(rows)`. Note `effective_limit` arrives **from the server** (A17) — the frontend does not recompute carry.
8. **`lib/CategoriesView.svelte`** — rebuilt. Header + summary meter; search input; sticky filter chips with counts; grouped sections with sticky headers and group totals; rows as `rounded-xl` cards with name, badges, meter, `spent of limit`, remaining; tap-to-edit opening a daisyUI `modal` bottom-sheet editor; add-category button; delete with confirm; skeleton loading; empty/zero states; error alert.

**Filter chip set — `All` plus five filters, every chip showing a live count:** `All` · `Over limit` · `Near limit` · `No limit` · `Funds` · `Rollover`. (The AC floor is three — Over limit, No limit, Funds; the issue's design brief asks for five. Shipping the full set since `healthStatus` already computes `"near"` and `rollover_enabled` is on the row.)

### Design direction (from `ui-ux-pro-max`, applicable subset)

- **Density 8** — dense/dashboard spacing (8–32px), matching the transactions list's rhythm.
- **Motion subtle** — 150–300ms transitions on meters and chips; **must** respect `prefers-reduced-motion`.
- **Never color alone (High severity)** — every status carries a lucide icon + a text label alongside the hue.
- **Contrast ≥ 4.5:1** in both daisyUI light and dark themes.
- **Touch ≥ 44×44px with ≥ 8px gaps** for every control.
- **Feedback** — skeleton/spinner beyond 300ms; every mutation shows pending → success/error.
- **Inline validation on blur** in the editor (name non-empty, limit numeric ≥ 0).
- **Sticky headers must not obscure content** — same `sticky top-0 z-10 bg-base-200/95 backdrop-blur` treatment transactions uses.
- **SVG icons only** (`lucide-svelte`, already a dependency) — no emoji.

## 6. Error Handling & Edge Cases

| Case | Behavior |
|---|---|
| No active budget | Existing `commands.noActiveBudget` line (unchanged). |
| Budget with zero categories | Empty state + an "add your first category" CTA for editors. |
| Category with `category_limit = NULL` | No meter; explicit "no limit — tracking only" text; counted in the `No limit` chip; excluded from group/summary limit totals but its spend still counts. |
| **NULL-limit FUND** (reachable — no constraint requires a fund to have a limit) | **The NULL-limit rule wins over A13**: `category_limit IS NULL` → no meter, regardless of `fund_balance`. A meter needs a denominator; `0 + fund_balance` is a balance, not a limit. The fund badge and balance still render. |
| **Clearing a limit is NOT possible** | `update_category` uses `category_limit = COALESCE($3, category_limit)`, so `null` means "unchanged", not "clear". The editor can set or change a limit but cannot move a category back to unlimited. Recorded (not fixed) — changing it would need a sentinel or a nullable-aware payload, which is out of scope. |
| Fund with negative effective limit | `fund_effective_limit` has no floor; meter clamps to 100% and status is `over`; the signed amount still renders correctly. |
| Rollup mirror | `Rollup` badge + source budget name; no edit/delete controls (A9). |
| Archived rollup source | `category_table_rows` already resolves it to 0 — renders as a $0 mirror; no special-casing added. |
| Closed budget | All mutation controls disabled with an explanatory tooltip (mirrors `ensure_not_closed`'s 409). |
| Viewer permission | Read-only; no editor, add, or delete affordances. |
| Rename collision | `update_category` returns 409; surfaced as an inline field error, not a toast. |
| Stale response race | Keep the existing `budgetId` capture-and-compare guard from the current `load()`. |
| Mutation failure | Row reverts to server state; error surfaced inline; no optimistic-write left stranded. |
| Non-expense fund attempt | 400 from the backend; the toggle is only rendered for expense categories anyway. |

## 7. Testing Approach

- **Backend:** pure unit tests for `category_carry_for` (fund precedence beats #49; mirror → 0; non-expense → 0; rollover off → 0; overspend clamps to 0 via `category_carried`). `#[ignore]`d DB-backed tests for the fund helpers' marker/balance semantics on enable / disable / re-enable-preserves-balance, and for `/categories-view` (carry present, mirror resolution, modal currency, permission 403) — consistent with the existing `#[ignore]` integration-test convention. Run: `cargo test --bin backend` (bin-only crate — never `--lib`); the `#[ignore]`d tests need local pgvector on port 6153 via `podman-compose up -d`.
- **Regression net for the fund-helper move:** the existing `#[ignore]`d fund tests around `rag.rs:14670` and `rag.rs:14962` (including re-enable-preserves-balance) must still pass unchanged — that is what makes "zero behavior change" verifiable rather than asserted.
- **Frontend:** TDD on `categoriesView.js` helpers — grouping order and totals, meter percent clamping (0, >100, null limit, negative effective), threshold boundaries at exactly 0.8 and 1.0, chip counts, search matching, expense summary excluding income/savings. **No Svelte component tests** (vitest runs node-env here). Run: `pnpm test`, then `pnpm run build`. The 6-locale i18n AC is **not** gated automatically: `frontend/src/lib/i18nLocales.test.js` enforces parity **per namespace, opt-in**, via one `describe` block per feature (`linkedAccounts`, `auth`, `chat`, `transactions` — there is no `categories` block today). This work must **add** a `describe("i18n categories key parity (#426)")` block with a required-key list plus the `Object.keys(...).sort()` equality check, following the `transactions` (#403) block verbatim. Without it, a key added to `en.json` alone would ship silently.
- **Manual:** load the page against a local backend with a fund, a rollover category, a rollup mirror, an unlimited category, and an over-limit category.

## 8. Risks & Open Questions

1. **The fund-toggle move is the highest-risk change** — it touches the #228 idempotency contract (`fund_advanced_through`) and has TWO pre-existing callers that #228 §5.5 deliberately unified. Mitigation: move `enable_category_fund` with **zero** behavior change (same SQL, same `is_fund = FALSE` guard, same `CASE WHEN fund_advanced_through IS NULL` balance rule), repoint both callers in the same commit, unit-test the helper, leave the hourly `advance_fund_categories` job untouched. **Resolved during review:** the first cut ran the disable, the UPDATE and the enable as three loose statements, which made a failing UPDATE leave the fund off. `update_category` now wraps the whole sequence in one transaction (§ Interface 5) and `update_category_rolls_back_the_fund_disable_when_the_rename_conflicts` is the regression guard. This is no longer an accepted residual.
2. **Modal-currency (A5) is a heuristic**, not a modeled fact. A budget mixing currencies shows one symbol for all rows. Accepted: strictly better than today's hard-coded `$`, and a real `budgets.currency` column is the honest long-term fix (follow-up).
3. **Release-please dual-release** — this touches BOTH `/backend` and `/frontend`, so it will produce two release PRs that conflict on `.release-please-manifest.json`; merge one, hand-resolve the other keeping both versions.
4. **Squash-commit body must contain no nested parentheses** — nested parens silently break release-please (workflow goes green, no release PR, nothing deploys).
5. **A15 (always-group) changes the single-type rendering** of the new view only; the chat HTML table keeps its flat single-type behavior. The two surfaces will intentionally differ for a single-type budget.
6. **The new view and the chat HTML table will report different effective limits for a #49 rollover category** (A13): the new view includes the carry, `build_categories_table_html` does not. This is a deliberate accuracy improvement in the new surface, not a regression — but it IS a visible inconsistency between two surfaces of the same data, and bringing the chat table up to match is a natural follow-up that this issue does not scope.
