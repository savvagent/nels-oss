# Spec: Retirement projection engine — accumulation, decumulation, Monte Carlo (nels#467)

## 1. Brief (verbatim from the ticket)

**As a** Nels Pro subscriber
**I want** a projection engine that turns my retirement profile, Social Security input, and asset balances into a projected monthly retirement income — with a deterministic headline figure, a Monte Carlo percentile band around it, a %-of-goal, an income-source breakdown, and a depletion age
**So that** I can tell whether I am on track and what changes would fix a shortfall.

Part of #454 (retirement planner epic). Depends on the *types* from #464, #465, #466 — not on their data. Built and tested against fixtures, so it does **not** wait on #468.

This is the highest-value unit in the epic to TDD, and the one where a bug is least visible and most damaging. Everything else is plumbing around it.

**Shape**: A new pure `backend/src/retirement.rs` — no `sqlx`, no `reqwest`, no `std::env`, no clock. The current date is an argument. Follow the precedent of `backend/src/bank_provider.rs` and `backend/src/entitlement.rs`. Callers assemble the inputs; this module only computes.

Everything in **today's dollars at a real return**. There is no nominal path anywhere in this module.

**Three functions**: (1) accumulation — today → retirement date, per year apply real return to each asset's balance, add employee contributions split pre-tax/Roth, add employer match evaluated by #465's tiered evaluator; buckets stay separate by tax treatment throughout. (2) decumulation — retirement → life-expectancy horizon, per the tax decision on #454: model the tax **wrapper** but not **brackets**; withdrawal ordering taxable → pre-tax → Roth; **RMDs are modelled** (forced pre-tax withdrawals from age 73 / 75 for 1960+, Uniform Lifetime Table divisors as a static table); tax is a single user-editable effective rate applied to pre-tax withdrawals, kept behind a small `TaxModel` input (`tax_on_withdrawal(kind, amount, year)`); Social Security (#466) added as an income stream from the claiming age onward. (3) **Monte Carlo** — return-sequence sampling for the %-of-goal band and "how long will my money last": sample a return *per year* (sequence-of-returns risk is the entire point), seeded RNG (same seed + same inputs = identical output), report percentiles 10/25/50/75/90 and a success rate, return distribution documented as named constants with sourced comments, iteration count a parameter with a documented default chosen against a measured runtime budget.

**Output**: one struct carrying the deterministic monthly income figure, the percentile band around it, percent-of-goal, the income-source decomposition for the stacked bar (own savings / employer contributions / Social Security / other assets / gap), depletion age (and whether depletion occurs at all), and **the full set of assumptions that produced it** (compliance decision on #454 requires the assumptions be rendered on the same screen as the number — the engine must hand them back rather than let the UI re-derive them and drift).

**Performance**: the UI has live contribution sliders. Before #469 can decide client-side vs. debounced server recompute, this module needs a measured answer to: how long does one deterministic path take, and how long does a full Monte Carlo take? Publish both numbers in the PR. Expect the deterministic path to be cheap enough to run per keystroke and the Monte Carlo not to be — in which case the right design is to recompute the point figure live and the band on settle, and #469 should be told that explicitly.

**Acceptance Criteria** (condensed here; full list in §3):
- `retirement.rs` contains no `sqlx`/`reqwest`/`env::var`/`Utc::now()` — enforced by review and stated in the module doc
- Accumulation tests: zero years to retirement (identity), zero return, zero contributions, employer match at/below/above each tier boundary, pre-tax and Roth buckets tracked separately end to end
- Decumulation tests: withdrawal ordering exhausts taxable before pre-tax before Roth; RMD forces a withdrawal larger than the spending need; RMD start age differs for a 1959 vs. a 1960 birth year; portfolio never goes negative; portfolio that survives to the horizon reports no depletion
- Monte Carlo tests: fixed seed reproducible across runs; a front-loaded bad-return sequence produces a strictly worse outcome than the same returns reversed (the sequence-risk assertion); percentiles are ordered; success rate is 100% for a trivially over-funded input and 0% for a trivially under-funded one
- Degenerate inputs handled explicitly and tested: no assets, no profile, retirement age already passed, life expectancy below retirement age, 100% Roth, 100% taxable, zero income
- Every default constant is named, commented with its source, and covered by a test asserting its value (so a silent change to a user-facing assumption fails CI)
- Deterministic and Monte Carlo runtimes measured and reported in the PR
- Output struct carries the assumption set used

**Surfacing**: Chat gets a read-only `RETIREMENT_PROJECTION` action arm returning a **rendered projection card**, not free-text commentary. The model must not editorialize on the result; the arm returns structured data on `ChatResponse` (`backend/src/rag.rs:94`) and the reply text is fixed. This also finally gives `rag.rs:2208`'s offline "forecast" branch — currently a hard-coded string containing a fabricated `$100.00` and no math at all — something real to point at.

REST: `GET /api/retirement/projection` plus a `POST` that accepts assumption overrides for the sliders without persisting them. User-scoped, `require_caller_tier(..., Tier::Pro)`.

**Not in scope**: tax brackets, capital-gains treatment, state tax, IRMAA, provisional-income taxation of Social Security, joint/survivor modelling, any UI.

## 2. Assumptions

1. **The engine lives in a NEW pure file `backend/src/retirement_projection.rs`, NOT in the existing `backend/src/retirement.rs`. This is an explicit interpretation of the AC's file reference, and it is the only satisfiable one.** The AC's "A new `backend/src/retirement.rs`" was written against the pre-#465 state of the repo; #465 has since created `backend/src/retirement.rs` as a 4000+ line module whose `get_profile`/`put_profile` handlers run `sqlx` against `&AppState`. The AC's *intent* — a projection engine that is pure, I/O-free, and testable against fixtures — is the requirement; the literal filename is impossible and would only be satisfiable by moving #465's handlers out of the file. Moving #465's handlers is churn with no benefit. So: `backend/src/retirement_projection.rs`, registered as `mod retirement_projection;` in `main.rs`, with the no-`sqlx`/`reqwest`/`env`/`Utc` contract stated in its module doc and enforced by review (same discipline as `entitlement.rs`). The REST/chat **handlers** that assemble inputs and call the engine live in `retirement.rs` (alongside the existing profile handlers) and `rag.rs` respectively — the handlers may touch I/O; the engine module may not.
2. **The engine takes plain fixture-shaped inputs it does not know how to load.** A single `ProjectionRequest` struct (all fields `f64`/`u32`/dates/`EmployerMatch`/`SsInput`, `#[derive(Serialize, Deserialize, Clone, Copy, Debug)]` where the types allow) is the engine's only entry. Callers (the `retirement.rs` handlers and `rag.rs` chat arm) assemble it from `retirement_profiles` + `assets` + `asset_holdings` + `social_security` DB rows and the current date. The engine imports only pure types from pure modules: `retirement::EmployerMatch`/`MatchTier` (for the match evaluator), `social_security::claiming_adjustment` (for the SS income stream). It never constructs a `sqlx::Executor` or reads an env var.
3. **Bucket model: three buckets + a pre-tax sub-split, mirrored from #464's `TaxTreatment`.** `TaxTreatment::PreTax` → `pre_tax`; `Roth` → `roth`; everything else (`Taxable`, `Hsa`, `Other`) → `taxable`. `Hsa`/`Other` are folded into `taxable` because v1 has no dedicated HSA withdrawal rule and the epic's three-way ordering is taxable → pre-tax → Roth; folding is documented in the module doc. `ProjectionRequest.starting_buckets: Buckets { pre_tax, roth, taxable }` are the caller-assembled starting values at `today` (each = the asset's `current_balance` when present, else the sum of that asset's `asset_holdings.market_value`, else `0.0`). **`pre_tax` is internally tracked as two sub-accounts, `pre_tax_own` and `pre_tax_employer`**, from the first contribution day to the last withdrawal, because the stacked bar must split "own savings" from "employer contributions" and no post-hoc allocation can reproduce the split. **The OPENING `pre_tax` balance is attributed entirely to `pre_tax_own`**: an existing 401(k)/IRA assembled from #464 assets is the user's own savings; the `pre_tax_employer` sub-account accrues only from sim-time employer-match dollars. This is pinned because it directly determines the `IncomeSources.employer_contributions` segment of the stacked bar. Roth is entirely own; taxable is entirely "other assets".
4. **All dollar figures are real (today's dollars) and annual inside the sim; monthly at the boundary.** Returns are real returns. `current_gross_income` is real and held CONSTANT in real terms across the accumulation phase (no real salary growth — documented as a conservative conventional planning figure, not a forecast, per the #454 compliance decision; a growth assumption is a later additive constant). Contributions = `gross × rate/100` per year. The employer match is `retirement::employer_match(gross, employee_pct, formula)` with `employee_pct = contribution_rate_pre_tax + contribution_rate_roth` (the total employee contribution percent; #465's evaluator already handles 0..N tiers and clamps to `0.0` for non-positive inputs). Match dollars are added to the `pre_tax_employer` sub-account.
5. **Annual time step; age granularity is whole years; current age via a pure `age_on(today, birth_date)` helper.** The horizon is `current_age..life_expectancy_age` as attained-age integer years. `current_age` is computed from `birth_date` and the passed-in `today` with a small pure helper using calendar year/month arithmetic (floored whole years — pinned and unit-tested so the deterministic path is stable across `today` values). Accumulation runs for years where `current_age + year_index < target_retirement_age`; decumulation from `target_retirement_age` through `life_expectancy_age` inclusive. **Within a year, the return applies first to the start-of-year balance, then contributions are added** (contributions earn no return in the year they are made — a documented convention, consistent across all three functions so the deterministic path, MC, and tests agree).
6. **Decumulation year = forced RMD + needs-driven withdrawal, in that order.** Each year, for attained age `a`:
   - **RMD**: if `a >= rmd_start_age(birth_year)` and `pre_tax > 0`, a forced GROSS pre-tax withdrawal `pre_tax / divisor(a)` occurs regardless of spending need (`rmd_start_age` = 73 for `birth_year <= 1959`, 75 for `birth_year >= 1960`, per #454's decision and the AC's 1959-vs-1960 test; `divisor(a)` from the static Uniform Lifetime Table, see Assumption 8). The RMD is split proportionally between the `pre_tax_own`/`pre_tax_employer` sub-accounts and its **net** after tax counts toward funding the year's income need. **Simplification, documented**: `birth_year <= 1959 → 73` collapses the real-world pre-1951 cohorts (70.5 → 72 → 73) into 73 — a tiny population, and the AC pins only the 1959-vs-1960 boundary.
   - **Needs-driven withdrawal**: the year's net spending need is `target_income − ss_income_for_the_year` (clamped at 0). It is funded in order **taxable → pre-tax → Roth**: taxable dollars are untaxed; pre-tax dollars are grossed up by `1/(1 − effective_tax_rate)` to deliver the net amount (and split own/employer proportionally); Roth dollars are untaxed. If the RMD alone already delivered more net than the need, no further withdrawal is made (the excess is genuine surplus income in that year, per #454's "RMDs can exhaust the pre-tax bucket earlier than a need-driven model would predict" — the portfolio, not the target, is exhausted; the year still never goes negative).
   - **Depletion**: if total available across all three buckets (net of tax) cannot fund the need in a given year, withdraw everything available, clamp balances to `0.0` (the portfolio NEVER goes negative — AC), and record that year as the depletion year.
7. **Social Security is a deterministic income stream from the claiming age onward, in today's dollars, never inflated/deflated.** The engine calls `social_security::claiming_adjustment` — real signature, quoted verbatim so the two `i32` month args cannot be silently swapped (they are order-interchangeable and would compile if transposed): `pub fn claiming_adjustment(benefit: f64, quoted_at_age_months: i32, claiming_age_months: i32, birth_date: NaiveDate) -> Result<f64, String>` — to derive the adjusted MONTHLY benefit, then treats `adjusted × 12` as annual income for every decumulation year where attained age `>= claiming_age_months / 12` (integer division, floored). The "no COLA adjustment" contract is #466's, and it is preserved here by construction: `claiming_adjustment` has no inflation parameter (§23/#466). If any SS input is absent, SS income is `0.0` (a partial SS input is a valid half-entered state the engine computes with). SS is NOT subject to the effective tax rate (per #454's "no provisional-income taxation of Social Security" — out of scope, explicitly in the ticket).
8. **RMD divisors: a static table keyed by attained age, from the IRS Uniform Lifetime Table (Pub. 590-B, Table III), with a documented tail.** The table covers the RMD-start age (73/75) through 115+; ages past the printed table reuse the last printed divisor (documented). The table is a `const` array indexed by `age − RMD_START_FLOOR` (the lowest possible start age), sourced-commented to the IRS publication and edition, and pinned by a test asserting a representative sample of rows plus the tail rule. No divisor lookups are ever computed; the table is the single source of truth.
9. **`TaxModel` is a small struct, not a trait — same closed-set discipline as `bank_provider::Provider`.** `pub struct TaxModel { pub effective_rate: f64 }` (a fraction, `0.0..=1.0`, validated finite and in range by the caller; a negative/NaN rate is an invalid input) with `pub fn tax_on_withdrawal(&self, kind: TaxedBucket, amount: f64, _year: u32) -> f64` where `pub enum TaxedBucket { Taxable, PreTax, Roth }`. The method returns `0.0` for `Taxable`/`Roth`, `amount × effective_rate` for `PreTax`. The `year` parameter is part of the signature per the AC but is UNUSED in v1 (documented `_year`): it is the seam that lets a future bracket engine phase in tax rates by calendar year without changing the call sites. A bracket engine would be a second `TaxModel`-shaped implementation later, not a rewrite — but v1 ships exactly one. Pre-tax withdrawals are taxed once, on the gross amount, when withdrawn.
10. **The deterministic path uses the profile's `expected_real_return` as a constant real annual return every year.** No sampling, no noise. It produces the headline figure, the deterministic depletion age, and the source decomposition. `expected_real_return` is #465's PERCENT-scaled field (e.g. `5.0` = 5% real), converted to a fraction internally — the units bullet in §21/#465 is load-bearing and the conversion is pinned by a test.
11. **Monte Carlo: lognormal annual real returns, seeded, path-major draw order.** Each path samples a real return multiplier per year from a lognormal with mean `expected_real_return` (as a fraction, converted to log-mean via `ln(1 + r) − σ²/2`) and standard deviation `σ = MC_REAL_RETURN_STD_DEV` (named constant, sourced-commented — a representative long-run real return volatility for a diversified portfolio, a conventional planning figure, NOT a forecast, per the compliance decision; see §8 for the sourcing note). `MC_REAL_RETURN_STD_DEV` is a SINGLE constant applied to the whole portfolio regardless of the user's actual allocation (v1 has no per-asset-class return model — documented simplification, not a bug). RNG is `StdRng::seed_from_u64(seed)` (`rand` 0.8; `rand_distr = "0.4"` is the NEW dependency, matching the existing `rand` version — `Normal` distribution). The `seed` is a required field of `ProjectionRequest`, so same seed + same inputs = identical output, always (AC). Draw order is fixed and documented: outer loop over paths, inner loop over years, one draw per accumulation year and per decumulation year in ascending year order. **No `thread_rng`, no entropy, anywhere in the engine.** The production REST/chat handlers use a documented fixed default seed constant (`MC_DEFAULT_SEED`), so production output is reproducible too.
12. **Monte Carlo: percentiles and success rate, per-path.**
    - **Success rate** = fraction of paths in which a target-withdrawal run (withdrawing the year's net need `target_income − ss` via the Assumption 6 ordering, RMDs forced) reaches `life_expectancy_age` without depleting. A trivially over-funded input (huge starting buckets) → 100%; a trivially under-funded one (tiny starting buckets, real target) → 0%. AC-pinned.
    - **Percentile band** = percentiles (10/25/50/75/90) of per-path **total monthly income** across the sampled paths, where each path's total = its sustainable portfolio monthly income (Assumption 13) **+ ss_monthly**. Because `ss_monthly` is deterministic and identical across paths, the band is exactly the per-path portfolio-band shifted by SS — so the band always bounds the deterministic headline (`sustainable_annual_w/12 + ss_monthly`) by construction, satisfying the AC's "percentile band around [the deterministic figure]" even when SS > 0. The band is reported as monthly figures alongside the deterministic headline. Percentiles are computed on the sorted per-path values; ties are fine (a degenerate input yields a flat band — reported, not an error).
    - Iteration count `paths` is a required field of `ProjectionRequest`; `MC_DEFAULT_PATHS` is the named production default, chosen against the measured runtime budget (Assumption 14). The deterministic path is recomputed live per keystroke; the MC band on settle — the #469 instruction falls out of the measured numbers.
13. **The headline "deterministic monthly income" is the SUSTAINABLE withdrawal, not the target.** `sustainable_annual_w` = the constant real ANNUAL net portfolio withdrawal that exactly exhausts the portfolio at `life_expectancy_age`, solved by bisection over `w ∈ [0, w_max]` with a fixed iteration count (named constant, tested). **The solve-run is Assumption 6's decumulation with the trial `w` substituted for `target_income` in the year's need** (SS still offsets it; RMDs still forced) — the bisection searches for the `w` whose need-stream the portfolio exactly funds, it does NOT fix the target and then measure the shortfall. Then `deterministic_monthly_income = sustainable_annual_w/12 + ss_monthly`, `percent_of_goal = deterministic_monthly_income / target_monthly_income` (an `Option<f64>` — `None` when `target_monthly_income <= 0`, see Assumption 15). Per-path sustainable portfolio monthly income (same solve per MC path) feeds Assumption 12's band. **This is why the dial can exceed 100%**: an over-funded plan sustains more than its target, matching the epic's "you're at 124%" shape. The `w_max` bound is a named constant with a source comment and must be comfortably above any realistic annual withdrawal (the bisection clamps the search to it; a pathological input that would need more is reported as `percent_of_goal > 1` but the band's sustainable figure is capped at `w_max` — documented).
14. **Runtime budget and measurement.** `MC_DEFAULT_PATHS` defaults to a value that keeps a full Monte Carlo well under the debounced-server-recompute budget (target: full MC in single-digit ms–low tens of ms in release against fixture inputs; measured, not assumed). A deterministic path must be sub-millisecond. A `#[ignore]`d `runtime_benchmarks` test (documented run command in the test's doc comment) times both against a standard fixture set and prints them; the PR body publishes the measured numbers and states the resulting #469 recommendation (live point figure + settle-debounced band). The ignored test is `#[ignore]` because CI timing is unreliable; the PR report is the deliverable, per the AC.
15. **Degenerate inputs are first-class.** The engine NEVER panics on them and NEVER emits NaN/Infinity (every `f64` entering the sim is `is_finite()`-guarded, and per the §20/#464 trap, the guard is `!x.is_finite()` evaluated FIRST — never an ordered comparison, since `NaN <= 0.0` is false). Concretely:
    - **No assets** → `Buckets { 0, 0, 0 }` is a valid input; the projection is contributions-only (accumulation from zero). Tested.
    - **No profile** → a handler-level state, not an engine input: the REST/chat handlers return a clear 404-style "set up your retirement profile first" error before calling the engine (tested at handler level). The engine itself never sees "no profile".
    - **Retirement age already passed** → zero accumulation years; decumulation starts at `current_age` (the "zero years to retirement" identity). Tested.
    - **Life expectancy <= current age, or life expectancy < retirement age** → impossible geometry: the engine returns a typed `ProjectionError::InvalidInput` with a per-field message (never a silent degenerate number). Tested.
    - **100% Roth / 100% taxable** → ordinary bucket shapes; withdrawal ordering never touches the empty buckets (tested that a 100%-Roth portfolio's pre-tax bucket stays zero and all withdrawals come from Roth).
    - **Zero gross income** → `target_monthly_income <= 0` → `percent_of_goal = None`, sustainable figure computed normally. Tested.
    - **Non-finite or out-of-range inputs** (NaN/Infinity return/rate/income/balances, `effective_tax_rate` outside `0..=1`, negative balances) → `ProjectionError::InvalidInput`, tested.
16. **The output struct `Projection` carries the full assumption set used** (compliance decision on #454). `Projection` is `#[derive(Serialize)]` and includes: the deterministic monthly income, `percent_of_goal`, the percentile band, success rate, `IncomeSources { own_savings, employer_contributions, social_security, other_assets, gap }` (monthly figures from the DETERMINISTIC sustainable run — own_savings = roth + pre_tax_own withdrawals, employer = pre_tax_employer withdrawals, social_security = adjusted SS monthly, other_assets = taxable withdrawals, `gap = max(0, target_monthly − sum)` — the stacked bar's five segments), `depletion_age: Option<i32>`, `depletes: bool` (both from the deterministic TARGET-withdrawal run — Assumption 12's target run re-run with constant returns; a plan that survives reports `depletes: false`), and **`assumptions: ProjectionAssumptions`** — every input that produced the numbers: all `ProjectionRequest` fields (echoed), the derived `current_age`/`rmd_start_age`, `σ`, `MC_DEFAULT_SEED`/`paths` used, the tax model rate, the SS adjusted benefit and claiming age used, `sustainable_annual_w` and the bisection iteration count, the `w_max` bound, and the current date. The UI renders `assumptions` on the same screen as the number; the engine returning them is what stops the UI from re-deriving and drifting.
17. **Serialization boundary**: `Projection`, `ProjectionRequest`, `ProjectionAssumptions`, `Buckets`, `IncomeSources`, `TaxModel`, `SsInput` are all `serde`-derived (Serialize; Deserialize where the engine accepts input). They are plain data types with no behavior. The chat card and the REST response serialize the SAME `Projection` — no second spelling of the numbers, so chat and REST cannot disagree (the `upsert_profile` "one writer, two surfaces" discipline applied to the read side).
18. **REST surface**: `GET /api/retirement/projection` (user-scoped, `require_caller_tier(..., Tier::Pro)` — the #465 precedent: the caller's own tier, `require_caller_tier`, NOT `require_tier`, since there is no budget in scope) assembles the request from the stored profile + assets + today and returns `Projection`. `POST /api/retirement/projection` accepts a `ProjectionOverrides` body (the slider fields: `contribution_rate_pre_tax`, `contribution_rate_roth`, `expected_real_return`, `target_retirement_age`, `current_gross_income`, `target_replacement_ratio`, `effective_tax_rate`, `employer_match_formula`) merged over the stored profile WITHOUT persisting anything (no DB write, no audit row — it is a what-if, not a save), and returns the same `Projection` shape; overrides are validated (finite, in-range, matching `validate_profile`'s spirit — the engine's own `ProjectionError::InvalidInput` on violation). Both are Pro-gated; a lapsed user's GET returns 402 (the #465 rule: reading a projection is a paid feature, unlike reading your own profile).
19. **Chat surface**: a read-only `RETIREMENT_PROJECTION` action. The LLM invokes it with NO free-text editorializing (rule in the system prompt, mirroring #465/#466's no-advice rule); the arm runs the engine via the same handler path as REST (Pro-gated), renders a **fixed** projection card (a `build_projection_card_html` builder mirroring `build_categories_table_html`'s shape, showing headline, band, %-of-goal, success rate, sources, depletion, and the assumption-disclosure line) as `ChatResponse.response_text`, and attaches the structured `Projection` to `ChatResponse` via a new optional field (e.g. `retirement_projection: Option<Projection>`), so #469 can render the real card later without re-running anything. The offline "forecast"/"next month" branch (`rag.rs:2271`'s hard-coded `$100.00` string — the ticket's `2208` is stale, the branch actually lives at 2271-2272) is repointed at the same engine path for the deterministic figure (offline = no LLM, so the card is built directly). **The offline matcher must be NARROWED so a near-term budget utterance ("forecast next month", "what will I have left over") is not answered with a retirement projection**: retirement-phrasing words (retire/retirement/projection) claim the branch; the existing forecast/next-month budget semantics keep their own arm, and the AC's "finally gives rag.rs:2271's forecast branch something real to point at" is satisfied by the retirement-phrased branch returning the real engine figure instead of the fabricated `$100.00`. Chat is Pro-gated like REST.
20. **No migration.** #467 adds no schema. The engine reads existing `retirement_profiles`, `assets`, `asset_holdings` columns. The only repo-level change is the new `rand_distr = "0.4"` dependency (matched to the existing `rand = "0.8"`).

## 3. Goal & Success Criteria

A Pro subscriber can obtain a projection of their monthly retirement income — deterministic headline + Monte Carlo percentile band + %-of-goal + income-source decomposition + depletion age + the assumptions behind it — via REST (`GET`/`POST /api/retirement/projection`) and via a read-only chat action that renders a fixed card, with the engine being a pure, deterministic, fixture-testable module.

Success criteria (mapped 1:1 from the AC):
- [ ] `retirement_projection.rs` contains no `sqlx`/`reqwest`/`env::var`/`Utc::now()` — module doc states the contract; review enforces it
- [ ] Accumulation: identity (zero years → buckets unchanged), zero return (balance grows by contributions only), zero contributions (balance grows by return only), employer match at/below/above each tier boundary (match dollars = `employer_match(gross, total_pct, formula)`), pre-tax vs Roth tracked separately end to end (a Roth contribution never lands in pre-tax and vice versa)
- [ ] Decumulation: ordering exhausts taxable before pre-tax before Roth (asserted at the point each bucket hits zero); an RMD larger than the spending need forces the larger gross withdrawal; `rmd_start_age` differs for birth year 1959 (73) vs 1960 (75); no bucket ever goes negative; a surviving plan reports `depletes: false`/`depletion_age: None`
- [ ] Monte Carlo: same seed reproduces identical output across two runs; a front-loaded bad-return sequence (bad returns first) produces a strictly worse outcome than the same returns reversed (the sequence-risk assertion); percentiles are ordered p10 ≤ p25 ≤ p50 ≤ p75 ≤ p90; success rate 100% for trivially over-funded, 0% for trivially under-funded
- [ ] Degenerate inputs (§2.15) all handled and tested
- [ ] Every default constant (`MC_REAL_RETURN_STD_DEV`, `MC_DEFAULT_PATHS`, `MC_DEFAULT_SEED`, `w_max`, bisection iterations, `rmd_start_age` thresholds, `TaxModel` validation bounds) is named, source-commented, and pinned by a value-asserting test
- [ ] Deterministic + MC runtimes measured and published in the PR (Assumption 14)
- [ ] `Projection` carries the full `ProjectionAssumptions` set (Assumption 16)

## 5. Architecture

**New module**: `backend/src/retirement_projection.rs` — pure. Imports only pure types (`retirement::EmployerMatch`, `social_security::claiming_adjustment`) and `rand`/`rand_distr`. ## 6. Error Handling & Edge Cases

- Impossible geometry (`life_expectancy <= current_age`, `life_expectancy < retirement_age`) → `ProjectionError::InvalidInput` with a per-field message (400 at the handler), tested.
- Non-finite/out-of-range inputs (NaN/Infinity return, rates, income, balances; `effective_tax_rate` outside `0..=1`; negative balances) → `ProjectionError::InvalidInput`, `is_finite()` guarded FIRST per the §20/#464 NaN trap, tested.
- No profile at handler level → 404-style "set up your retirement profile first", before any engine call, tested.
- Lapsed subscriber (REST or chat) → 402 via `require_caller_tier(Pro)`, zero engine work, mirroring the #465 Pro gate, tested.
- Partial SS input (benefit but no ages) → SS income `0.0`, projection computed normally (never an error), tested.
- `claiming_adjustment` returning an error for a stored row our own math refuses (the #466 `adjustment_unavailable` case) → surfaced as `ProjectionError::InvalidInput` at the handler (400), never silently recomputed, tested.
- RMD exceeding the year's need → genuine surplus income that year, portfolio never negative, tested.
- Pathological inputs that would exceed `w_max` → sustainable figure capped at `w_max`, `percent_of_goal` still reported (>1 possible), documented in the module doc, tested.
- Zero gross income → `percent_of_goal = None`, rest of the projection valid, tested.
- MC with `paths = 0` → `ProjectionError::InvalidInput` (a band from zero paths is meaningless), tested.

## 7. Testing Approach

- **Unit tests (in `retirement_projection.rs`, no DB/HTTP/clock)**: all of §3's success criteria — accumulation identity/zero-return/zero-contribution/tier-boundary/separate-buckets; decumulation ordering/RMD-forced/RMD-age/never-negative/survives; MC reproducibility/sequence-risk/percentile-ordering/100%-and-0%-success; every §2.15 degenerate input; every named constant's value (incl. a representative sample of Uniform Lifetime Table rows + the tail rule); `age_on`; the `expected_real_return` percent→fraction conversion; the percentiles-of-sorted-values computation; bisection convergence on the sustainable solve. **The sequence-risk test needs an explicit per-year return series seam**: the deterministic path takes its constant return as a `&[f64]`-shaped return series internally (a one-element series that gets repeated, or a series consumed in order), so a test can hand-build `[bad, bad, bad, good…]` and its reversal, run the same simulation on both, and assert the front-loaded one yields a strictly worse sustainable figure. If the year-loop does not accept an explicit series, the sequence-risk AC cannot be tested as written — this seam is mandatory, not optional.
- **`#[ignore]`d DB/handler tests** (mirroring `retirement.rs`/`assets.rs`'s style, `mk_pro`-seeded Pro user with `status='trialing'` per the §21 test-infrastructure note): Pro gate (402, zero work), no-profile 404, `GET` returns a `Projection` for a seeded profile+assets fixture, `POST` applies overrides without persisting (row unchanged after), chat `RETIREMENT_PROJECTION` card + structured field, offline "forecast" branch returns the real deterministic figure (no `$100.00`), `rand_distr` draws are stable for a fixed seed at the module boundary.
- **Runtime**: `#[ignore]`d `runtime_benchmarks` test timing a deterministic path and a full `MC_DEFAULT_PATHS` run against the fixture set, printed with `--nocapture`; PR body reports the numbers and the resulting #469 recompute recommendation (Assumption 14).
- **Frontend**: NONE (no UI in scope; #469 owns it).

## 8. Risks & Open Questions

- **The `σ` constant is a named assumption with sourcing responsibility, and its value is user-facing** (per #454's compliance decision, assumptions render on the same screen as the number). This spec proposes `MC_REAL_RETURN_STD_DEV` as a single constant for the whole portfolio (a representative long-run real return volatility for a diversified portfolio), but the exact VALUE and citation must be pinned during planning from a real source (e.g. a published long-run real-return-volatility figure for a balanced US portfolio, similar in spirit to how #465 sourced its conventional planning figures). If no defensible citation is found, the fallback is to document it explicitly as a conventional planning figure rather than a forecast — never silent. This is the one open numeric in this spec and is expected to be resolved in the plan, not deferred.
- **`MC_DEFAULT_PATHS` is a placeholder** ("single-digit ms–low tens of ms" target); the real value is chosen against the measured benchmark (Assumption 14). The PR must state both the value and the measured time, since #469's recompute architecture (live vs. settle-debounced) depends on it.
- **Sole sourced number for the whole portfolio regardless of the user's actual allocation** (§2.11) is a documented v1 simplification. A user's real allocation (from #464 holdings) does not feed the return distribution in v1; this biases every user's band toward the same volatility. Acceptable for the epic's v1 shape, explicitly not a forecast; a per-asset-class return model is a later additive change.
- **Annual granularity loses the sub-annual claiming-age precision** (#466 stores ages in months; the sim steps in whole years, flooring `claiming_age_months/12`). The monthly SS figure itself is exact; only the START year is floored to whole years. Documented in the module doc; the error is bounded by one year of SS income, which the deterministic/MC shapes absorb. Flagged rather than hidden.
- **Constant-real-gross and no-real-salary-growth** (§2.4) understates contributions for a growing earner — a conservative direction of error (the #465/#466 house preference: never overstate readiness). Documented as a conventional planning figure.
- **The AC's literal file reference (`retirement.rs`) is unsatisfiable** post-#465 and is explicitly interpreted as "a pure engine module" (Assumption 1). Any reviewer must accept this interpretation or reopen the "move #465's handlers" option, which is churn with no benefit.
- **Compliance copy**: the chat card and the assumption-disclosure line render server-side as FIXED text (§2.19); the fuller on-screen framing (a "hypothetical educational illustration" disclosure) is #469's AC and is explicitly not built here. The engine's obligation is only to RETURN the assumptions; rendering them fully is #469's.
