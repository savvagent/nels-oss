# Spec: Link bank accounts via Belvo — Mexico, Brazil (nels#322)

## 1. Brief (verbatim from the ticket)

**As a** Nels Pro subscriber banking in Mexico or Brazil
**I want** to link my bank account via Belvo (the leading open-finance data platform in Latin America)
**So that** my transactions import automatically, matching the experience #303 provides for US subscribers via Stripe Financial Connections.

**Acceptance Criteria**
- A Pro subscriber with a bank account in Mexico or Brazil can start a Belvo link/consent flow and link one or more accounts to a budget.
- A non-Pro user is blocked from starting the link flow and shown an upgrade prompt, same as #303.
- Linked accounts' transactions import into the existing `transactions` table, attributed to the user's active budget at import time, recording a `currency` of `MXN` or `BRL` on each imported row as applicable — no FX conversion; budget-level multi-currency handling is out of scope for this ticket.
- Transactions refresh automatically via Belvo's webhook notifications, plus a manual refresh action.
- A user can view linked accounts and disconnect one; disconnecting stops future imports without deleting previously-imported transactions, same as #303.
- Linking and "what's linked" status are reachable from the chat co-pilot, using Belvo's embeddable widget.
- If a subscription lapses, automatic refresh stops for Belvo-linked accounts without deleting them, same as #303.

**Notes**: Implement Belvo as a new provider against the existing `BankProvider`/`bank_linking.rs` dispatch layer introduced by #320 — the shared `linked_accounts.provider`/`provider_account_id` schema and the `bank_provider::Provider` enum already exist; this story does not redo that generalization, it adds a third variant and a new `backend/src/belvo.rs` module alongside `financial_connections.rs` (Stripe) and `gocardless.rs` (GoCardless).

## 2. Assumptions

1. **Belvo REST API**, base `https://sandbox.belvo.com`/`https://api.belvo.com`, authenticated with **HTTP Basic Auth** (`SECRET_ID`:`SECRET_PASSWORD` as the Basic-auth username/password) on every request — no bearer-token exchange/cache layer is needed, unlike GoCardless's `access`/`access_expires` dance. This makes `belvo.rs`'s HTTP layer the simplest of the three provider modules: a module-local `reqwest::Client` plus a `belvo_get`/`belvo_post`/`belvo_delete` trio that attach `.basic_auth(secret_id, Some(secret_password))` per call, mirroring `financial_connections.rs`'s "own HTTP helpers, own env-driven test seam" convention (`BELVO_API_BASE` env var, default `https://api.belvo.com`, pointed at a local `wiremock` server in tests exactly like `STRIPE_API_BASE`/`GOCARDLESS_API_BASE`).
2. **Belvo's consent flow is a client-side embeddable widget, not a full-page redirect** — closer in spirit to Stripe's client-driven modal than to GoCardless's redirect-and-return. Concretely: our backend calls `POST /api/token/` with `{id: SECRET_ID, password: SECRET_PASSWORD, scopes: "read_institutions,write_links", fetch_resources: ["ACCOUNTS","TRANSACTIONS"], widget: {external_id, country_codes}}` to mint a short-lived (~10 min, single-use) **widget access token**; the frontend loads `https://cdn.belvo.io/belvo-widget-1-stable.js` and initializes the widget with that token; the user picks their institution and authenticates entirely inside the widget (Belvo's UI, not ours — so, unlike GoCardless's v1 fuzzy-text institution matcher, **no server-side institution search/matching code is needed for Belvo at all**); on success the widget's JS callback (`onSuccess(link_id, institution)`) fires in the frontend with a Belvo `link_id`, which the frontend then posts to our backend to complete the link server-side.
3. **A pending-session table is still required for anti-replay**, even though there's no redirect round-trip, because Belvo's widget token flow never tells our backend *which of our users* completed it — only whatever `external_id` we supplied at token-mint time comes back attached to the created Link. New table `belvo_link_sessions` (one row per pending widget-token mint), directly analogous to GoCardless's `bank_link_sessions` but simpler (no requisition/agreement bookkeeping, since the widget itself handles institution selection and authentication):
   ```sql
   CREATE TABLE belvo_link_sessions (
       id          UUID PRIMARY KEY,   -- minted before the token call; passed to Belvo as widget.external_id
       budget_id   UUID NOT NULL REFERENCES budgets(id) ON DELETE CASCADE,
       user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
       country     TEXT NOT NULL CHECK (country IN ('MX','BR')),
       status      TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','completed')),
       created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
   );
   ```
   `start_link_session` (Pro-gated, Edit-or-Owner, budget-not-closed) inserts this row, mints the widget token with `widget.external_id = session.id.to_string()` and `widget.country_codes = [country]` (restricts the widget's institution picker to the right country's banks), and returns `{access_token, session_id}` to the caller (REST response body or `ChatResponse` fields — Assumption 12). No `redirect_url`/`client_secret` field is reused for this — Belvo's shape (a widget-init token plus our own session id) is distinct enough from both existing providers to warrant its own pair of fields, same reasoning #320 used to justify `LINK_BANK_ACCOUNT` being the one call site allowed to branch per-provider.
4. **`complete_link_session(session_id, belvo_link_id)` re-fetches everything it needs server-side, trusting nothing from the client except which Belvo `link_id` to look up** (same anti-replay posture as both existing providers' `complete_link_session`): loads the `belvo_link_sessions` row by `session_id` (404 if missing), verifies caller's `budget_id`/`user_id` match it (403 on mismatch), verifies `status = 'pending'` (409 if already `'completed'` — no double-complete); calls `GET /api/links/:link_id/` and confirms the returned Link's own `external_id` equals `session_id` (403 if it doesn't — defense in depth against a client submitting someone else's `link_id`); the Link response's own `institution` field (Belvo returns the institution's display name directly on the Link resource, not just a code) supplies `linked_accounts.institution_name` for every account under it — populated the same way Stripe reads its display name straight off its session payload, so a Belvo-linked account never ships with a blank name in "what's linked" (chat/REST list); then calls `GET /api/accounts/?link=:link_id` to enumerate every bank account under that Link (a single Belvo Link can cover multiple accounts at one institution, same "one session, N accounts" shape GoCardless's requisition has); for each account, the same cross-budget guard (409 if `provider_account_id` already linked to a *different* budget) and `INSERT ... ON CONFLICT (provider_account_id) DO UPDATE` used by both existing providers — including `institution_name`, `institution_id`, and `last4` (derived from the account's masked number) in that insert; attempts a best-effort initial `sync_account_transactions` per account (failure only logged — Belvo's own data model is async-by-nature per Assumption 6, so an empty/failed initial sync is expected, not exceptional); marks the session `'completed'`.
5. **`provider_account_id` = the individual Belvo account id; `provider_ref` = the parent Belvo `link_id`** — this is exactly `provider_ref`'s existing generalized meaning ("the provider-side parent reference used for anti-replay/ownership verification"; #320 Assumption 9), reused as-is: Stripe's is the Customer id, GoCardless's is the Requisition id, Belvo's is the Link id. No `linked_accounts` schema change needed for this — the columns already exist and are generic.
6. **Belvo has real webhooks (unlike GoCardless), so Belvo is webhook-driven, not polled** — no scheduled ticker is added for Belvo. Belvo's data model is pull-then-notify: a `POST /api/transactions/` call (Assumption 7) *requests* a resync from the institution, and once Belvo has it, a webhook (`webhook_type: "TRANSACTIONS"`, `webhook_code` one of `"historical_update"`/`"new_transactions_available"`, carrying `link_id` and `external_id`) tells us data is ready to *pull*. A new public route `POST /api/belvo/webhook`, registered the same way as Stripe's `/financial-connections/webhook` (a separate `belvo_public_routes` Router nested outside `auth_middleware`, `main.rs`), looks up every `linked_accounts` row with `provider='belvo'` and `provider_ref = link_id`, and — after the same Pro/closed-budget double-check the Stripe webhook already does (#320's established "pause without deleting" mechanism) — calls `sync_account_transactions` for each. A webhook whose `link_id` matches no linked account (e.g. a stale/abandoned session, or a webhook for a Link we never completed) is a silent 200 no-op, not an error.
7. **Webhook auth: HTTP Basic, per Belvo's own webhook-configuration model**, not HMAC. Belvo's webhook setup lets the integrator attach an optional `Authorization: Basic <base64(user:password)>` header that Belvo will send with every webhook delivery, configured once in the Belvo dashboard/API when registering the webhook URL — there is no separate signing-secret/HMAC scheme to verify against (unlike Stripe's `STRIPE_FC_WEBHOOK_SECRET` HMAC). `belvo::webhook` checks the incoming request's `Authorization` header against `BELVO_WEBHOOK_USER`/`BELVO_WEBHOOK_PASSWORD` env vars (constant-time compare), returning 401 on mismatch or a missing header. **Flagged as a Risk** (§8): this codebase's actual Belvo webhook registration (done once, out-of-band, via the Belvo dashboard or a one-time API call — not part of this ticket's runtime code) must set that same Basic-auth pair for the check to mean anything; documented here so it isn't silently skipped during ops setup.
8. **`sync_account_transactions`** (called from: best-effort initial complete, manual refresh, and the webhook handler — one function, three callers, same shape as the other two providers) calls `POST /api/transactions/` with `{link: link_id, date_from: <last_synced_at or account creation date>, date_to: <today>, save_data: true}` — Belvo's request-and-return-if-ready semantics: if the data is already fresh (which it will be right after a webhook fires), the response body itself contains the transaction list synchronously; if not yet ready, Belvo returns a 202-class response with nothing to import, treated as a **clean no-op** (`Ok(0)`), not an error — the eventual webhook (or the next manual refresh) will complete it. Per-transaction: same "drop rather than import" guard for a missing/malformed id or amount (mirrors both existing providers); category is resolved the same way both existing providers already do — load the budget's `categories` once per sync call and pass each transaction's own description through the existing, reused-as-is `crate::financial_connections::guess_category_id(&description, &categories)` (never reimplemented per-provider, per #320's own established reuse of this exact function for GoCardless); `ON CONFLICT (external_account_id, provider_transaction_id) WHERE provider_transaction_id IS NOT NULL DO NOTHING` (the exact index #320 already generalized for a second provider — needs no further change for a third).
9. **Currency is read per-transaction from Belvo's payload, with a country-derived fallback — not a single hardcoded default.** Each Belvo transaction record carries its own `currency` (ISO 4217, `"MXN"` or `"BRL"` depending on the linked account's country). If a transaction is ever missing that field, the fallback is **the linked account's own `country` column** (`'MX'` → `MXN`, `'BR'` → `BRL`) rather than a single constant — deliberately different from `gocardless.rs`'s existing blanket `"EUR"` default (§8 Risk notes why that default would be actively wrong here: a single hardcoded currency can't cover two different countries with two different currencies the way it can for a single-currency-zone aggregator).
10. **Amount sign/normalization**: Belvo's transaction payload carries a numeric `amount` plus a `type` field (`"INFLOW"`/`"OUTFLOW"`) rather than GoCardless's signed decimal string or Stripe's signed integer cents. `belvo::normalize_amount(amount: f64) -> f64` takes the absolute value (matching this codebase's established "amount is always a positive magnitude" convention — same contract as the other two providers' normalization functions, each provider still owning its own version since the wire shape differs every time).
11. **Reconciliation on reconnect uses last4 + institution match, not IBAN.** GoCardless's re-consent reconciliation (#320 Assumption 11) matches on IBAN, which Mexican and Brazilian bank accounts generally don't have (IBAN isn't used in either country's domestic banking system) — Belvo's own account payload doesn't expose one. Belvo's reconciliation instead matches an existing `consent_expired` row for the same `budget_id` + `institution_id` (Belvo's institution code, stored in the existing generic `institution_id` column) by the account's `last4` (Belvo exposes a masked account `number`, from which the last 4 digits are extracted the same way the existing `last4` field is already populated for Stripe/GoCardless). A match reconciles onto the existing row (preserving transaction history); no match inserts a new row — same bounded, documented, no-data-loss-either-way heuristic #320 already established as this codebase's precedent for "reconciliation is best-effort, not perfect."
12. **Link-status changes surface via the *same* `consent_expired` status value already on `linked_accounts`**, not a new Belvo-specific status. Belvo Links have their own status field (`valid`/`invalid`/`unconfirmed`/`token_required`); a webhook or a `sync_account_transactions` response indicating a non-`valid` Link status flips the local row to `status = 'consent_expired'` — reusing #320's existing semantics ("needs re-auth before further sync") rather than widening the `status` CHECK again. `LIST_LINKED_ACCOUNTS` and manual refresh already render/short-circuit on `consent_expired` for GoCardless; this is a pure reuse, no new UI states.
13. **Schema change is one small migration, not a repeat of #320's generalization**: `linked_accounts.provider` CHECK widened to add `'belvo'` (`ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ... CHECK (provider IN ('stripe','gocardless','belvo'))`); new `belvo_link_sessions` table (Assumption 3). No new `linked_accounts`/`transactions` columns — `institution_id`, `country`, `iban` (left `NULL` for Belvo, per Assumption 11), `consent_expires_at` (left `NULL` — Belvo's expiry is status-driven, not a fixed calendar window, per Assumption 12), and `transactions.currency` all already exist and are provider-generic.
14. **`bank_provider::Provider` grows a third variant, still enum dispatch, no `dyn` trait object** — `pub enum Provider { Stripe, GoCardless, Belvo }`. Adding Belvo costs exactly one new match arm in `for_country`, one new pair in `supported_countries()`, one new `"belvo"` arm in `as_str` (exhaustive match, compiler-enforced) and in `parse` (its `_ => None` wildcard means a forgotten arm would compile silently rather than error — `parse`/`as_str` have no production callers today beyond their own tests, so this is a discipline note for the plan, not a live bug), and one new `"belvo"` arm in each of `bank_linking.rs`'s `refresh_linked_account`/`disconnect_linked_account` dispatchers — confirming, not undermining, #320's tradeoff call that a closed, small provider set doesn't justify `async-trait`+`Arc<dyn BankProvider>` machinery. `Provider::for_country`: `"MX" | "BR" => Some(Provider::Belvo)` (both map to the same provider, same one-aggregator-many-countries shape GoCardless already has for its 8 European countries).
15. **Pro-gating and disconnect-ordering mirror both existing providers exactly**: `start_link_session` and manual `refresh_linked_account` are Pro-gated (402, zero Belvo API calls made if not Pro); `list`/`disconnect` are not. `disconnect_linked_account` calls Belvo's `DELETE /api/links/:link_id/` first (tolerating a 404 as "already gone," same idempotent-tolerance precedent both other providers use), then flips the local row to `disconnected` — ends Belvo-side access so no further webhook deliveries are possible even if the local flip somehow failed to persist.
16. **Chat surface**: `LINK_BANK_ACCOUNT`'s existing `country`/`institution_query` `AiActionParams` fields are reused as-is for the country (`institution_query` is simply unused on the Belvo branch, since the widget handles institution selection — no new param needed). `ChatResponse` gains two new optional fields, `belvo_widget_access_token: Option<String>` and `belvo_link_session_id: Option<Uuid>`, set together only when `LINK_BANK_ACCOUNT` resolves to `Provider::Belvo` (parallels the existing `financial_connections_client_secret`/`bank_link_redirect_url` pair-of-Options pattern rather than introducing a nested response type). The system prompt (rule 2o) is extended to name Mexico and Brazil alongside the existing 9 countries; the offline keyword router (`offline_country_hint`) gains `"mexico"/"méxico"→"MX"` and `"brazil"/"brasil"→"BR"` phrase matches. `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/`REFRESH_BANK_ACCOUNT` need zero changes — they already call the provider-agnostic `bank_linking::*` functions per #320, and now transparently cover Belvo-provider rows too.
17. **Frontend**: a new shared widget-loader helper in `linkedAccounts.js` (`startBelvoWidget(accessToken, {onSuccess, onExit})`) lazily injects the `cdn.belvo.io` script tag once and initializes Belvo's widget object — used both by `LinkedAccounts.svelte`'s country select (adding Mexico/Brazil options alongside the existing US/GoCardless-8 options) and by the chat surface (`App.svelte`, rendering the widget inline when `belvo_widget_access_token` is present in a chat response, same "reacts to a new optional chat-response field" shape as the existing Stripe-modal and GoCardless-redirect handling). On the widget's `onSuccess(link_id)` callback, the frontend calls `POST /api/budgets/:id/belvo/complete` with `{session_id, belvo_link_id: link_id}`. i18n: the existing 6-locale `linkedAccounts` key block gains Belvo-specific strings (mirroring the GoCardless-added keys), added to all 6 locale files.
18. **No marketing site changes** — authenticated-app feature only, same as #303 and #320.
19. **Test seam**: `BELVO_API_BASE` env var (default `https://api.belvo.com`), mirroring `STRIPE_API_BASE`/`GOCARDLESS_API_BASE`, pointed at a local `wiremock` server in `#[ignore]` integration tests exactly like both existing providers' suites.

## 3. Goal & Success Criteria

Pro subscribers in Mexico or Brazil can link one or more bank accounts via Belvo's embeddable widget, with transactions landing in the existing `transactions` table (currency-tagged `MXN`/`BRL` per the linked account's country, no FX conversion). Auto-refresh happens via Belvo's webhook (pull-on-notify), plus manual refresh; a Link that goes invalid reuses the existing `consent_expired` status and UI. View/disconnect and chat reachability match #303/#320's UX exactly. Belvo plugs into the existing `bank_provider::Provider` enum and `bank_linking.rs` dispatch layer as a third match arm — no changes to the generalized schema or dispatch shape #320 already built.

Success criteria:
- [ ] A Pro user in Mexico or Brazil can complete an end-to-end link via the embeddable widget (mint token → widget UI → `onSuccess` → complete call), and it appears via `LIST_LINKED_ACCOUNTS` (REST + chat) indistinguishably from a Stripe/GoCardless-linked account (`provider: "belvo"`).
- [ ] A non-Pro user's attempt to start a Belvo link (REST or chat) is rejected with a clear upgrade prompt and makes zero Belvo API calls.
- [ ] A Belvo webhook for a completed link triggers a transaction pull, idempotently, for active/Pro/non-closed-budget accounts only; a webhook for a lapsed-Pro or closed-budget account's link is a silent no-op.
- [ ] A Belvo Link whose status goes non-`valid` flips the local row to `consent_expired`, surfaced the same way GoCardless's expired consent already is; a manual refresh on it returns a clear re-connect message instead of a doomed API call.
- [ ] Re-linking the same institution while a `consent_expired` row exists reconciles onto it (by institution + last4 match) rather than creating an orphaned duplicate, when Belvo returns a matching account.
- [ ] Disconnecting a Belvo account (REST + chat) calls Belvo's delete endpoint, marks it locally disconnected, and preserves historical transactions.
- [ ] Existing #303/#320 Stripe and GoCardless tests all still pass unchanged — this ticket only adds a third `provider` match arm, never touches the existing two providers' code paths.
- [ ] All new pure logic (currency-fallback-by-country, amount normalization, last4/institution reconciliation decision, webhook Basic-auth check, offline chat-router country-phrase extraction) is unit tested; DB/HTTP-touching flows have `#[ignore]`+`wiremock` integration tests mirroring the existing two providers' style.

## 4. Scope

**In scope**: one migration (widen `provider` CHECK + new `belvo_link_sessions` table); `bank_provider.rs` (`Provider::Belvo`, country mapping, supported-countries list); `backend/src/belvo.rs` (widget-token minting, complete, sync, webhook handler, refresh, disconnect, require_pro); `bank_linking.rs` new `"belvo"` dispatch arms; new REST endpoints (start/complete for Belvo; no institutions-list endpoint needed, per Assumption 2); new public webhook route; chat action extension (`LINK_BANK_ACCOUNT` Belvo branch, two new `ChatResponse` fields, system-prompt + offline-router country coverage); frontend (widget-loader helper, country-select entries, chat-inline widget rendering, i18n); AGENTS.md documentation; tests.

**Out of scope**: countries beyond Mexico/Brazil; any FX conversion or multi-currency aggregation/display beyond storing `currency` per row; institution-logo/branding UI beyond what Belvo's own widget already renders; a scheduled poll job (Belvo has real webhooks, unlike GoCardless); building a generic `dyn BankProvider` trait-object system; retrying/backfilling transaction history beyond Belvo's own default lookback; admin console changes; marketing site changes.

## 6. Error Handling & Edge Cases

- Unsupported country (chat or REST) → 400 / clarifying question, no Belvo call.
- Widget token mint failure (Belvo API error, missing `BELVO_SECRET_ID`/`BELVO_SECRET_PASSWORD`) → 502/503, logged, mirrors both existing providers' credential/upstream-failure convention.
- `complete_link_session` session not found, or found but `budget_id`/`user_id` mismatch, or Belvo Link's `external_id` doesn't match the session id → 404/403 (anti-replay), mirrors GoCardless's session-mismatch handling.
- Already-`completed` session resubmitted → 409, no double-import.
- Cross-budget re-link of an already-linked `provider_account_id` → 409, same guard both existing providers use.
- Belvo Link status non-`valid` detected (webhook or sync response) → local status flips to `consent_expired`, no error surfaced synchronously (same as GoCardless's poll-detected expiry — surfaced next time the user views/refreshes).
- Manual refresh on a `consent_expired` account → clear 409-with-message before any Belvo call, same as GoCardless.
- Manual refresh/disconnect on a nonexistent/foreign account id → 404, same as both existing providers.
- Closed budget → every mutating path (start link, complete link, manual refresh, webhook-triggered sync) no-ops/rejects, mirroring the existing closed-budget guard exactly.
- Webhook with an unrecognized/missing Basic-auth header → 401, logged, no data pulled.
- Webhook whose `link_id` matches no `linked_accounts` row → silent 200 no-op (stale/abandoned session or a Link we never completed).
- Belvo's `POST /api/transactions/` returns "not ready yet" (202-class, no body data) → clean `Ok(0)` no-op, not an error; the next webhook or manual refresh completes it.

## 7. Testing Approach

- Unit tests (no DB/HTTP): `Provider::for_country`/`supported_countries` (Belvo cases), currency-fallback-by-country, `normalize_amount`, last4/institution reconciliation decision function, webhook Basic-auth check (accept/reject), offline chat-router MX/BR phrase extraction.
- `#[ignore]`+`wiremock` DB-integration tests, mirroring `gocardless.rs`'s/`financial_connections.rs`'s existing suites: Pro-gate rejection (zero Belvo calls made), full link→sync happy path (widget-token mint → complete → transactions imported with correct currency), idempotent re-sync, Link-status-invalid detection flipping to `consent_expired`, reconciliation-onto-existing-row on re-link, disconnect calling Belvo's delete endpoint first, closed-budget guards on every mutating path, webhook double-checking Pro/closed-budget before pulling, webhook auth rejection.
- A migration-only smoke: run the new migration against a #320-seeded DB, confirm existing Stripe/GoCardless rows are unaffected and a `'belvo'` provider value is now accepted by the CHECK constraint.
- Frontend: `linkedAccounts.test.js` gains Belvo widget-loader/complete-call cases; component test for the country-select Belvo entries and the widget `onSuccess` → complete flow.

## 8. Risks & Open Questions

- **Every concrete Belvo API shape claimed in this spec is documentation-derived, not independently verified against a live Belvo sandbox account in this environment** — the token-mint request/response, `/api/links/:link_id/`, `/api/accounts/?link=`, `/api/transactions/`'s "ready vs. not-ready" response shape, and the widget script's callback signature are all taken from Belvo's public docs. Since this ticket's tests run against `wiremock` (validating this codebase's handling of the *assumed* shape, not Belvo's actual live behavior), a systemic misunderstanding of the real API would pass every test here and only surface against a live/sandbox account during rollout — same caveat #320's GoCardless spec carried for its own API claims, called out here as a single top-level risk rather than scattered per-assumption.
- **Webhook authentication scheme is inferred from Belvo's documented "optional Basic-auth header on webhook registration" feature, not verified against a live Belvo sandbox account in this environment** (Assumption 7). If Belvo's actual delivered header shape differs (e.g. a dedicated signature header instead), the webhook auth check needs a follow-up fix — flagged explicitly so it isn't silently assumed correct once shipped; the out-of-band step of registering the webhook URL + credentials in the Belvo dashboard is an ops task outside this ticket's code.
- **Reconciliation without IBAN (last4 + institution match) is a best-effort heuristic**, same class of limitation #320 already documented for GoCardless's IBAN-based version — some banks may reuse `last4` across accounts, or Belvo may not expose a stable `institution_id` for every institution; a false-negative match creates a cosmetic duplicate row, never data loss.
- **Belvo sandbox behavior may differ from documented production behavior** for Link status transitions and the "not ready yet" transactions-endpoint response shape — the `wiremock`-based tests validate this codebase's handling of documented response shapes, not live sandbox parity (same caveat both existing providers' specs carry).
- **No scheduled poll job for Belvo is a deliberate scope decision, not an oversight** — if Belvo's webhook delivery ever proves unreliable in production, a follow-up poll-job ticket (mirroring GoCardless's) would be the fix; out of scope here since Belvo's product does provide real webhooks.
- **Widget DOM-mounting mode is unverified against a live account.** The frontend calls `createWidget(accessToken, config).build()` programmatically (no container/selector argument, per Belvo's own documented config shape) rather than using Belvo's alternative static-integration pattern (a `<script src="...">` tag paired with a conventional `<div id="belvo">`, which some of Belvo's own docs/examples show). Final-review research turned up references to that static `#belvo` div convention alongside the exact CDN URL this codebase uses, which raises a real (if unconfirmed) possibility that the programmatic `.build()` call may still expect a specific existing container id/element to render into, rather than fully self-managing a floating overlay as assumed. This codebase's two Svelte components render a small "Connecting…" loading message instead of a placeholder div implying an unverified mount contract (code review fix, nels#322) — correct either way, but the underlying question of whether `.build()` needs a `#belvo`-id element present in the DOM to actually render anything is only resolvable against a live Belvo sandbox account, which this development environment does not have. **Recommended before/shortly after this ships**: a manual smoke test against a real Belvo sandbox account confirming the widget overlay actually appears when `belvoWidgetActive` flips true; if it doesn't, the fix is almost certainly adding a `<div id="belvo"></div>` back (this time because the real API needs it by convention, not because this codebase mistakenly assumed it did).
