# Spec: Link bank accounts via Stripe Financial Connections (nels#303)

## 1. Brief (verbatim from the ticket)

**As a** Nels Pro subscriber
**I want** to securely link my bank account(s) via Stripe Financial Connections
**So that** my transactions are imported automatically instead of me having to log every expense by hand, giving me a fuller, more accurate picture of my spending to take control of my financial well-being.

**Acceptance Criteria**
- A subscriber with an active/trialing subscription (`billing::user_is_pro`) can start a Financial Connections session and link one or more bank accounts to a budget.
- A non-Pro user is blocked from starting the link flow and is shown an upgrade prompt instead.
- Once linked, the account's transactions are pulled from Stripe and appear as `transactions` rows (existing table, #195) attributed to the linked account, categorized where possible and otherwise landing in an "Uncategorized" bucket for the user to assign.
- Transactions refresh automatically on Stripe's `financial_connections.account.refreshed_transactions` webhook (no manual "sync" step required in the common case), and a manual refresh action is also available.
- A user can view which accounts are linked and disconnect (unlink) an account; disconnecting stops future imports but does not delete previously-imported transactions.
- The linking flow and "what's linked" status are reachable from the chat co-pilot (consistent with our chat-first UX), not just a buried settings page.
- If a user's subscription lapses (status leaves active/trialing), automatic transaction refresh stops for their linked accounts until they resubscribe; already-linked accounts are not silently deleted.

**Notes**: Pro-gated. Builds on `backend/src/billing.rs` (#25) and `transactions` table (#195). No separate expense-tracking system. Prerequisite for the multi-country bank-sync epic (#324).

## 2. Assumptions

1. **Stripe integration style mirrors `billing.rs` exactly**: hand-rolled `reqwest` form-encoded calls (no `async-stripe` crate), a module-local `stripe_post`/`stripe_get`/`stripe_delete`-equivalent set of helpers, `STRIPE_API_BASE` test seam, `#[ignore]`+`wiremock` DB-integration tests. New module `backend/src/financial_connections.rs`.
2. **Frontend must use Stripe.js.** Financial Connections has no hosted-redirect flow like Checkout — the client MUST call `stripe.collectFinancialConnectionsAccounts({clientSecret})` from `@stripe/stripe-js` (a new frontend dependency) using a publishable key shipped in the frontend bundle via `VITE_STRIPE_PUBLISHABLE_KEY` (publishable keys are not secret; this mirrors how every Stripe Elements integration ships the pk to the client).
3. **Session completion is verified server-side, never trusted from the client** — mirrors billing.rs's "webhooks are the only source of truth" spirit. After `collectFinancialConnectionsAccounts` resolves client-side, the frontend calls our backend with only the `session_id`; the backend re-fetches `GET /v1/financial_connections/sessions/:id` with our own secret key to get the authoritative account list, and confirms the session's `account_holder.customer` matches the caller's own Stripe customer id before persisting anything (prevents a user replaying another user's session id).
4. **One Stripe secret key (`STRIPE_SECRET_KEY`), one Stripe account.** Financial Connections events are delivered to their own webhook endpoint (Stripe supports multiple endpoints per account with independent signing secrets), so a NEW route `POST /api/financial-connections/webhook` is added, public, with its own `STRIPE_FC_WEBHOOK_SECRET` env var — analogous to, but separate from, `billing.rs`'s `/api/billing/webhook` / `STRIPE_WEBHOOK_SECRET`. Reuses `billing::verify_stripe_signature` / `billing::StripeEvent` (already `pub`).
5. **`billing::ensure_customer` is widened to `pub(crate)`** so linking reuses the SAME Stripe Customer as billing (one customer per user, never two) instead of duplicating customer-creation logic. This mirrors the precedent of widening `gemini_api_base()` to `pub(crate)` for `reports.rs` (#283).
6. **Schema**: new `linked_accounts` table (one row per linked Stripe Financial Connections Account, scoped to the budget it was linked into) plus two new nullable columns on `transactions`: `external_account_id UUID REFERENCES linked_accounts(id) ON DELETE SET NULL` (NULL = manually-entered, as today) and `stripe_transaction_id TEXT` with a `UNIQUE` constraint (Stripe's `fctxn_...` id — the idempotency key that lets repeated syncs skip rows already imported, and lets a user's manual edits to an imported row survive a later re-sync since we only ever `ON CONFLICT DO NOTHING`). No separate `import_source` column: `external_account_id IS NOT NULL` alone distinguishes an imported row from a manual one — a third column would be redundant (YAGNI; revisit only if/when #324 adds a second import source and "which source" genuinely needs its own field).
7. **"Categorized where possible" = a cheap, honest v1 heuristic, not ML.** Stripe's Financial Connections `transaction` object carries no spending-category field (unlike Plaid's personal-finance-category). v1 categorization: case-insensitive substring match of each of the budget's existing category **names** against the transaction `description`; first match (by category creation order) wins; no match → `category_id = NULL` ("Uncategorized"). This is documented as a known, narrow heuristic — smarter (embedding-based) categorization is explicitly out of scope and left as a natural follow-up (matches this codebase's existing precedent of documenting narrow-but-honest v1 scope, e.g. #228's fund-catch-up limitation note in AGENTS.md).
8. **"Uncategorized" is a display convention, not a new column/value.** `category_id IS NULL` already means "no category" today (nullable FK, `ON DELETE SET NULL`); the frontend/chat surfaces `NULL` as "Uncategorized" for imported rows specifically. No schema change needed for this beyond what already exists.
9. **Amount sign/direction**: Stripe's FC transaction `amount` is an integer in cents; sign convention is not reliably documented as debit-negative/credit-positive across all account types. Since this codebase already stores `transactions.amount` as a **positive magnitude** regardless of direction (see `init.sql` comment: "Positive for expense/savings/income; type determined by category"), imports store `abs(amount) / 100.0`. Because imported transactions start `category_id = NULL` (no `category_type` to infer direction from) this is consistent with the existing model and does not need a new "direction" column. This is called out as a limitation: a future issue may want a raw signed amount for reconciliation, out of scope here.
10. **Permission model for the new REST/chat actions**: mirrors `ADD_TRANSACTION`'s Edit-or-Owner requirement (a shared "household" collaborator with Edit access should be able to manage the linked bank feed, same as they can add manual transactions) for **start link / complete link / manual refresh / disconnect**. **Viewing** the linked-accounts list requires only budget View access (same as any other budget read). This is a judgment call, documented here for review.
11. **Pro-gating applies specifically to actions that consume the Stripe FC data pull**: starting a NEW link session and triggering a manual refresh both return `402 Payment Required` (chat: an upgrade-prompt `response_text`, no Stripe call made) for a non-Pro caller. **Viewing already-linked accounts and disconnecting one are NOT Pro-gated** — a user whose subscription lapsed must still be able to see what's linked and disconnect it (AC: "already-linked accounts are not silently deleted", i.e. the user keeps control of their own data regardless of billing state).
12. **Auto-refresh gating on subscription lapse** happens in the **webhook handler**, not by disabling a scheduled job (there is no scheduled job — refresh is Stripe-webhook-driven, not a `main.rs` hourly ticker like rollover/fund advancement). On `financial_connections.account.refreshed_transactions`, the handler resolves the linked account's owning user and checks BOTH `linked_accounts.status == 'active'` AND `billing::user_is_pro` before pulling new transactions; if either check fails, it logs and no-ops (200, so Stripe does not retry), leaving `linked_accounts` and existing `transactions` untouched — satisfying "stops auto-refresh without deleting accounts." The `status == 'active'` check is belt-and-suspenders alongside Assumption 15's actual Stripe-side disconnect call: webhook delivery/ordering is not guaranteed, so a `refreshed_transactions` event could in principle arrive after a local disconnect but before (or instead of) Stripe's own `disconnected` event — the local status check ensures a disconnected account never gets re-synced regardless of event ordering.
13. **Chat co-pilot surface**: four new `AiStructuredResponse.action` values — `LINK_BANK_ACCOUNT`, `LIST_LINKED_ACCOUNTS`, `UNLINK_BANK_ACCOUNT`, `REFRESH_BANK_ACCOUNT` — following the exact existing pattern (`AiActionParams` field(s), `required_perm_for_action` entries, a dispatch match arm, system-prompt directive additions, offline-router phrase fallbacks). `UNLINK_BANK_ACCOUNT` takes a fuzzy `account_match` locator string (institution name / display name / last4 substring, case-insensitive) mirroring `transaction_match`'s locator pattern for `EDIT_TRANSACTION`/`DELETE_TRANSACTION` — but a simple substring match over the (typically ≤5) linked accounts, not an embedding search (no need for semantic search over so few, short, structured strings).
14. **`LINK_BANK_ACCOUNT` via chat returns a `client_secret`, not a URL.** Since there is no hosted redirect for Financial Connections, the chat response payload needs a way to carry the `client_secret` to the frontend so `App.svelte` can open the Stripe.js modal. Pinned by reading `backend/src/rag.rs`: the chat envelope is `pub struct ChatResponse` (rag.rs ~line 94), which already carries several `#[serde(skip_serializing_if = "Option::is_none")]` advisory fields for exactly this kind of "frontend, do something extra" signal (e.g. `open_insights`, `pending_deletion`). We add `financial_connections_client_secret: Option<String>` to it the same way, rather than overloading `response_text`.
15. **Disconnecting is a real Stripe-side call, not just a local flag flip.** `disconnect_linked_account` calls `POST v1/financial_connections/accounts/:id/disconnect` FIRST (revokes Stripe's/the bank's access to that account) and only marks the local row `status = 'disconnected'`/`disconnected_at = now()` after that call succeeds (idempotent — Stripe returns the account with `status: "disconnected"` even if already disconnected, so a repeat call is harmless, mirroring `billing::stripe_delete`'s already-canceled tolerance). This closes the gap where a merely-local flag flip would leave the account still live on Stripe's side, able to keep firing `refreshed_transactions` webhooks. The webhook ALSO handles `financial_connections.account.disconnected` (fired independently if the bank itself revokes access, e.g. from the bank's own portal) by marking the local row `status = 'disconnected'` the same way — so a bank-initiated disconnect also correctly stops future sync, not just our own UI-initiated one.
16. **Countries filter**: `filters[countries][]=US` only for v1 (this repo/company is US-only today per existing billing/marketing copy); #324 (the multi-country epic this ticket is a prerequisite for) is explicitly where broader country support lands.
17. **No marketing site changes.** This is an authenticated-app feature; `/marketing` is out of scope.

## 3. Goal & Success Criteria

Pro subscribers can link one or more bank accounts to a budget via Stripe Financial Connections, see their bank transactions land automatically in the existing `transactions` table (categorized when a cheap heuristic matches, else "Uncategorized"), refresh either automatically (webhook) or manually, and view/disconnect linked accounts — all reachable from the chat co-pilot as well as a small settings panel. Non-Pro users are blocked from linking/refreshing with a clear upgrade prompt. A subscription lapse pauses auto-refresh without deleting any data.

Success criteria:
- [ ] A Pro user can complete an end-to-end link (session → Stripe.js modal → complete → `linked_accounts` row persisted, initial sync attempted though it may legitimately import 0 rows pending Stripe's async pull) via REST and the result is visible via chat's `LIST_LINKED_ACCOUNTS`.
- [ ] A non-Pro user's attempt to start a link (REST or chat) is rejected with a clear upgrade-prompt message and makes zero Stripe API calls.
- [ ] The `financial_connections.account.refreshed_transactions` webhook, when the owning user is Pro, imports new transactions idempotently (no duplicates on redelivery) and skips already-imported rows without clobbering user edits.
- [ ] The SAME webhook, when the owning user is NOT Pro (lapsed), no-ops without deleting `linked_accounts` or `transactions`.
- [ ] A manual refresh action (REST + chat) is available and Pro-gated identically to linking.
- [ ] Disconnecting (REST + chat) marks the account inactive, stops future imports, and does not delete historical `transactions` rows; it works regardless of the caller's current Pro status.
- [ ] `financial_connections.account.disconnected` webhook also marks the row disconnected (bank-initiated disconnect).
- [ ] All new pure logic (categorization heuristic, permission table entries, webhook event→action mapping, amount normalization) is unit tested; DB-touching flows have `#[ignore]` integration tests mirroring `billing.rs`'s style.

## 4. Scope

**In scope**: backend migration + `financial_connections.rs` module + REST endpoints + webhook route + chat actions + minimal frontend (Stripe.js dependency, a Linked Accounts panel, chat-triggered link modal, upgrade-prompt surfacing) + AGENTS.md documentation update + tests.

**Out of scope**: the multi-country epic (#324) beyond a US-only v1; ML/embedding-based categorization; balances/ownership permissions (only `transactions` permission is requested); a dedicated new "budget for imported transactions only" concept (explicitly ruled out by the ticket — reuses the existing `transactions` table); marketing site; admin console changes; retrying/backfilling historical transactions beyond what Stripe returns by default (no explicit historical-window param in v1 — accept Stripe's default lookback).

## 5. Architecture

- **Migration** `backend/migrations/<ts>_financial_connections.sql`:
  - `linked_accounts` table: `id UUID PK`, `budget_id UUID NOT NULL REFERENCES budgets(id) ON DELETE CASCADE`, `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE` (the linker — for audit/ownership even though budget_id is the scoping key), `stripe_account_id TEXT NOT NULL UNIQUE` (`fca_...`), `stripe_customer_id TEXT NOT NULL`, `institution_name TEXT`, `display_name TEXT`, `last4 TEXT`, `category TEXT`, `subcategory TEXT`, `status TEXT NOT NULL DEFAULT 'active'` (CHECK `'active'|'disconnected'`), `last_synced_at TIMESTAMPTZ`, `disconnected_at TIMESTAMPTZ`, `created_at`/`updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
  - `transactions` additions: `external_account_id UUID REFERENCES linked_accounts(id) ON DELETE SET NULL`, `stripe_transaction_id TEXT`, `UNIQUE INDEX transactions_stripe_transaction_id_idx ON transactions (stripe_transaction_id) WHERE stripe_transaction_id IS NOT NULL` (partial: a plain `UNIQUE` on a nullable column already permits multiple NULLs with no collision, so the `WHERE` clause isn't needed for correctness — it's used here to keep the index smaller by excluding the (majority) manually-entered rows that will never carry a `stripe_transaction_id`).
  - `db.rs`: new `LinkedAccount` struct (`FromRow`); `Transaction` struct gains the two new `Option` fields.

- **`backend/src/financial_connections.rs`** (new module), following `billing.rs`'s shape:
  - Local `stripe_post`/`stripe_get_json` helpers (same `STRIPE_API_BASE`/`STRIPE_SECRET_KEY` env reads as billing.rs — duplicated per this repo's per-module convention, not shared).
  - `pub async fn create_link_session(pool, user_id, budget_id) -> Result<SessionResponse, (StatusCode, String)>`: `check_permission` (Edit-or-Owner) → `billing::user_is_pro` gate (402) → `billing::ensure_customer` → `POST v1/financial_connections/sessions` (`account_holder[type]=customer`, `account_holder[customer]=<cid>`, `permissions[]=transactions`, `filters[countries][]=US`) → returns `{client_secret}` (never logged).
  - `pub async fn complete_link_session(pool, user_id, budget_id, session_id) -> Result<Vec<LinkedAccountResponse>, ..>`: same perm+Pro gate → `GET v1/financial_connections/sessions/:id` → verify `account_holder.customer` == caller's own customer id (403 on mismatch — anti-replay) → for each `accounts.data[]` item, `INSERT ... ON CONFLICT (stripe_account_id) DO UPDATE` (idempotent re-link) → for each newly-linked account, call `sync_account_transactions` once inline (initial import) → return the persisted rows.
  - `pub async fn sync_account_transactions(pool, linked_account) -> Result<u64, sqlx::Error>`: `GET v1/financial_connections/transactions?account=...` (paginated via `starting_after`), for each row: `guess_category_id` (pure helper — substring match against the budget's category names) then `INSERT INTO transactions (..., external_account_id, stripe_transaction_id) VALUES (...) ON CONFLICT (stripe_transaction_id) DO NOTHING`; updates `linked_accounts.last_synced_at`. Returns count imported. **Note**: Stripe's Financial Connections transaction data is populated asynchronously after a session completes — the FIRST call to this function (from `complete_link_session`) may legitimately return 0 rows if Stripe hasn't finished the initial pull yet; the real data typically lands moments later via the `refreshed_transactions` webhook. Callers/tests must not assume a non-empty result immediately after linking.
  - `pub(crate) fn guess_category_id(description: &str, categories: &[(Uuid, String)]) -> Option<Uuid>` — PURE, unit-tested.
  - `pub async fn refresh_linked_account(pool, user_id, budget_id, account_id) -> Result<(), (StatusCode, String)>` (manual refresh, both REST and chat): perm+Pro gate, then `POST v1/financial_connections/accounts/:id/refresh` with `features[]=transactions`. This is intentionally ASYNC, matching Stripe's own design: it kicks off a fresh bank pull and returns immediately (no new transactions yet); the actual import happens moments later when Stripe's `financial_connections.account.refreshed_transactions` webhook fires and the SAME `sync_account_transactions` path runs. Manual refresh and webhook-driven auto-refresh are thus literally the same underlying mechanism — manual refresh just proactively asks Stripe to check now instead of waiting for Stripe's own schedule. The REST/chat response says "refresh requested" rather than reporting an import count.
  - `pub async fn disconnect_linked_account(pool, user_id, budget_id, account_id) -> Result<(), (StatusCode, String)>`: perm gate (NOT Pro-gated — see Assumption 11) → `POST v1/financial_connections/accounts/:id/disconnect` (idempotent: Stripe returns the account object with `status: "disconnected"` whether or not it already was) → on success, set local `status='disconnected'`, `disconnected_at=now()`. The Stripe call happens BEFORE the local write so a failed Stripe call never leaves us believing an account is disconnected when Stripe still considers it live.
  - REST handlers: `start_link`, `complete_link`, `list_linked_accounts`, `refresh_linked_account` (handler wraps the fn above), `disconnect_linked_account` (handler wraps the fn above) (axum handlers, `State<AppState>` + `Path`/`Extension`/`Json`, matching every other handler's signature style in `budget.rs`).
  - `pub async fn webhook(State, HeaderMap, Bytes) -> Result<StatusCode, ..>`: verifies signature with `STRIPE_FC_WEBHOOK_SECRET` (reuses `billing::verify_stripe_signature`/`StripeEvent`), matches `financial_connections.account.refreshed_transactions` (looks up the local row by `stripe_account_id`; requires BOTH `status == 'active'` AND the owning user is Pro before calling `sync_account_transactions` — see Assumption 12) and `financial_connections.account.disconnected` (mark row disconnected, idempotent); everything else → 200 ignored, mirroring `billing::webhook`'s shape exactly.
  - `pub(crate) fn map_fc_webhook_event(event: &StripeEvent) -> Option<FcAccountEvent>` — PURE mapping function (mirrors `billing::apply_subscription_event`), unit-tested independent of the DB/HTTP handler.

- **`main.rs` wiring**: `mod financial_connections;`, new protected routes under `.route("/budgets/:id/linked-accounts/session", post(...))` etc., new public `financial_connections_public_routes` nest for `/financial-connections/webhook` (mirrors `billing_public_routes`).

- **`billing.rs`**: widen `async fn ensure_customer` → `pub(crate) async fn ensure_customer`.

- **`rag.rs`**: `AiStructuredResponse.action` gains 4 new string values; `AiActionParams` gains `account_match: Option<String>` (reuses none of the existing fields — a fresh field, since none fit); `required_perm_for_action` gains 4 entries; a dispatch match arm per action (near the existing `ADD_TRANSACTION`/`DELETE_TRANSACTION` arms). `LINK_BANK_ACCOUNT`'s arm calls `financial_connections::create_link_session` and sets the new `ChatResponse.financial_connections_client_secret` field — note `complete_link_session` is NOT chat-reachable, since completing a link needs a client-side Stripe.js round trip (the chat action only STARTS the session and hands the `client_secret` back through the chat response for the frontend to drive the modal, exactly like the REST `start_link` endpoint does). `LIST_LINKED_ACCOUNTS` / `UNLINK_BANK_ACCOUNT` / `REFRESH_BANK_ACCOUNT`'s arms call the corresponding `financial_connections::` functions directly (no client round trip needed). System-prompt directive addition (next numbered rule after the existing list); offline-router phrase entries.
  - Chat response envelope: `rag.rs`'s `pub struct ChatResponse` (~line 94) gains `#[serde(skip_serializing_if = "Option::is_none")] pub financial_connections_client_secret: Option<String>`, set only by the `LINK_BANK_ACCOUNT` dispatch arm.

- **Frontend** (`frontend/`):
  - `pnpm add @stripe/stripe-js`; new `VITE_STRIPE_PUBLISHABLE_KEY` (frontend `.env`/`.env.example`).
  - `src/lib/linkedAccounts.js` (or `.svelte` + extracted pure helpers file, matching the `*.test.js`-alongside-logic convention already used for `budgetDisplay.js`-style modules) — `fetchApi` calls for list/refresh/disconnect, and a `startLinkFlow(budgetId)` helper that: POSTs session → `loadStripe(pk).collectFinancialConnectionsAccounts({clientSecret})` → POSTs complete with the returned session id.
  - `Settings.svelte` (or a new `LinkedAccounts.svelte` panel included from Settings): list + "Link a bank account" button (Pro-gated — shows upgrade CTA reusing the existing `startCheckout()` handler in `App.svelte` when not Pro) + disconnect + manual-refresh buttons.
  - `App.svelte` chat-response handling: if the chat response carries `financial_connections_client_secret`, drive the same `startLinkFlow`'s Stripe.js-modal + complete-call sequence (factored so REST-button and chat share one code path).

## 6. Error Handling & Edge Cases

- Missing `STRIPE_SECRET_KEY`/`STRIPE_FC_WEBHOOK_SECRET` → 503 "Billing is not configured" (mirrors `billing.rs`'s fail-loud convention), never a silent no-op.
- Non-Pro caller hits start-link or manual-refresh → 402 with a clear message; chat mirrors with an upgrade-prompt `response_text` and takes no action (no Stripe call).
- Session-id replay / customer mismatch on complete → 403, nothing persisted.
- Stripe 5xx / network error on any call → 502 "Billing provider error" (mirrors `billing.rs`), never swallowed.
- Re-delivered webhook (same event, or a re-import of already-seen transactions) → idempotent no-op via `ON CONFLICT DO NOTHING` on `stripe_transaction_id`; `linked_accounts` re-link (`ON CONFLICT (stripe_account_id) DO UPDATE`) does not create duplicate rows.
- Webhook for an unknown `stripe_account_id` (linked in a different environment/DB) → logged at `warn`, 200 (no retry storm), mirrors `billing.rs`'s "unknown customer" handling.
- Disconnect is idempotent — disconnecting an already-disconnected account is a 200 no-op, not an error (matches the archive/unarchive precedent in AGENTS.md §6).
- `UNLINK_BANK_ACCOUNT`/chat locator matches zero or >1 accounts → a clarifying `response_text`, no mutation (mirrors `DELETE_TRANSACTION`'s locator-ambiguity handling).
- Budget deletion cascades to `linked_accounts` (`ON DELETE CASCADE`) but transactions already imported keep their `external_account_id` pointing at a row that's now gone only if the BUDGET itself is deleted (which cascades transactions too, so this is moot) — no orphan risk in practice; disconnect alone never deletes the `linked_accounts` row, only flips `status`.

## 7. Testing Approach

- `cargo test` (backend): unit tests for `guess_category_id`, `map_fc_webhook_event`, updated `required_perm_for_action`/`is_chat_action_authorized` tables, amount normalization; `#[ignore]` DB+wiremock integration tests (mirroring `billing.rs`'s `test_pool()`/`mk_user()`/`set_stripe_env()` helpers) for: full link → sync → idempotent re-sync, Pro-gate rejection, webhook-driven refresh (Pro vs lapsed), manual refresh calls Stripe's `/refresh` endpoint and responds with "requested" (not an import count) while itself remaining Pro-gated, disconnect calls Stripe's disconnect endpoint AND stops future sync, a `refreshed_transactions` webhook arriving for an already-locally-disconnected account is a no-op (the belt-and-suspenders `status == 'active'` check), disconnect webhook from bank-side.
- Frontend `pnpm test` (vitest): pure-logic tests for `linkedAccounts.js` helpers (request shaping, response parsing) mirroring the existing `*.test.js` convention; Stripe.js itself is mocked/stubbed (never call the real SDK in tests).
- `cargo check` / `cd frontend && pnpm run build` as the compile-gate for every task.

## 8. Risks & Open Questions

- Stripe's FC transaction `amount` sign convention is not fully nailed down from docs alone; the abs()-value decision (Assumption 9) is conservative but should be spot-checked against a real sandbox transaction during implementation if `STRIPE_SECRET_KEY` sandbox creds are available in this dev environment (if not, ship as documented and flag as a follow-up).
- Whether the FE should show the upgrade-prompt as a full modal vs. inline text is a judgment call left to the implementer to match existing `Settings.svelte` visual conventions.
