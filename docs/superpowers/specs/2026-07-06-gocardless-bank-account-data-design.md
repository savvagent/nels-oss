# Spec: Link bank accounts via GoCardless Bank Account Data (nels#320)

## 1. Brief (verbatim from the ticket)

**As a** Nels Pro subscriber banking in the UK, France, Germany, Italy, Spain, Denmark, Finland, or Norway
**I want** to link my bank account via GoCardless Bank Account Data (the single aggregator covering all 8 of these countries)
**So that** my transactions import automatically, matching the experience #303 provides for US subscribers via Stripe.

**Acceptance Criteria**
- A Pro subscriber (`billing::user_is_pro`) with a bank account in any of these 8 countries can start a GoCardless Bank Account Data consent flow and link one or more accounts to a budget.
- A non-Pro user is blocked from starting the link flow and shown an upgrade prompt, same as #303.
- Linked accounts' transactions import into the existing `transactions` table, attributed to the user's active budget at import time. Imported rows record a `currency` (ISO 4217) column — no FX conversion is performed; budget-level multi-currency display/aggregation is explicitly out of scope for this ticket.
- Transactions refresh automatically where GoCardless provides webhook/event notifications, plus a manual refresh action. GoCardless Bank Account Data consent windows expire under PSD2 (typically ~90 days) and require periodic re-consent — the refresh flow surfaces and handles re-consent explicitly rather than silently failing once a consent lapses.
- A user can view linked accounts and disconnect one; disconnecting stops future imports without deleting previously-imported transactions.
- Linking and "what's linked" status are reachable from the chat co-pilot. Because GoCardless's flow is redirect-based (not an embeddable modal like Stripe.js), the chat action initiates the redirect and the user lands back in the app after consent completes.
- If a subscription lapses, automatic refresh stops for GoCardless-linked accounts without deleting them, same as #303.

**Notes**: Prerequisite #303 ships the `linked_accounts` table, webhook-dispatch pattern, and chat actions this story extends. As the first non-US provider, this story introduces the `linked_accounts.provider`/`provider_account_id` generalization and a shared `BankProvider` interface so `rag.rs`, webhook dispatch, and the frontend don't special-case providers — refactoring the existing Stripe code onto the new interface without changing its behavior.

## 2. Assumptions

1. **GoCardless Bank Account Data API** (formerly Nordigen; `https://bankaccountdata.gocardless.com/api/v2/`), a JSON REST API distinct in shape from Stripe's form-encoded API — a new module `backend/src/gocardless.rs` owns its own `reqwest` client, mirroring `financial_connections.rs`'s "own HTTP helpers, own env-driven test seam" convention, but JSON-bodied (`gocardless_post`/`gocardless_get`/`gocardless_delete` taking/returning `serde_json::Value`) rather than form-encoded.
2. **Auth is a cached bearer token, not a static secret key.** `POST /token/new/ {secret_id, secret_key}` (env `GOCARDLESS_SECRET_ID`/`GOCARDLESS_SECRET_KEY`) returns `{access, access_expires}` (~24h). A process-wide `tokio::sync::RwLock<Option<CachedToken>>` caches it, refreshing lazily when expired (a fixed 60s safety margin before `access_expires`) — no scheduled refresh job, matching this codebase's "no unnecessary schedulers" bias (§0.5 discovery: the only existing scheduled jobs are the hourly rollover/fund ticker in `main.rs`).
3. **No webhooks in GoCardless Bank Account Data** — this product has no per-transaction/per-account webhook, unlike Stripe Financial Connections. This is a genuine capability gap, not an oversight: the AC's "webhook/event notifications where available" is satisfied by NOT wiring a GoCardless webhook route and instead adding a **scheduled poll job** (`gocardless::poll_active_accounts`, hourly-family ticker in `main.rs`, default every `GOCARDLESS_POLL_INTERVAL_HOURS=8`) that syncs every `active` GoCardless-linked account whose owner is still Pro and whose budget isn't closed — the same gating semantics as the Stripe webhook handler, just poll-driven instead of push-driven. **Rate-limit accounting**: each poll cycle makes exactly ONE GoCardless call per account (the transactions pull itself — see Assumption 10, which folds expiry detection into that same call instead of a separate status check), so the 8h default is 3 calls/account/day, leaving headroom under GoCardless's ~4-calls/day/account guidance for the initial link-time sync and any manual refreshes the same day. This asymmetry (Stripe = webhook-pushed, GoCardless = polled) is documented explicitly here and in AGENTS.md so it reads as an intentional API-shape difference, not a missed unification.
4. **Redirect-based consent needs a server-persisted pending session**, unlike Stripe FC (whose `client_secret` alone round-trips the session identity via Stripe's own servers). New table `bank_link_sessions`, one row per pending GoCardless consent attempt:
   ```sql
   CREATE TABLE bank_link_sessions (
       id              UUID PRIMARY KEY,        -- also the value we embed as our own `gc_ref` query param (Assumption 17) — NOT sent to GoCardless as `reference`; see Assumption 5
       budget_id       UUID NOT NULL REFERENCES budgets(id) ON DELETE CASCADE,
       user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
       requisition_id  TEXT NOT NULL,            -- GoCardless's own requisition id, needed to re-fetch it server-side on completion
       agreement_id    TEXT,
       institution_id  TEXT NOT NULL,
       country         TEXT NOT NULL,
       status          TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','completed')),
       created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
   );
   ```
   After the user returns, the frontend calls our backend with this same `id` (as `gc_ref`), which looks up the pending row to recover `budget_id`/`user_id`/`requisition_id` before ever trusting the redirect. No TTL/cleanup job for stale `pending` rows in v1 — an abandoned session is a small, harmless orphan row (documented Risk, not a correctness issue).
5. **Consent flow, concretely.** We choose the exact redirect URL string handed to GoCardless — GoCardless does not append anything of its own to it, it redirects the user's browser to precisely the URL we registered — so we embed our own `bank_link_sessions.id` directly in that URL ourselves, avoiding any reliance on a GoCardless-appended parameter. `start_link_session` (Pro-gated, Edit-or-Owner, budget-not-closed — mirrors `create_link_session` exactly): inserts a `bank_link_sessions` row first (to get its `id`), creates a GoCardless End User Agreement (`POST /agreements/enduser/`; `access_valid_for_days` and `max_historical_days` both default 90 via `GOCARDLESS_ACCESS_VALID_DAYS`/`GOCARDLESS_MAX_HISTORICAL_DAYS` env, honoring the ticket's "~90-day PSD2" figure, each **clamped to the institution's own `transaction_total_days`** — fetched via `list_institutions`/looked up by `institution_id` — when that's smaller, since GoCardless rejects a request exceeding an institution's supported max), then a Requisition (`POST /requisitions/` with `redirect = "{APP_URL}/?gc_ref={session.id}"`, `reference = {session.id}` (also handed to GoCardless, purely as its own idempotency/lookup key — not what we rely on for round-tripping), `institution_id`, `agreement`), updates the row with the returned `requisition_id`, and returns `{redirect_url, reference: session.id}` to the caller. `complete_link_session` (same gates) takes `gc_ref`, looks up the `bank_link_sessions` row by id, verifies its `budget_id`/`user_id` match the caller (403 on mismatch — anti-replay, same spirit as Stripe's customer-id check) and its `status = 'pending'` (409 if already `'completed'` — no double-complete), re-fetches the requisition **server-side** via its stored `requisition_id`, and for each linked GoCardless account persists/updates a `linked_accounts` row, attempts an initial sync (best-effort, same as Stripe), and flips the session row to `'completed'`.
6. **Institution selection is a fuzzy text match, not a picker UI, in v1** — mirrors `UNLINK_BANK_ACCOUNT`'s existing `account_match` substring-locator pattern rather than building a new searchable-dropdown component. `gocardless::find_institution_id(country, query)` case-insensitive-substring-matches `query` against `GET /institutions/?country=<cc>` names; zero matches → a clear "couldn't find that bank" error; 2+ matches → an ambiguous-match error listing the candidate names (caller — both REST and chat — turns this into a clarifying question, mirroring the existing ambiguous-match UX elsewhere in this codebase). The frontend's REST-driven flow additionally offers a real `<select>` of the country's institutions (fetched via a new `GET .../gocardless/institutions?country=` endpoint) so a human never has to type an exact bank name — the fuzzy-match path exists specifically for the chat surface, which only has free text.
7. **Country → provider mapping is a static table, not user profile data.** No new `users.country` column: `bank_provider::Provider::for_country(cc) -> Option<Provider>` maps `"US" → Stripe`, `{"GB","FR","DE","IT","ES","DK","FI","NO"} → GoCardless`, anything else → `None`. The chat `LINK_BANK_ACCOUNT` action and the REST start-link request both require an explicit country code from the caller (chat: parsed from the user's message or asked for if absent/unsupported; REST: a required field) — this codebase has no stored user-country field anywhere today, and inferring one is out of scope.
8. **The shared `BankProvider` interface is enum dispatch, not a `dyn` trait object.** With exactly two providers and no plan for a third in this ticket, a `pub enum Provider { Stripe, GoCardless }` (`backend/src/bank_provider.rs`) plus a new orchestration module `backend/src/bank_linking.rs` whose functions (`list_linked_accounts`, `refresh_linked_account`, `disconnect_linked_account`, `sync_account_transactions`) each match on `linked_accounts.provider` **once**, at the top, and delegate to `financial_connections::*` (Stripe) or `gocardless::*` (GoCardless) — is preferred over introducing an `async-trait` dependency + `Arc<dyn BankProvider>` object-safety machinery for a closed, two-member set. This still satisfies the ticket's actual ask: `rag.rs`'s `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/`REFRESH_BANK_ACCOUNT` arms, the REST list/refresh/disconnect handlers, and the frontend's account-list rendering call ONE provider-agnostic function/shape each, with zero per-provider branching at those call sites. `LINK_BANK_ACCOUNT` (starting a NEW link) is the one call site that legitimately branches on provider, because Stripe's and GoCardless's start-link responses are different in kind (an opaque `client_secret` for a client-side SDK modal vs. a `redirect_url` for a full-page navigation) — documented here as an intentional, minimal exception, not a gap.
9. **Schema generalization, in one migration** (`backend/migrations/<ts>_gocardless_bank_account_data.sql`):
   - `linked_accounts.provider TEXT NOT NULL DEFAULT 'stripe' CHECK (provider IN ('stripe','gocardless'))` — every existing (#303) row backfills to `'stripe'` via the column default, no explicit `UPDATE` needed.
   - `stripe_account_id` → renamed to `provider_account_id` (`ALTER TABLE ... RENAME COLUMN`); the existing `UNIQUE` constraint/index is renamed alongside it for readability, not correctness (Postgres preserves the constraint through a column rename).
   - `stripe_customer_id` → renamed to `provider_ref` — generalizes "the provider-side parent reference used for anti-replay/ownership verification on completion": Stripe's value is the Stripe Customer id; GoCardless's is the Requisition id.
   - New nullable `consent_expires_at TIMESTAMPTZ` (GoCardless PSD2 expiry; always `NULL` for Stripe rows — Stripe FC sessions don't expire on this cadence in this codebase's model), nullable `country TEXT` (ISO 3166-1 alpha-2; always `NULL` for Stripe rows, since Stripe FC here is US-only), and nullable `institution_id TEXT` (GoCardless's own institution id, e.g. `MONZO_MONZ_GB`; always `NULL` for Stripe rows, which already have `institution_name` but no separate machine id) — `institution_id` is the field Assumption 11's reconciliation matches on (together with `budget_id`), since `institution_name` is free text and not guaranteed stable/exact across a re-consent.
   - `status` CHECK widened from `('active','disconnected')` to `('active','disconnected','consent_expired')` — `consent_expired` means "GoCardless says re-consent is needed"; `disconnected_at` stays `NULL` for it (only `'disconnected'` sets that column), so the existing `linked_accounts_status_disconnected_at_check` combined constraint needs no change.
   - `transactions.stripe_transaction_id` → renamed to `provider_transaction_id`. The existing index is **replaced**, not merely renamed: the old partial-unique index was on `provider_transaction_id` alone, which assumed a single globally-unique id space (true for Stripe's `fctxn_...` ids, NOT guaranteed for GoCardless's bank-assigned transaction ids). New index: `CREATE UNIQUE INDEX ON transactions (external_account_id, provider_transaction_id) WHERE provider_transaction_id IS NOT NULL` — scoped per linked account. Both `financial_connections.rs`'s and the new `gocardless.rs`'s `ON CONFLICT` targets change to `(external_account_id, provider_transaction_id) WHERE provider_transaction_id IS NOT NULL` accordingly (a safe generalization for Stripe too, since its ids are already globally unique — a superset, not a behavior change). The pairing CHECK constraint's expression follows the column rename automatically.
   - New nullable `transactions.currency TEXT` (ISO 4217). GoCardless imports set it from each transaction's own `transactionAmount.currency` field (no FX conversion, per AC). The Stripe sync path is also updated to write `'USD'` explicitly now that the column exists (Stripe FC in this codebase is US-only, so this is a correct, not a guessed, backfill for NEW imports; pre-existing Stripe-imported rows keep `currency = NULL`, read as "unknown/assume USD" by any future multi-currency display work — out of scope here).
   - New table `bank_link_sessions` (Assumption 4) — provider-scoped to `'gocardless'` only (Stripe never needs a pending-session row of its own).
   - **Rename scope note**: `financial_connections.rs`'s existing `#[cfg(test)]` module and any raw-SQL test seeding in `rag.rs` that insert into `linked_accounts`/reference `stripe_account_id`/`stripe_customer_id`/`stripe_transaction_id` by name are part of this rename, not just production code — the plan's Task 1 explicitly enumerates these test-fixture touch points so "existing tests pass unchanged" (success criteria) is actually achievable.
10. **Consent-expiry detection is folded into the transactions call itself, not a separate status check** (keeps the poll job to one GoCardless call per account per cycle — see Assumption 3's rate-limit accounting). `gocardless::sync_account_transactions` calls the transactions endpoint directly; GoCardless returns a distinct error (documented as a 409/403-class response identifying the account status as `EXPIRED`/`SUSPENDED`) when consent has lapsed. On that specific error shape, mark the local row `status = 'consent_expired'` (idempotent — a repeat detection is a no-op UPDATE) and return `Ok(0)` (a clean no-op, not an error — mirrors the Stripe webhook's "lapsed subscription" no-op shape); any OTHER GoCardless error is treated as a real transient failure (propagated `Err`, same as `financial_connections.rs`'s existing contract). This is what makes re-consent an explicit, surfaced state (AC: "not silent failure") rather than transactions quietly stopping with no visible cause: `LIST_LINKED_ACCOUNTS` (REST + chat) renders a `consent_expired` account distinctly ("needs reconnecting"), and the manual-refresh action on a `consent_expired` account short-circuits with a clear, actionable message rather than attempting a doomed sync (checked against the locally-stored status BEFORE calling GoCardless at all, so it costs zero API calls).
11. **Re-consent reuses the same start-link flow, with a bounded reconciliation heuristic.** There is no separate "reconnect" endpoint — re-consenting is "run `LINK_BANK_ACCOUNT` again for the same country/institution." Because GoCardless does not guarantee a stable account id across a fresh requisition for every bank, `complete_link_session` reconciles a newly-returned GoCardless account against an existing `consent_expired` row for the SAME `budget_id` + `institution_id` by matching IBAN (`GET /accounts/:id/details/`) when available: a match REPLACES that row's `provider_account_id`/`provider_ref`/`consent_expires_at`/`status` (preserving the local row id, and therefore all `transactions.external_account_id` history) instead of inserting a new disconnected-looking duplicate. No IBAN match (or IBAN unavailable) falls back to inserting a new row — documented as a known, bounded v1 limitation (mirrors the categorization heuristic's "cheap and honest, not perfect" precedent from #303), not a silent data-loss bug: no history is ever deleted either way.
12. **Pro-gating mirrors #303 exactly**: starting a new link and manual refresh are Pro-gated (402, no GoCardless call made); viewing and disconnecting are NOT (a lapsed user keeps control of their own data). The poll job's Pro check is the auto-refresh analogue of the Stripe webhook's Pro check.
13. **Disconnect deletes the GoCardless requisition** (`DELETE /requisitions/:id/`, mirroring Stripe's "call the provider first, then flip the local flag" ordering and its idempotent-tolerance precedent) before writing `status = 'disconnected'` locally — ends the bank-side consent so no further polling is possible even if the local flip somehow failed to stick.
14. **Currency is recorded, never converted.** `transactions.currency` is populated per-row from the source; no aggregation, budget total, or display logic in this ticket performs cross-currency math — a GBP and a USD transaction both simply show their own `amount`/`currency` on the same `transactions` list, exactly as the AC specifies ("no FX conversion... multi-currency display/aggregation is explicitly out of scope").
15. **Chat surface**: `LINK_BANK_ACCOUNT` gains two new optional `AiActionParams` fields, `country` and `institution_query`. The system prompt (rule 2o) is extended so the model asks for a country when absent/unsupported (naming the 9 supported: US, GB, FR, DE, IT, ES, DK, FI, NO) and for a bank name when the country resolves to GoCardless and no institution was named — these are ordinary clarifying questions (`response_text`, no `action` mutation performed), the same non-mutating-question shape already used by `CREATE_BUDGET`'s missing-strategy clarification (§13 in AGENTS.md). `LIST_LINKED_ACCOUNTS`/`UNLINK_BANK_ACCOUNT`/`REFRESH_BANK_ACCOUNT` need no new params — they already operate on "linked accounts for this budget" regardless of provider, and (per Assumption 8) now call the provider-agnostic `bank_linking::*` functions instead of `financial_connections::*` directly.
16. **`ChatResponse` gains `bank_link_redirect_url: Option<String>`** (alongside the existing `financial_connections_client_secret`) — set only when `LINK_BANK_ACCOUNT` resolves to GoCardless. The frontend does a full-page `window.location.href` navigation on seeing this field, vs. opening the Stripe.js modal for the existing field.
17. **Frontend return-trip handling**: per Assumption 5, GoCardless redirects the browser to exactly `{APP_URL}/?gc_ref=<session.id>` — the app's existing root URL with an extra query param we chose ourselves (no dedicated `/gocardless/callback` route needed; this frontend is a single-page app with client-side routing already in `App.svelte`, and standing up a second server-routed path is unnecessary when we control the whole redirect string). `App.svelte`, on mount, checks for `gc_ref` in the URL, calls `POST /api/budgets/:id/gocardless/complete` with it (against the user's currently-active budget), shows the result, and strips the param from the URL (`history.replaceState`) so a page refresh doesn't re-submit it.
18. **No marketing site changes** — authenticated-app feature only, same as #303.
19. **GoCardless sandbox/test seam**: `GOCARDLESS_API_BASE` env var (default `https://bankaccountdata.gocardless.com/api/v2`), mirroring `STRIPE_API_BASE`, so integration tests point at a local `wiremock` server exactly like `financial_connections.rs`'s existing test suite.
20. **GoCardless amounts are decimal strings, not integer cents — a separate normalization function from Stripe's.** Each GoCardless transaction carries `transactionAmount: {amount: "-15.00", currency: "EUR"}` (a decimal string, sign meaningful) rather than Stripe's integer-cents `amount`. `gocardless::normalize_amount(amount_str: &str) -> Option<f64>` parses the string directly (via `str::parse::<f64>()`, guarded against a malformed string returning `None` rather than panicking) and takes the absolute value, matching this codebase's existing "amount is always a positive magnitude" convention — mirrors `financial_connections::normalize_amount`'s contract but is its own unit-tested pure function, NOT a shared/reused one, since the input shape (decimal string vs. integer cents) genuinely differs. Only GoCardless's `transactions.booked` array is imported (not `pending`): a pending entry can lack a stable id and later reappear under a different id once booked, which would either fail to dedupe or silently skip the eventual booked version depending on ordering — importing only `booked` avoids that whole class of bug, at the documented cost of not showing not-yet-settled transactions (a reasonable v1 tradeoff, analogous to accepting Stripe's default lookback window rather than backfilling further history).

## 3. Goal & Success Criteria

Pro subscribers in the UK, France, Germany, Italy, Spain, Denmark, Finland, and Norway can link one or more bank accounts via GoCardless Bank Account Data, following the same redirect-then-return shape the ticket describes, with transactions landing in the existing `transactions` table (currency-tagged, no FX conversion). Auto-refresh happens via a scheduled poll (no GoCardless webhook exists) plus manual refresh; PSD2 ~90-day consent expiry is detected and surfaced explicitly, with re-consent handled through the same link flow. View/disconnect and chat reachability match #303's UX. The `linked_accounts.provider` generalization and a `bank_linking.rs` orchestration layer mean `rag.rs`, the list/refresh/disconnect REST handlers, and the frontend's account list all treat Stripe and GoCardless accounts uniformly except at the point of starting a brand-new link.

Success criteria:
- [ ] A Pro user in a GoCardless country can complete an end-to-end link (start → GoCardless-hosted consent page → return → `linked_accounts` row persisted with `provider='gocardless'`, `consent_expires_at` set) via REST, and it appears via chat's `LIST_LINKED_ACCOUNTS` indistinguishably from a Stripe-linked account (same response shape, `provider` field added).
- [ ] A non-Pro user's attempt to start a GoCardless link (REST or chat) is rejected with a clear upgrade prompt and makes zero GoCardless API calls.
- [ ] The scheduled poll job imports new transactions idempotently for active, Pro-owned, non-closed-budget GoCardless accounts; skips (no GoCardless call) for lapsed-Pro or closed-budget accounts, same as the Stripe webhook's gating.
- [ ] A GoCardless account whose consent has expired (detected via the account status field) flips to `consent_expired` locally, is surfaced distinctly by `LIST_LINKED_ACCOUNTS`, and a manual refresh attempt on it returns a clear re-consent-needed message instead of a generic failure.
- [ ] Re-running the link flow for the same institution while a `consent_expired` row exists reconciles onto the existing row (by IBAN match) rather than creating an orphaned duplicate, when GoCardless returns a matching IBAN.
- [ ] Disconnecting a GoCardless account (REST + chat) deletes the GoCardless requisition, marks it locally disconnected, and preserves its historical transactions.
- [ ] Existing #303 Stripe tests all still pass unchanged after the `provider`/`provider_account_id`/`provider_ref`/`provider_transaction_id` rename refactor — behavior-preserving, per the ticket's explicit instruction.
- [ ] All new pure logic (institution fuzzy-match, country→provider mapping, consent-expiry detection, IBAN reconciliation decision, currency passthrough) is unit tested; DB/HTTP-touching flows have `#[ignore]`+`wiremock` integration tests mirroring `financial_connections.rs`'s existing style.

## 4. Scope

**In scope**: migration generalizing `linked_accounts`/`transactions` + new `bank_link_sessions` table; `backend/src/bank_provider.rs` (Provider enum); `backend/src/gocardless.rs` (GoCardless HTTP integration: token mgmt, institutions, agreements, requisitions, accounts, transactions, disconnect, consent-expiry + IBAN reconciliation); `backend/src/bank_linking.rs` (shared list/refresh/disconnect/sync dispatch); refactor of `financial_connections.rs`/`db.rs`/`main.rs`/`rag.rs` onto the generalized schema and shared dispatch (behavior-preserving for Stripe); new REST endpoints (start/complete/institutions for GoCardless); scheduled poll job; chat action extensions (`LINK_BANK_ACCOUNT` country/institution params, provider-agnostic list/refresh/unlink); frontend (country+institution picker, redirect handling, `consent_expired` UI state, i18n); AGENTS.md documentation; tests.

**Out of scope**: countries beyond the 8 GoCardless ones + existing US/Stripe; any FX conversion or multi-currency aggregation/display beyond storing `currency` per row; a dedicated institution-logo/branding UI; ML-based categorization (reuses #303's existing substring heuristic unchanged, applied to GoCardless transactions' own description field too); building a generic `dyn BankProvider` trait-object system for a hypothetical third provider; retrying/backfilling transaction history beyond GoCardless's `max_historical_days` window; admin console changes; marketing site changes.

## 6. Error Handling & Edge Cases

- Unsupported country (chat or REST) → 400 / clarifying question, no GoCardless call.
- Institution not found / ambiguous → 400 with candidate list (REST) or clarifying question (chat), no requisition created.
- `complete_link_session` reference not found, or found but `budget_id`/`user_id` mismatch → 404 / 403 respectively (anti-replay), mirrors Stripe's customer-mismatch handling.
- GoCardless token fetch/refresh failure → 502 (mirrors `stripe_post`/`stripe_get`'s `BAD_GATEWAY` convention), logged.
- Consent expired mid-poll → local status flips, no error surfaced to the poll job caller (it's a scheduled job, nothing user-facing to show synchronously) — surfaced instead the next time the user views/refreshes.
- Manual refresh on a `consent_expired` account → clear 409-with-message ("this account's consent has expired — reconnect it") rather than attempting (and failing) a GoCardless call.
- Manual refresh/disconnect on a nonexistent/foreign account id → 404, same as Stripe's existing behavior.
- Closed budget → every mutating path (start link, complete link, manual refresh, poll-driven sync) no-ops/rejects, mirroring #303's closed-budget guard exactly.
- GoCardless rate-limit response (HTTP 429) during poll → logged, `last_synced_at` NOT advanced for that account this cycle (so the discrepancy is visible), no retry-storm (poll job simply waits for its next scheduled tick).

## 7. Testing Approach

- Unit tests (no DB/HTTP): `Provider::for_country`/`parse`, institution fuzzy-match (`find_institution_id`), consent-expiry-status mapping, IBAN-reconciliation decision function, currency passthrough, offline chat-router country/institution phrase extraction.
- `#[ignore]`+`wiremock` DB-integration tests, mirroring `financial_connections.rs`'s existing suite exactly: Pro-gate rejection, full link→sync happy path, idempotent re-sync, consent-expiry detection flipping status, reconciliation-onto-existing-row on re-link, disconnect calling GoCardless's delete endpoint, closed-budget guards on every mutating path, poll-job Pro/closed-budget gating.
- A migration-only smoke: run the new migration against a fresh + against a #303-seeded DB, confirm existing Stripe rows read back with `provider='stripe'` and all renamed columns present.
- Frontend: `linkedAccounts.test.js` gains GoCardless start/complete/`consent_expired`-rendering cases; component test for the country/institution picker and the `gc_ref` completion flow.

## 8. Risks & Open Questions

- **IBAN-based reconciliation is a best-effort heuristic** (Assumption 11) — some banks don't return IBAN via GoCardless's `details` endpoint, or return a masked one; those re-consents create a new row rather than reconciling onto the old one. Documented, not silently wrong (no data is lost either way — only a cosmetic "duplicate-looking" entry results).
- **GoCardless sandbox behavior may differ from documented production behavior** for institution status transitions/rate limits — the `wiremock`-based tests validate this codebase's own handling of documented response shapes, not live sandbox parity (same caveat #303's spec carries for Stripe).
- **Poll interval (default 8h, 3 calls/account/day) is a judgment call** balancing "auto-refresh feels timely" against GoCardless's stated ~4-calls/day/account guidance, leaving 1 call/day of headroom for the initial link-time sync and manual refreshes; configurable via env for ops to tune without a code change.
